## Background

You write a CUDA kernel, and a few hundred milliseconds later the GPU runs it. In between, a
compiler has turned C++ into instructions for NVIDIA's hardware. For a large share of GPU code
that compiler is **LLVM**: Clang compiles CUDA with it, Triton (and so
[TorchInductor](/blog/torch-inductor/)) generates GPU code through it, and the
[MLIR](/blog/mlir/) stacks under Triton and the CuTe DSL end by handing LLVM IR to it.

Knowing how LLVM works explains things you see every day when you read generated code. Why does
`a * x[i] + y[i]` become a single `fma` instruction? Why does the PTX declare loads as
`ld.global` when the source only had plain pointers? Why does a float `atomicAdd` sometimes turn
into a loop? Why does PTX never spill a register, while the same kernel in SASS (the GPU's real
machine code) does? Each answer lives in a specific part of LLVM, and to find it you have to be
able to read three languages: LLVM IR, TableGen and PTX.

This post teaches the first two from the syntax up, and follows one small kernel through all of
LLVM. It starts with the big picture, then reads **LLVM IR**, the language at the centre: names,
types, every family of instructions, attributes and metadata, ending with a program written and
run by hand. Next comes the **optimizer**, then the **backend** that turns IR into machine code:
the SelectionDAG, instruction selection, Machine IR and code emission, with a guide to reading
each one's dumps. Then **TableGen**, the language that describes a target to the backend, from toy
files to NVPTX's real instruction definitions and the C++ they generate. Finally, the **NVPTX
backend**, LLVM's code generator for NVIDIA GPUs, through kernels that use shared memory,
barriers, warp shuffles, atomics and vector loads. Every listing is real output from LLVM 23.1.2,
and every link into LLVM's source points at the same pinned commit. The [PTX post](/blog/ptx/)
covers the output language itself.

## The big picture

### Three phases

A compiler for $M$ languages and $N$ machines could be $M \times N$ separate programs. LLVM is
built so it needs only $M + N$ pieces. A **front end** turns one language into **LLVM IR** (its
intermediate representation). An **optimizer** improves the IR without caring where it came from.
A **back end** turns IR into code for one machine. Any front end can then pair with any back end,
and every language gets every optimization for free.

<LlvmOverview />

The highlighted path is the one this post follows. **Clang** compiles a CUDA kernel to IR, the
optimizer (the `opt` tool) improves it, and the **NVPTX** back end (run by the `llc` tool) turns
it into **PTX**, NVIDIA's virtual instruction set. NVIDIA's own assembler, **ptxas**, then
compiles PTX into **SASS** for a specific GPU. That last step is outside LLVM.

### One kernel, end to end

The running example is `saxpy`, $y \leftarrow a x + y$, one thread per element:

```cpp
extern "C" __global__ void saxpy(int n, float a, const float *x, float *y) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n)
    y[i] = a * x[i] + y[i];
}
```

Two commands take it to PTX, with LLVM IR in between:<Sidenote>The listings come from Homebrew's
LLVM 23.1.2 on macOS, which has no CUDA toolkit. So the clang command also passes `-nocudainc
-nocudalib`, the file includes clang's own `__clang_cuda_builtin_vars.h` (which defines
`threadIdx` and friends), and `__global__` is defined as `__attribute__((global))`, which is what
the CUDA headers define it as. None of this changes the generated code.</Sidenote>

```bash
clang++ -x cuda --cuda-device-only --cuda-gpu-arch=sm_90 -O2 -S -emit-llvm saxpy.cu -o saxpy.ll
llc -mtriple=nvptx64-nvidia-cuda -mcpu=sm_90 -O2 saxpy.ll -o saxpy.ptx
```

## LLVM IR

### Modules, functions and blocks

Here is the complete IR Clang writes for `saxpy` at `-O2`, nothing removed:

```llvm
; ModuleID = 'saxpy.cu'
source_filename = "saxpy.cu"
target datalayout = "e-p6:32:32-i64:64-i128:128-i256:256-v16:16-v32:32-n16:32:64"
target triple = "nvptx64-nvidia-cuda"

; Function Attrs: mustprogress nofree noinline norecurse nosync nounwind willreturn memory(argmem: readwrite)
define dso_local ptx_kernel void @saxpy(i32 noundef %0, float noundef %1, ptr nofree noundef readonly captures(none) %2, ptr nofree noundef captures(none) %3) local_unnamed_addr #0 {
  %5 = tail call noundef i32 @llvm.nvvm.read.ptx.sreg.ctaid.x()
  %6 = tail call noundef i32 @llvm.nvvm.read.ptx.sreg.ntid.x()
  %7 = mul i32 %5, %6
  %8 = tail call noundef i32 @llvm.nvvm.read.ptx.sreg.tid.x()
  %9 = add i32 %7, %8
  %10 = icmp slt i32 %9, %0
  br i1 %10, label %11, label %19

11:                                               ; preds = %4
  %12 = sext i32 %9 to i64
  %13 = getelementptr inbounds [4 x i8], ptr %2, i64 %12
  %14 = load float, ptr %13, align 4, !tbaa !8
  %15 = fmul contract float %1, %14
  %16 = getelementptr inbounds [4 x i8], ptr %3, i64 %12
  %17 = load float, ptr %16, align 4, !tbaa !8
  %18 = fadd contract float %15, %17
  store float %18, ptr %16, align 4, !tbaa !8
  br label %19

19:                                               ; preds = %11, %4
  ret void
}

; Function Attrs: mustprogress nocallback nofree nosync nounwind speculatable willreturn memory(none)
declare noundef range(i32 0, 2147483647) i32 @llvm.nvvm.read.ptx.sreg.ctaid.x() #1

; Function Attrs: mustprogress nocallback nofree nosync nounwind speculatable willreturn memory(none)
declare noundef range(i32 1, 1025) i32 @llvm.nvvm.read.ptx.sreg.ntid.x() #1

; Function Attrs: mustprogress nocallback nofree nosync nounwind speculatable willreturn memory(none)
declare noundef range(i32 0, 1024) i32 @llvm.nvvm.read.ptx.sreg.tid.x() #1

attributes #0 = { mustprogress nofree noinline norecurse nosync nounwind willreturn memory(argmem: readwrite) "frame-pointer"="all" "no-trapping-math"="true" "stack-protector-buffer-size"="8" "target-cpu"="sm_90" "target-features"="+sm_90" "uniform-work-group-size" }
attributes #1 = { mustprogress nocallback nofree nosync nounwind speculatable willreturn memory(none) }

!llvm.module.flags = !{!0, !1}
!llvm.ident = !{!2}
!llvm.errno.tbaa = !{!3}

!0 = !{i32 4, !"nvvm-reflect-ftz", i32 0}
!1 = !{i32 7, !"frame-pointer", i32 2}
!2 = !{!"Homebrew clang version 23.1.2"}
!3 = !{!4, !5, i64 0}
!4 = !{!"__libc_errno", !5, i64 0}
!5 = !{!"int", !6, i64 0}
!6 = !{!"omnipotent char", !7, i64 0}
!7 = !{!"Simple C++ TBAA"}
!8 = !{!9, !9, i64 0}
!9 = !{!"float", !6, i64 0}
```

That looks like a lot, but it has only four levels, each inside the one before:

- A **module** is one file of IR. It starts with the **target triple** (here
  `nvptx64-nvidia-cuda`) and the **data layout**, which records facts the optimizer needs about
  the target, such as type sizes and alignments. Then come globals, functions, attribute groups and
  metadata, in any order.
- A **function** is a `define` with a body, or a `declare` without one. Its parameters are
  `%0` to `%3`, in source order: `n`, `a`, `x`, `y`.
- A **basic block** is a straight run of instructions with one way in (the top) and one way out
  (its last instruction). This function has three: the entry block, `%11` (the `if` body) and
  `%19` (the return).
- The last instruction of every block is a **terminator**: a branch (`br`), a `switch` or a
  return (`ret`).

Everything after `;` on a line is a comment. Clang adds comments of its own: the `; preds = %4`
after a block label lists the blocks that branch to it, and `; Function Attrs:` repeats a
function's attribute group in readable form. The rest of this section takes the listing apart
piece by piece.

#### Names and sigils

Every name in IR starts with a character that says what kind of thing it is. Once you know the
five, the listing becomes much easier to scan.

| Sigil | Names | Example | Scope |
| ----- | ----- | ------- | ----- |
| `@` | a global: function or global variable | `@saxpy`, `@llvm.nvvm.read.ptx.sreg.tid.x` | the module |
| `%` | a local value: parameter, instruction result, block label | `%0`, `%13`, `%11` | one function |
| `%` (at top level) | a named type | `%struct.Particle` | the module |
| `#` | an attribute group | `#0` | the module |
| `!` | metadata | `!8`, `!llvm.module.flags` | the module |

Names are either **named** (`%x`, `@saxpy`) or **numbered** (`%13`). Unnamed values are numbered
in order, starting at 0 in each function: `%0` to `%3` are the parameters, `%4` is the entry block
(which has no label line), and so on. Clang keeps source names only in debug builds, so optimized
IR is mostly numbers.<Sidenote>That is why the entry block's number, `%4`, appears only in the
`; preds = %4` comments. Names with odd characters are quoted, as in `@"my name"`. Numbering is
strict: if you write IR by hand with numbered values, they must appear in order with no
gaps.</Sidenote>

**Linkage** says who else can see a global. The common ones, and what produces them from C++:

| Linkage | Visible to | Produced by |
| ------- | ---------- | ----------- |
| (none written) = `external` | other modules | an ordinary function or global |
| `internal` | this module only | `static`, anonymous namespaces, function-local statics |
| `private` | this module only, and not even in the symbol table | string literals, compiler-made constants |
| `linkonce_odr` | merged with identical copies; dropped if unused | inline functions, templates |
| `weak_odr` | merged with identical copies; kept | explicit template instantiations |

A few global declarations, all accepted by `llvm-as`:

```llvm
@counter = internal global i32 0, align 4
@table   = private unnamed_addr constant [3 x i32] [i32 1, i32 2, i32 4], align 4
@weights = external addrspace(4) global [16 x float]    ; defined elsewhere, in constant memory
```

#### Attributes

**Attributes** are facts and promises attached to functions, parameters and return values. Front
ends add some, and the optimizer's attribute-inference passes (`PostOrderFunctionAttrs` in the
[optimizer table](#the-optimizer)) add more. Later passes rely on them: a `readonly` pointer
can't be the target of a store, so loads through it can move freely. The ones in this post:

| Attribute | On | Means |
| --------- | -- | ----- |
| `noundef` | param, return | the value is never `undef` or `poison` |
| `readonly`, `writeonly` | pointer param | the function only reads, or only writes, through it |
| `captures(none)` | pointer param | the pointer doesn't outlive the call |
| `noalias` | pointer param | no other pointer reaches the same memory (from `__restrict__`) |
| `byval(T)` | pointer param | the argument is a copy of a `T`, passed by value |
| `range(i32 0, 1024)` | return | the result lies in $[0, 1024)$ |
| `nounwind` | function | never throws |
| `memory(argmem: readwrite)` | function | touches only memory reachable from its pointer arguments |
| `convergent` | function, call | can't be made control-dependent on more values (barriers, shuffles) |
| `"target-cpu"="sm_90"` | function | a string attribute: free-form key and value for the backend |

`convergent` matters on GPUs. A barrier must be reached by all threads of a block together, so the
optimizer must not, for example, move a `__syncthreads()` inside an `if` that only some threads
take. The [reduction kernel](#shared-memory-and-barriers) below carries it.

#### Metadata

**Metadata** is information about the code that is not part of its meaning: dropping it must
never change what the program computes, only how well it is optimized or debugged. Metadata nodes
are written `!{...}`, numbered `!0`, `!1`, ..., and attached to instructions after a comma:

- `!tbaa !8` on the loads and store is **type-based alias analysis** metadata. `!8` says "an
  access to a `float`" (whose type node is `!9`); `int` has the type node `!5`. C++'s aliasing rules say a
  `float` access and an `int` access can never touch the same memory, and this is how the
  optimizer learns it.
- `!llvm.module.flags` is a **named metadata** list of module-wide flags. `!0 = !{i32 4,
  !"nvvm-reflect-ftz", i32 0}` reads: behaviour 4 (*override* when modules are linked), key
  `nvvm-reflect-ftz`, value 0. The [NVVMReflect](#special-registers-intrinsics-and-nvvmreflect)
  pass reads it.
- `!llvm.loop !10` on a loop's back-edge branch carries loop hints, such as "don't unroll"; one
  appears in the [reduction kernel](#shared-memory-and-barriers).

### Types

IR is **typed**, and every value has exactly one type. The full set is small:

| Type | Example | Notes |
| ---- | ------- | ----- |
| integer `iN` | `i1`, `i8`, `i32`, `i64`, `i33` | any width from 1 bit; no sign |
| floating point | `half`, `bfloat`, `float`, `double` | 16, 16, 32 and 64 bits |
| pointer | `ptr`, `ptr addrspace(3)` | opaque: no pointee type, only an address space |
| vector | `<4 x float>` | SIMD values; arithmetic works lane by lane |
| array | `[256 x float]` | fixed length, in memory |
| structure | `{ float, float, i32 }`, `<{ i8, i32 }>` | fields in order; `<{ }>` is packed, without padding |
| named struct | `%Particle = type { float, float, i32 }` | a struct with a name, defined at top level |
| `void`, `label` | | no value; a basic block |

Integer types carry no sign: the instruction says how to treat the bits, so the comparison in
`saxpy` is `icmp slt` ("signed less than") and the widening of `i` is `sext` ("sign extend"). Odd
widths are real. When `opt` rewrote the loop of [a hand-written program](#writing-and-running-ir-by-hand)
below, it used an `i33` so that a product of two 32-bit values could not overflow.

Pointers used to say what they point to (`float*`), but since LLVM 15 every pointer is just `ptr` (typed pointers were removed entirely in LLVM 17).
The type of the memory is given by the instruction that uses it instead: `load float, ptr %13`
loads a `float`.

The **data layout** string says how big and how aligned each type is on the target. It is a list
of specifications separated by `-`. Decoding NVPTX's:

| Spec | Means |
| ---- | ----- |
| `e` | little-endian |
| `p6:32:32` | pointers in address space 6 are 32 bits, 32-bit aligned (all others: the default, 64 bits) |
| `i64:64` | `i64` is 64-bit aligned (likewise `i128:128`, `i256:256`) |
| `v16:16`, `v32:32` | 16- and 32-bit vectors are aligned to their size |
| `n16:32:64` | native integer widths: the optimizer prefers arithmetic in 16, 32 or 64 bits |

A **constant** is written as its type and value: `i32 7`, `float 1.0`, `float 0x3FB99999A0000000`
(floats that aren't exact in decimal are written in hex), `<4 x float> splat (float 2.0)`,
`[3 x i32] [i32 1, i32 2, i32 4]`, `zeroinitializer`, `null`, and the two special values `undef`
and `poison`, explained under [flags](#flags-and-poison).

### Instructions

LLVM IR has about 70 instructions (opcodes 1 to 69 in `Instruction.def`). They fall into a few families, and once you know one member of
each, the rest read the same way. Every result in the tables below was checked by running the
instructions with `lli`, LLVM's interpreter and JIT, on the host CPU.

#### Arithmetic and bitwise

`add`, `sub`, `mul` work on integers and don't care about sign: in two's complement the bits of
the result are the same. Division, remainder and right shift do care, so each comes in two
versions:

| Instruction | Result | Why |
| ----------- | -----: | --- |
| `sdiv i32 -7, 2` | −3 | signed, rounds toward zero |
| `udiv i32 -7, 2` | 2147483644 | the bits of −7 read as unsigned are $2^{32} - 7 = 4294967289$ |
| `srem i32 -7, 2` | −1 | the remainder takes the dividend's sign |
| `ashr i32 -8, 1` | −4 | arithmetic shift copies the sign bit in |
| `lshr i32 -8, 1` | 2147483644 | logical shift fills with zero |

The bitwise ones are `and`, `or`, `xor` and `shl`. Floating point has its own: `fadd`, `fsub`,
`fmul`, `fdiv`, `frem` and `fneg`. All of them also work lane by lane on vectors:
`fmul <4 x float> %v, splat (float 2.0)` doubles four floats at once, and `extractelement` /
`insertelement` read and write one lane.

#### Flags and poison

Some instructions take flags that give the optimizer extra facts. On integer arithmetic, `nsw`
("no signed wrap") and `nuw` ("no unsigned wrap") promise the operation doesn't overflow. If it
does, the result is **poison**: a value that stands for "this computation went wrong". Poison is
not immediately undefined behaviour. It spreads through the instructions that use it, and only
becomes undefined behaviour when it matters, for example when a branch depends on it.

That promise is worth a lot. Here are two functions that compute `x + 1 > x`, one with `nsw`
and one without, and what `opt -passes=instcombine` makes of them:

```llvm
define i1 @with_nsw(i32 %x) {           ; after instcombine:
  %y = add nsw i32 %x, 1                ;   ret i1 true
  %c = icmp sgt i32 %y, %x
  ret i1 %c
}

define i1 @without_nsw(i32 %x) {        ; after instcombine:
  %y = add i32 %x, 1                    ;   %c = icmp ne i32 %x, 2147483647
  %c = icmp sgt i32 %y, %x              ;   ret i1 %c
  ret i1 %c
}
```

With `nsw` the answer is always true, because $x + 1$ can't overflow. Without it, $x = 2^{31} - 1$
wraps to $-2^{31}$, so the comparison is false for exactly that one value, and the optimizer has
to keep a test for it. C and C++ say signed overflow is undefined, so Clang puts `nsw` on every
signed `int` add. That is why a loop over `int i` optimizes better than one over `unsigned i`.

Other flags work the same way: `exact` on `sdiv`/`udiv`/`ashr`/`lshr` (no remainder or bits
shifted out), `nneg` on `zext` (the input is non-negative), `inbounds` and `nuw` on
`getelementptr`, and the fast-math flags on floating point, such as `contract`.

#### Comparisons and select

`icmp` compares integers and `fcmp` floats; both return an `i1`. The predicate says how:

| `icmp` | Means | `fcmp` | Means |
| ------ | ----- | ------ | ----- |
| `eq`, `ne` | equal, not equal | `oeq`, `one` | ordered: false if either is NaN |
| `slt`, `sle`, `sgt`, `sge` | signed | `olt`, `ole`, `ogt`, `oge` | ordered |
| `ult`, `ule`, `ugt`, `uge` | unsigned | `ueq`, `ult`, ... | unordered: true if either is NaN |

The same bits compare differently under each: `icmp ult i32 -1, 1` is false, because −1 read as
unsigned is $2^{32} - 1$, while `icmp slt i32 -1, 1` is true.

`select` picks one of two values without branching, like C's `?:`:

```llvm
%neg = icmp slt i32 %x, 0
%r = select i1 %neg, i32 0, i32 %x      ; r = x < 0 ? 0 : x
```

On a GPU this matters: a `select` keeps every thread of a warp on the same path, while a branch
can make them diverge. NVPTX turns a `select` into `selp`, or into something better: the
[hand-written kernel](#writing-nvptx-ir-by-hand) below shows a compare and a select becoming a
single `max.f32`.

#### Casts

A **cast** changes a value's type. Each one says exactly what happens to the bits:

| Cast | Example | Result |
| ---- | ------- | -----: |
| `trunc` | `trunc i32 300 to i8` | 44 (keeps the low 8 bits: $300 - 256$) |
| `zext` | `zext i8 -3 to i32` | 253 (fills with zeros) |
| `sext` | `sext i8 -3 to i32` | −3 (copies the sign bit) |
| `fptosi` | `fptosi float -2.7 to i32` | −2 (rounds toward zero) |
| `sitofp`, `uitofp` | `sitofp i32 -2 to float` | −2.0 |
| `fptrunc`, `fpext` | `fpext float %f to double` | the same number, wider |
| `bitcast` | `bitcast float 1.0 to i32` | 1065353216, which is `0x3F800000`: the same bits |
| `ptrtoint`, `inttoptr` | `ptrtoint ptr %p to i64` | the address as an integer |
| `addrspacecast` | `addrspacecast ptr %p to ptr addrspace(1)` | the same object, seen from another address space |

`addrspacecast` is the one the NVPTX backend cares about most; it is how generic pointers
become [global ones](#kernel-parameters-and-address-spaces).

#### Memory

Three instructions touch memory, and they are deliberately simple:

```llvm
%p = alloca i32, align 4              ; reserve 4 bytes on the stack, %p points to them
store i32 7, ptr %p, align 4          ; write: no result
%v = load i32, ptr %p, align 4        ; read: %v = 7
```

`alloca` reserves stack memory for the life of the function. `load` names the type it reads and
the pointer it reads from; `store` names the value it writes and the pointer it writes to. `align
4` promises the address is a multiple of 4. A `volatile` keyword stops the optimizer from removing
or merging the access. Clang's `-O0` output puts every local variable in an `alloca`; the
[optimizer section](#the-optimizer) shows how they disappear.

#### getelementptr

The instruction that surprises people is **getelementptr** (GEP). It only computes an address and
never touches memory. In `saxpy`:

```llvm
%13 = getelementptr inbounds [4 x i8], ptr %2, i64 %12
```

reads "start at `%2` (that is `x`) and step `%12` elements of type `[4 x i8]`", which is $4 \cdot
i$ bytes. Check one entry: for $i = 3$, `%13` is `x + 12`, the address of `x[3]`. The `load` on
the next line then reads it.

GEP gets interesting with structs and nested arrays, where it takes several indices. The first
index steps over whole objects of the given type; each later one goes one level inside:

So `&p[2].y` is $2 \cdot 12 + 4 = 28$ bytes from `p`. For a 2-D array, `getelementptr [4 x [8 x

integers.<Sidenote>`ptrtoint (getelementptr %Particle, ptr null, i64 2, i32 1)` printed 28, and the

"GEP from null" trick is how IR computes `sizeof` and `offsetof`.</Sidenote>

The optimizer rewrites these into a canonical byte-based form. `opt -passes=instcombine` turns the
struct GEP into two simpler ones:

```llvm
%q.split = getelementptr inbounds [12 x i8], ptr %p, i64 %i    ; + 12 * i
%q = getelementptr inbounds nuw i8, ptr %q.split, i64 4        ; + 4
```

which is the same `[4 x i8]` style seen in `saxpy`. NVPTX then selects `mad.lo.s64 %rd3, %rd2,
12, %rd1` and `add.s64 %rd4, %rd3, 4`: the address is $12 i + p + 4$.

#### Control flow and calls

Terminators end a block and say where to go next:

```llvm
br i1 %10, label %11, label %19        ; conditional: true → %11, false → %19
br label %19                           ; unconditional
switch i32 %k, label %other [          ; jump table: 0 → %zero, 1 → %one, else %other
  i32 0, label %zero
  i32 1, label %one
]
ret void                               ; return nothing; ret i32 %v returns a value
unreachable                            ; control never gets here
```

`call` runs a function: `%5 = tail call noundef i32 @llvm.nvvm.read.ptx.sreg.ctaid.x()`. The
`tail` marker says the callee doesn't use the caller's stack, `noundef` is an attribute on the
return value, and then come the return type, the callee and the arguments. A **variadic** call,
such as to `printf`, writes the function's type first: `call i32 (ptr, ...) @printf(ptr @fmt,
i32 %v)`.

The other atomics are `cmpxchg` (compare and swap), `fence` (an ordering without an access) and
`load atomic` / `store atomic`. `cmpxchg` returns a struct of two values, the old value and a
success bit, which `extractvalue` takes apart:

```llvm
%pair = cmpxchg ptr @counter, i32 0, i32 1 acq_rel monotonic, align 4  ; if 0, make it 1
%got  = extractvalue { i32, i1 } %pair, 0                              ; the old value
%ok   = extractvalue { i32, i1 } %pair, 1                              ; did it swap?
```

It takes two orderings: one for success and one, never stronger, for failure. The
[NVPTX section](#warp-shuffles-and-atomics) shows how these become PTX `atom` instructions, and
when an `atomicrmw` becomes a `cmpxchg` loop instead.

### SSA form and φ-nodes

Look again at the listing: every `%name` is assigned exactly once. That is **static single
assignment** (SSA) form, and all of LLVM's optimizer relies on it. Because a value has a single
definition, "where does this value come from?" has a single answer, so passes can follow a value
from its definition straight to its uses.

Loops seem to break this, since a loop counter changes on every trip. SSA handles it with a
**φ-node** (`phi`) at the start of a block, which picks a value depending on which block control
came from. Here is a dot product, $s = \sum_i x_i y_i$, compiled the same way:<Sidenote>Compiled
with `-O2 -fno-unroll-loops`, so the loop stays one iteration per trip and the graph stays
small.</Sidenote>

```cpp
extern "C" __device__ float dot(const float *x, const float *y, int n) {
  float s = 0.0f;
  for (int i = 0; i < n; ++i)
    s += x[i] * y[i];
  return s;
}
```

Its IR, drawn as a **control-flow graph** (CFG), with one box per basic block. Hover any
`%value` to see its single definition and all its uses; `%16`, the running sum, is highlighted to
start.

<IrCfg ir={dotIr} focus="%16" title="dot(), optimized IR as a control-flow graph" />

Block `%7` is the loop body, and it branches back to itself. Its first instruction,

```llvm
%8 = phi i32 [ %17, %7 ], [ 0, %3 ]
```

reads "`%8` is `%17` if we arrived from `%7` (the previous trip), or `0` if we arrived from the
entry block `%3`". Each `[ value, block ]` pair is one incoming edge, and a φ needs exactly one
pair per predecessor. So `%8` is `i`, and `%17 = %8 + 1` is `i + 1`, ready for the next trip. In
the same way `%9` is the sum coming into a trip and `%16` the sum going out. Running it with $n =
3$, $x = (1, 2, 3)$ and $y = (4, 5, 6)$:

| trip | `%8` ($i$) | `%9` ($s$ in) | `%12` ($x_i$) | `%14` ($y_i$) | `%16` ($s$ out) | `%17` ($i+1$) |
| ---: | ---------: | ------------: | ------------: | ------------: | --------------: | ------------: |
|    1 |          0 |             0 |             1 |             4 |               4 |             1 |
|    2 |          1 |             4 |             2 |             5 |              14 |             2 |
|    3 |          2 |            14 |             3 |             6 |              32 |             3 |

After the third trip `%17 = 3` equals $n$, so the branch goes to `%5`, whose φ-node picks `%16 =
32` and returns it. Check: $1 \cdot 4 + 2 \cdot 5 + 3 \cdot 6 = 32$. The φ in `%5` also has an
entry for arriving straight from `%3`, when $n \le 0$ and the loop never runs: then the result is
`0.0`.

SSA comes with one rule that the IR verifier enforces: a definition must **dominate** every use.
Block $A$ dominates block $B$ if every path from the entry to $B$ passes through $A$; within one
block, the definition must come first. A φ is the exception that makes loops possible: its
operand `%17` only has to dominate the end of the predecessor block `%7`, not the φ itself.

### Intrinsics, flags and address spaces

Three more things in the `saxpy` IR are worth knowing, because the NVPTX backend leans on them.

**Intrinsics** are functions whose names start with `llvm.` and which the compiler understands
itself. `threadIdx.x` became a call to `@llvm.nvvm.read.ptx.sreg.tid.x`, which reads a PTX
**special register**. Its declaration carries `range(i32 0, 1024)`: a block has at most 1024
threads, and telling the optimizer so lets it prove facts like "this index can't overflow".
Target-independent intrinsics exist too, such as `@llvm.fma.f32`. An intrinsic's name encodes its
types when it is generic: `@llvm.fma.f32` and `@llvm.fma.v4f32` are the same intrinsic on `float`
and `<4 x float>`.

**Flags** on instructions grant extra freedom. `contract` on `fmul` and `fadd` allows the two to
be fused into one fused multiply-add, which rounds once instead of twice. Clang adds it because
CUDA compiles with `-ffp-contract=fast` by default. Without the flag LLVM must not fuse them,
since the result can differ in the last bit: compiled with `-ffp-contract=off`, the same line
becomes a separate `mul.rn.f32` and `add.rn.f32` in PTX.

**Address spaces** say which kind of memory a pointer points to. A plain `ptr` is in address
space 0, the **generic** space, which can point anywhere. NVPTX numbers the others like
this:<Sidenote>From `NVPTXAddrSpace.h` ([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/include/llvm/Support/NVPTXAddrSpace.h#L21-L31)).
Two newer ones, tensor (6) and shared memory across a cluster (7), are left out of the table.</Sidenote>

| Address space | Memory | Holds |
| ------------: | ------ | ----- |
| 0 | generic | any of the below; the hardware works out which |
| 1 | global | device memory, `cudaMalloc` buffers |
| 3 | shared | per-block scratchpad, `__shared__` |
| 4 | constant | `__constant__` data |
| 5 | local | per-thread stack |
| 101 | param | kernel parameters |

A load through a generic pointer has to check where the address falls; a load through a global
pointer doesn't. We'll see the backend turn `saxpy`'s generic pointers into global ones in the
[NVPTX section](#kernel-parameters-and-address-spaces).

## The optimizer

Clang's IR at `-O0` is simple-minded on purpose. Every parameter and local variable gets a stack
slot (an `alloca`), every write stores to the slot, and every read loads from it. That makes the
front end easy to write: it never has to build SSA form itself.<Sidenote>Clang marks `-O0`
functions `optnone`, which tells `opt` to leave them alone. The `-O0` listings here were made
with `-Xclang -disable-O0-optnone` so `opt -O2` could then be run on them.</Sidenote>

The optimizer is a sequence of **passes**. A **transform pass** rewrites the IR; an **analysis
pass** only computes facts (a dominator tree, alias information) for transforms to use. `opt -O2`
runs a fixed pipeline of them, and `-print-changed` shows the IR after each pass that changed
something:

```bash
opt -O2 -print-changed=quiet saxpy.O0.ll -S -o saxpy.opt.ll
```

On `saxpy` the pipeline makes 118 pass runs (83 different passes), and only seven of them change
anything. Step through them:

<CodeStages stages={optStages} tags={saxpyTags} step={0} title="saxpy through opt -O2, one changing pass at a time" />

| Pass | Instructions after | What it did |
| ---- | -----------------: | ----------- |
| (clang `-O0`) | 39 | five stack slots, a load before every use |
| SROA | 20 | deleted the slots and wired values directly: now true SSA |
| EarlyCSE | 17 | computed `sext i` and `&y[i]` once instead of three and two times |
| GlobalOpt | 17 | deleted the unused `blockIdx`, `blockDim` and `threadIdx` globals |
| InstCombine | 17 | rewrote GEPs to the canonical byte form, `[4 x i8]` |
| PostOrderFunctionAttrs (×2), TailCallElim | 17 | attributes and `tail` markers only |

**SROA** (scalar replacement of aggregates) does almost all the work. It sees that no stack
slot's address escapes, so each slot is just a variable in disguise, and it replaces every load
with the value last stored. This is the job textbooks call **mem2reg**, and it is how SSA form
gets built in practice: front ends emit memory, and the optimizer promotes it to registers.

You can run any pass on its own with `-passes=`, which is the best way to learn what one does.
Pass names are the lower-case ones in the table (`sroa`, `early-cse`, `instcombine`), and
several can be chained: `opt -passes='sroa,early-cse,instcombine' -S file.ll`. The
`nsw` and GEP examples above were made exactly that way.

The optimizer is mostly target-independent, but not target-blind. Passes ask the target
questions through **TargetTransformInfo** (TTI), such as "is this instruction cheap?" or "which
address space can this pointer be assumed to be in?". The second question comes back in the NVPTX
section.

## The backend

### The code generation pipeline

The backend, `llc`, turns optimized IR into machine code. It is a pipeline of passes too, but the
code changes form along the way:

1. **LLVM IR**, still: target-aware IR passes prepare the code for selection.
2. **SelectionDAG**: each basic block becomes a graph, which is legalized and matched against the
   target's instructions.
3. **Machine IR** (MIR) in SSA form: real target instructions on virtual registers.
4. **Machine IR** after SSA: φ-nodes removed and, on most targets, physical registers assigned.
5. **MC layer**: instructions as `MCInst`, printed as assembly text or encoded as bytes.

These are the passes `llc -O2` runs on `saxpy` for NVPTX, grouped by phase. Click a phase to list
its passes; the ones written for NVPTX are highlighted.

### Building the SelectionDAG

**Instruction selection** chooses target instructions for each IR operation. NVPTX does it with
the **SelectionDAG** (`SelectionDAGISel`), which works on one basic block at a time and represents
it as a directed acyclic graph.<Sidenote>LLVM has a second instruction selector, **GlobalISel**,
which works on whole functions. Several targets use it (AArch64 does at `-O0`); NVPTX uses only
the SelectionDAG.</Sidenote> Each node is one operation; each edge points from an operand to the
node that uses it.

Here is the DAG of `saxpy`'s `if` body, block `%11`, at four points during selection, drawn from
`llc -debug-only=isel` dumps. Operands are above their users, so data flows downward.

Things to notice in the first step, **Built**:

- **CopyFromReg** nodes bring in values computed in other blocks: `%2` is `i`, `%0` and `%1` are
  the pointers `x` and `y`, `%3` is `a`. One DAG covers one block, so anything from outside
  enters this way.
- Each node lists its results. `load` produces two: the `f32` value and a `ch`.
- The **chain** (`ch`, dashed) is an ordering edge, not data. The two loads and the store all hang
  off it, so the store can't move above the loads that read the same address. `TokenFactor`
  merges two chains into one.
- The GEP is gone. It became plain arithmetic: `sign_extend` $i$ to 64 bits, shift left by 2
  (times 4 bytes), and `add` to the base pointer.

### Combining and legalizing

Selection then alternates two kinds of rewrite.

The **DAG combiner** simplifies small patterns. In step 2, **Combined**, it made two changes, both
outlined. `fmul` + `fadd` became one `fma`, because both carry `contract`. And `sign_extend` +
`shl` became `NVPTXISD::MUL_WIDE_SIGNED`, a node of NVPTX's own: PTX has a `mul.wide.s32`
instruction that multiplies two 32-bit values into a 64-bit result, which is exactly "widen $i$,
then times 4". The target adds rewrites like this one through its `PerformDAGCombine` hook (here,
`TryMULWIDECombine` in
[`NVPTXISelLowering.cpp`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXISelLowering.cpp#L6444-L6511)).<Sidenote>By
default the fma is formed even earlier, by an IR pass, `NVPTXIRPeephole`, that runs just before
selection; that is the `llvm.fma` call in the "IR before isel" stage above. The DAG figure was made
with `-disable-nvptx-ir-peephole` to show the combiner doing the same job. The final PTX is
identical either way.</Sidenote>

**Legalization** makes the DAG use only types and operations the target supports. A target
declares its legal types by giving each a register class; NVPTX has 1-, 16-, 32- and
64-bit register classes ([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXISelLowering.cpp#L594-L605)).
For each operation and type, it then says whether it is **Legal**, should be **Promoted** to a
wider type, **Expanded** into other operations, or handled by **Custom** C++. In `saxpy`
everything is `i32`, `i64` or `f32`, all legal, so step 3 changes nothing.

For legalization to do something, the type must be missing. There are no 8-bit registers, so
here is an 8-bit add, `store (a + b)` with `a` and `b` of type `i8`:

<SelectionDag example="add8" step={0} title="An i8 add on NVPTX: promoted to i16" />

**Type legalization** promotes every `i8` to `i16`: the loads now extend to 16 bits, the add
happens in 16 bits, and the store truncates back to 8 (`trunc to i8` in its dump line; hover it).
**Operation legalization** then fixes an operation NVPTX can't do as written: the loads extend
with *any* upper bits, which the target turns into a zero-extending load. The PTX is `ld.param.b8`
into a 16-bit register, `add.s16`, and `st.global.b8`.

### Instruction selection

The last step, **Selected** (step 4 in both figures), replaces every generic node with a machine
node: an actual NVPTX instruction. `fma` became `FMA_F32rrr`, `add` became `ADD64rr`, `load`
became `LD_i32`. The selector does this by pattern matching: it walks the DAG from the root and,
at each node, tries patterns such as "an `fma` on three `f32` registers is `FMA_F32rrr`". Those
patterns are not hand-written C++. They are written in TableGen and compiled into a table, as the
[TableGen section](#patterns-and-the-generated-c) shows.

Selection also picks the cheapest of several matches. The `mul` and `add` that compute
`i = blockIdx.x * blockDim.x + threadIdx.x` (in the entry block, not drawn) match both "`mul`,
then `add`" and the single pattern `MAD_LO_S32rrr` for `add (mul a, b), c`. The bigger pattern
wins, so the PTX has one `mad.lo.s32`. [Later](#one-instruction-from-td-to-ptx) we follow exactly
this instruction from its TableGen definition to the PTX.

still in SSA form, on **virtual registers** (`%0`, `%1`, ...) that each belong to a **register
class** (`b1`, `b32`, `b64`). This is the whole function, from `llc -stop-after=finalize-isel`:

#### Reading Machine IR

A block header `bb.1 (%ir-block.13)` names the machine block and the IR block it came from.
`successors:` lists where it can go, each with a branch probability as a fraction of
`0x80000000`: `0x40000000` is 50%, so the entry block's two successors are equally likely. In
each instruction, `%13:b32` is a virtual register with its class, `killed` marks a register's last
use, and anything after `::` is a **memory operand**, the same description of the access the DAG
had.

The bare numbers are the instruction's other operands, and only its TableGen definition says what
they mean. Here is the load of `x[i]`, decoded with the operand list of `LD_i32` from
[`NVPTXInstrInfo.td`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXInstrInfo.td#L1940-L1953),

So the operands spell `ld` + `.global` + `.b` + `32`, and the AsmPrinter prints `ld.global.b32
%r7, [%rd6];`. Likewise `SETP_i32rr %2, %4, 5` has comparison mode 5, `GE` in NVPTX's `CmpMode`
enum, which becomes `setp.ge.s32`, and the last `0` of `FMA_F32rrr` is its `$ftz` flag: no
flush-to-zero.

Machine IR is where the late optimizations run: machine common-subexpression elimination,
loop-invariant code motion, sinking, and peephole rewrites. The dump is also a file format: `llc
-stop-after=<pass>` writes a `.mir` file (YAML around the body above, with a `registers:` table
listing each virtual register's class), and `llc -run-pass=<pass>` reads one back and runs a
single machine pass on it.

#### Register allocation, skipped

Then the function leaves SSA form. φ-nodes become copies, and on a CPU the **register allocator**
maps the unlimited virtual registers onto the few physical ones (16 general-purpose registers on
x86-64), **spilling** values to the stack when they don't fit. This is one of the most expensive
and most important phases of a CPU compiler.

NVPTX skips it. In
[`NVPTXTargetMachine.cpp`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXTargetMachine.cpp#L441-L443):

```cpp
FunctionPass *NVPTXPassConfig::createTargetRegisterAllocator(bool) {
  return nullptr; // No reg alloc
}
```

PTX has unlimited virtual registers, so LLVM keeps its own and prints them. Real allocation,
onto the GPU's register file of up to 255 registers per thread, happens later in ptxas, which is
why spills show up in SASS but never in PTX.<Sidenote>This is also why NVPTX's register file in
TableGen defines only five registers per class (`%r0` to `%r4` and so on;
[source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXRegisterInfo.td#L35-L41)):
they exist to satisfy the framework, and are never allocated to.</Sidenote>

### Emitting PTX

The final pass is the **AsmPrinter**. It turns each machine instruction into an `MCInst`, the
**MC layer**'s representation, and hands it to an `MCStreamer`. For CPU targets the streamer
either prints assembly or encodes bytes into an object file; NVPTX only ever prints text. The
`NVPTXAsmPrinter` also writes everything around the instructions: the `.entry` header, the
parameter list, and one declaration per register class, such as `.reg .b32 %r<10>;`, which
declares `%r0` to `%r9`.

## TableGen

### The language

A backend needs a lot of tables: every instruction with its operands, assembly syntax and
selection pattern; every register and register class; every processor and feature. Writing those
in C++ would be thousands of lines of near-repetition. LLVM writes them in **TableGen**
(`.td` files), a small language whose only job is to produce **records**: named bags of typed
fields.

TableGen doesn't run anything. `llvm-tblgen` parses the files, builds every record, and then
hands the records to a **backend**, a C++ program inside `llvm-tblgen` that writes one output
file. The most useful backend for learning is `--print-records`, which just prints every record
with all its fields resolved. All the toy examples below are real `.td` files run through it.

These are the types a field can have:

| Type | Values look like | Notes |
| ---- | ---------------- | ----- |
| `bit` | `true`, `false`, `1`, `0` | a single bit |
| `int` | `7`, `-3`, `0x1F`, `0b1010` | 64-bit integer |
| `bits<n>` | `0b1010`, `{ 1, 0, 1, 0 }` | $n$ bits; select with `Nibble{3}` or `Inst{8...7}` |
| `string` | `"add.s32"` | `#` pastes strings: `"add" # ".s32"` |
| `code` | `[{ return N->hasOneUse(); }]` | a string meant to be pasted into C++ |
| `list<T>` | `[16, 32, 64]` | a list of any one type |
| `dag` | `(add i32:$a, i32:$b)` | an operator applied to named arguments |
| a class | `F32RT`, `B32` | a reference to a record of that class |

A field set to `?` is **uninitialized**: it has no value yet. Comments are `//` and `/* */`, and
`include "file.td"` pulls in another file.

### Records and classes

A **class** is a template for records, with parameters and default fields. A **def** creates one
record from one or more classes. Step through a toy file and the records TableGen builds from it:

<CodeStages stages={tdClassStages} tags={tdClassTags} step={0} maxLines={26} title="Classes, defs and let: shapes.td" />

Four rules are at work here:

- **Template arguments** (`<string name, int sides>`) are only visible while the class body is
  being built. A field that wants to keep one has to copy it: `string Name = name;`.
- **Fields can be computed**: `bit IsPolygon = !gt(sides, 2);` is evaluated for each record.
- **`let` overrides** a field the class already has. `def Square : Shape<...> { let Area = 16; }`
  changes `Area`; `let` can't create a new field.
- **Several parents** are allowed, separated by commas, and their fields are combined in order.
  The comment after `def RedSquare {` lists them: `// Shape Coloured`.

NVPTX's registers are a real example. `NVPTXReg` inherits from LLVM's generic `Register` class
and sets one field, and a `foreach` loop defines 25 records, `P0` to `RQ4`:

```tablegen
class NVPTXReg<string n> : Register<n> {
  let Namespace = "NVPTX";
}

foreach i = 0...4 in {
  def P#i  : NVPTXReg<"%p"#i>;  // Predicate
  def RS#i : NVPTXReg<"%rs"#i>; // 16-bit
  def R#i  : NVPTXReg<"%r"#i>;  // 32-bit
  def RL#i : NVPTXReg<"%rd"#i>; // 64-bit
  def RQ#i : NVPTXReg<"%rq"#i>; // 128-bit
}
```

`0...4` is an inclusive range, and `#` pastes strings together, also in record names, so `R3`
gets the assembly name `%r3`.

### Bang operators and dags

Computed fields use **bang operators**, built-in functions whose names start with `!`. There are
several dozen; a handful do most of the work in real `.td` files. One more toy file, with the values
it resolves to:

<CodeStages stages={tdValueStages} tags={tdValueTags} step={0} maxLines={26} title="Values, bang operators and dags: values.td" />

| Operator | Does | In the example |
| -------- | ---- | -------------- |
| `!if(c, a, b)` | `a` if `c` is non-zero, else `b` | `"seven"` |
| `!eq`, `!ne`, `!lt`, `!gt`, `!ge` | compare | `!eq(Seven, 7)` = 1 |
| `!add`, `!mul`, `!and`, `!or`, `!not` | arithmetic and logic | |
| `!strconcat(a, b)`, `a # b` | paste strings | |
| `!foreach(x, list, expr)` | map over a list (or a dag) | `["b16", "b32", "b64"]` |
| `!filter(x, list, pred)` | keep elements where `pred` holds | `[32, 64]` |
| `!foldl(init, list, acc, x, expr)` | reduce a list | $16 + 32 + 64 = 112$ |
| `!size`, `!empty`, `!range(n)` | length, emptiness, the list $0 \ldots n-1$ | `!size(Widths)` = 3 |
| `!interleave(list, sep)` | join strings | `"b16, b32, b64"` |
| `!cast<T>(x)` | convert, or look a record up by its name | |
| `!con(d1, d2)` | concatenate two dags | `(ins B32:$a, B32:$c)` |
| `!getdagname(d, i)`, `!getdagarg<T>(d, i)` | a dag argument's `$name`, its value | `"a"` |

The **dag** type is what makes TableGen fit for compilers. A dag value is an operator followed by
arguments, each optionally named with `$`: `(ins B32:$a, i32imm:$b)` has operator `ins` and two
arguments, `B32` named `a` and `i32imm` named `b`. Operators and arguments are references to
records (that is why the toy file defines `ins`, `outs` and `B32` as empty records). Instruction
operand lists, selection patterns and output instructions are all dags, and the names tie them
together: `$a` in a pattern is the same operand as `$a` in the operand list and in the asm
string.

NVPTX uses these operators to build asm strings from operand lists. Its class
`BasicFlagsNVPTXInst`
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXInstrInfo.td#L253-L277))
takes just the opcode, such as `"add.s32"`, and appends the operands:

```tablegen
!strconcat(asmstr, " \t",
  !interleave(!foreach(i, !range(!size(outs_dag)), "$" # !getdagname(outs_dag, i)), "|"),
  ", ",
  !interleave(!foreach(i, !range(!size(ins_dag)),
      !if(!eq(!cast<string>(!getdagarg<DAGOperand>(ins_dag, i)), "ADDR"),
          "[$" # !getdagname(ins_dag, i) # "]",       // an address operand gets brackets
          "$" # !getdagname(ins_dag, i))), ", "),
  ";")
```

(slightly shortened: the real one also handles empty operand lists). For `(outs B32:$dst)` and
`(ins B32:$a, B32:$b)` this gives `"add.s32 \t$dst, $a, $b;"`, which is exactly the `AsmString`
of the record `ADD32rr`, so no instruction has to spell out its own operand syntax. The toy
file's `Asm` field does the same on a small scale.

### Describing a target

A backend is described by records of a few classes from LLVM's shared `.td` files:
`Register` and `RegisterClass` for registers, `Instruction` for instructions, `SDNode` and
`PatFrag` for DAG nodes and pattern pieces, `Pat` for extra patterns, and `Processor` and
`SubtargetFeature` for chips. The `Instruction` class
([`Target.td`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/include/llvm/Target/Target.td#L663))
has about 80 fields, but these are the ones you read most:

| Field | Type | Says |
| ----- | ---- | ---- |
| `OutOperandList` | `dag` | the results: `(outs B32:$dst)` |
| `InOperandList` | `dag` | the inputs: `(ins B32:$a, B32:$b)` |
| `AsmString` | `string` | how to print it; `$name` is replaced by that operand |
| `Pattern` | `list<dag>` | the SelectionDAG pattern it implements, if any |
| `Predicates` | `list<Predicate>` | conditions for using it, such as `hasSM<90>` |
| `mayLoad`, `mayStore`, `hasSideEffects` | `bit` | what it may do, for the optimizer |
| `isBranch`, `isTerminator`, `isCommutable` | `bit` | more properties |
| `AddedComplexity` | `int` | raises the pattern's priority |
| `Namespace` | `string` | the C++ namespace of its opcode: `NVPTX::ADD32rr` |

NVPTX layers its own classes on top. `NVPTXInst`
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXInstrFormats.td#L16))
sets the namespace and some flag bits; `BasicNVPTXInst` builds the asm string as above. And the
class `RegTyInfo` bundles everything about one value type, so a multiclass can take a single
argument for it:

```tablegen
class RegTyInfo<ValueType ty, NVPTXRegClass rc, string ptx_type, Operand imm, SDNode imm_node,
                bit supports_imm = 1> {
  ValueType Ty = ty;          // the DAG type, i32
  NVPTXRegClass RC = rc;      // its register class, B32
  Operand Imm = imm;          // its immediate operand, i32imm
  ...
  int Size = ty.Size;         // 32
  string PtxType = ptx_type;  // "b32"
}

def I32RT    : RegTyInfo<i32, B32, "b32",  i32imm, imm>;
def F32RT    : RegTyInfo<f32,  B32, "f32",  f32imm,  fpimm>;
```

With that, here is how one line defines every integer add. Follow the names:

```tablegen
multiclass I3Inst<string op_str, SDPatternOperator op_node, RegTyInfo t,
                  bit commutative, list<Predicate> requires = []> {
  def rr :
    BasicNVPTXInst<(outs t.RC:$dst), (ins t.RC:$a, t.RC:$b),
              op_str,
              [(set t.Ty:$dst, (op_node t.Ty:$a, t.Ty:$b))]>,
              Requires<requires>;
  def ri :
    BasicNVPTXInst<(outs t.RC:$dst), (ins t.RC:$a, t.Imm:$b),
              op_str,
              [(set t.Ty:$dst, (op_node t.Ty:$a, (t.Ty imm:$b)))]>,
              Requires<requires>;
  if !not(commutative) then
    def ir : ...   // immediate first; only needed if the order matters
}

multiclass I3<string op_str, SDPatternOperator op_node, bit commutative> {
  foreach t = [I16RT, I32RT, I64RT] in
    defm t.Size# : I3Inst<op_str # t.Size, op_node, t, commutative>;
}

defm ADD : I3<"add.s", add, commutative = true>;
```

`defm ADD` runs `I3`, whose `foreach` runs `I3Inst` three times, with name prefixes `16`, `32` and
`64` (`t.Size#` turns the number into a name piece). So the records are `ADD` + `32` + `rr` =
`ADD32rr`, with asm `"add.s" # 32` = `"add.s32"`, and `ADD32ri` with an immediate second operand.
There is no `ADD32ir`, because `add` is commutative and `ri` covers both orders; `SUB32ir` does
exist. Those are the opcodes in the Machine IR above: `ADD64rr`, `MUL_WIDEs32_ri`,
`FMA_F32rrr`.

Patterns refer to DAG nodes by records too. Generic ones like `add` and `fma` are defined in
`TargetSelectionDAG.td`; NVPTX adds its own, such as the wide multiply the combiner created:

```tablegen
def SDTMulWide : SDTypeProfile<1, 2, [SDTCisInt<0>, SDTCisInt<1>, SDTCisSameAs<1, 2>]>;
def smul_wide : SDNode<"NVPTXISD::MUL_WIDE_SIGNED", SDTMulWide, [SDNPCommutative]>;
```

`SDTypeProfile<1, 2, ...>` reads "one result, two operands; result 0 is an integer, operand 1 is
an integer, operands 1 and 2 have the same type". `SDNode` ties the record `smul_wide` to the C++
opcode `NVPTXISD::MUL_WIDE_SIGNED` and marks it commutative.

Not every pattern lives inside an instruction. A standalone **`Pat`** maps a DAG pattern to
existing instructions, and may reorder operands:

```tablegen
foreach vt = [v2f16, v2bf16, v2i16, v4i8] in {
def : Pat<(vt (select i1:$p, vt:$a, vt:$b)),
          (SELP_b32rr $a, $b, $p)>;
}
```

A `select` on any of four 32-bit vector types is just a 32-bit `selp`, with the condition moved
last. And some instructions have no pattern at all: `LD_i32` has `Pattern = []`, because choosing
a load's address space, width and ordering takes C++, in `NVPTXDAGToDAGISel::tryLoad`
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXISelDAGToDAG.cpp#L1111)).

### Patterns and the generated C++

The pattern is what connects TableGen to instruction selection. Here is the FMA multiclass, from
[`NVPTXInstrInfo.td`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXInstrInfo.td#L1278-L1315),
shortened to its first two variants:

```tablegen
multiclass FMA<RegTyInfo t, bit allow_ftz = true, list<Predicate> preds = []> {
  defvar flag_str = !if(allow_ftz, "$ftz", "");
  defvar flag_ops = !if(allow_ftz, (ins FTZFlag:$ftz), (ins));
  defvar op_str = "fma.rn" # flag_str # "." # t.PtxType;

  let Predicates = preds in {
    def rrr : BasicFlagsNVPTXInst<(outs t.RC:$dst), (ins t.RC:$a, t.RC:$b, t.RC:$c),
                        flag_ops, op_str,
                        [(set t.Ty:$dst, (fma t.Ty:$a, t.Ty:$b, t.Ty:$c))]>;

    if t.SupportsImm then {
      def rri : BasicFlagsNVPTXInst<(outs t.RC:$dst),
                          (ins t.RC:$a, t.RC:$b, t.Imm:$c),
                          flag_ops, op_str,
                          [(set t.Ty:$dst, (fma t.Ty:$a, t.Ty:$b, fpimm:$c))]>;
      // ... rir, rii, iir: the other register/immediate combinations
    }
  }
}

defm FMA_F32    : FMA<F32RT,    allow_ftz = true>;
defm FMA_F64    : FMA<F64RT,    allow_ftz = false>;
```

Three more pieces of syntax appear here. `defvar` names a value for use in the rest of the body
(it is not a field of the records). `if ... then { }` defines records only when the condition
holds. And `allow_ftz = true` in the `defm` line passes a template argument by name.

`defm FMA_F32` makes `FMA_F32rrr` (three registers), `FMA_F32rri` (third operand an immediate)
and so on. The suffix names the operand kinds, which is why the selected DAG showed
`FMA_F32rrr` and `MUL_WIDEs32_ri` (a register times the immediate 4). The pattern `(fma $a, $b,
$c)` is a DAG fragment; the selector matches it against the SelectionDAG. `(set t.Ty:$dst, ...)`
says the instruction's result `$dst` is the value of that fragment. `$ftz` is an extra operand
that selects the flush-to-zero variant, `fma.rn.ftz.f32`; `saxpy` gets the plain one.

#### One instruction from .td to PTX

To see all the pieces connect, follow `mad.lo.s32` from its definition to the line of PTX that
computes `saxpy`'s index. Step through the five stages:

<CodeStages stages={madStages} tags={madTags} step={0} maxLines={26} title="mad.lo.s32: source, record, matcher table, Machine IR, PTX" />

The pattern `(add (OneUse2<mul> $a, $b), $c)` uses a **PatFrag**, a reusable pattern piece with a
C++ check attached: `OneUse2<mul>` matches a `mul` only if nothing else uses its result. That
check is what keeps the multiply-add honest. If the product were needed elsewhere too, fusing it
into the add would compute it twice, so the pattern refuses. Compiling `m = a * b; return m + c;`
gives `mad.lo.s32`, while `m = a * b; return m + (m + c);` keeps a separate `mul.lo.s32`.

The predicate `hasOptEnabled` is a C++ condition on the compile settings, `TM.getOptLevel() != CodeGenOptLevel::None`. At `-O0` it is
false, and the same `a * b + c` compiles to `mul.lo.s32` followed by `add.s32`: the pattern exists
but is switched off. Both experiments were run with `llc` on small IR files.

In the matcher table, each entry carries its pattern as a comment: a `// Src:` line with the
pattern matched and its complexity, and a `// Dst:` line with the instruction produced. The table
is a byte code (`OPC_MoveChild0`, `OPC_CheckOpcode`, `OPC_RecordChild1`, ...) that
`SelectCodeCommon` interprets, trying the most complex patterns first. `mad.lo.s32`'s complexity
of 7 beats the 3 of a plain `add`, which is why the fused form wins.

the hand-written backend `#include`s. NVPTX runs six of them

You can drive a backend from your own records too. `-gen-searchable-tables` is a general-purpose

## The NVPTX backend

### PTX, a virtual ISA

Most backends emit the instructions a chip executes. NVPTX doesn't: it emits **PTX**, a virtual
instruction set that NVIDIA keeps stable across GPU generations. ptxas, or the CUDA driver at
load time, compiles PTX into SASS for the actual GPU. That split explains a lot of NVPTX's design:

- **Registers are virtual**, as above, so there is no register allocation in LLVM.
- **Scheduling for the real pipeline** happens in ptxas, which knows the exact hardware.
- **The output is text.** The header records what the code needs: `.version 7.8` (the PTX
  version), `.target sm_90` and `.address_size 64`.
- **The same PTX runs on newer GPUs**: the driver can compile PTX for an architecture that didn't
  exist when it was written.

### Kernel parameters and address spaces

A kernel is declared `.entry` (a device function would be `.func`), and its parameters live in
the **param** state space, readable only with `ld.param`. In the PTX of `saxpy`, the first
instructions load them:

```ptx
ld.param.b64 	%rd3, [saxpy_param_2];
cvta.to.global.u64 	%rd1, %rd3;
```

The second line is the address-space story from earlier. `x` arrived as a generic pointer;
`cvta.to.global` converts it to a global address, and from then on loads use `ld.global` instead
of a generic `ld`. Where does LLVM learn that `x` points to global memory? Not from the source.
The NVPTX target answers the optimizer's TTI question in
[`NVPTXTargetTransformInfo.cpp`](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXTargetTransformInfo.cpp#L602-L622):

```cpp
unsigned NVPTXTTIImpl::getAssumedAddrSpace(const Value *V) const {
  if (isa<AllocaInst>(V))
    return ADDRESS_SPACE_LOCAL;

  if (const Argument *Arg = dyn_cast<Argument>(V)) {
    if (isKernelFunction(*Arg->getParent())) {
      const NVPTXTargetMachine &TM =
          static_cast<const NVPTXTargetMachine &>(getTLI()->getTargetMachine());
      if (TM.getDrvInterface() == NVPTX::CUDA && !Arg->hasByValAttr())
        return ADDRESS_SPACE_GLOBAL;
  // ...
```

In CUDA, a pointer passed to a kernel can only point to global memory, because the host can't
hand out pointers to anything else. So the `InferAddressSpaces` pass, among `llc`'s IR passes,
adds `addrspacecast ptr %2 to ptr addrspace(1)` for both pointer arguments and rewrites the GEPs,
loads and store to use the global pointers. You can see the casts in the "IR before isel" stage of
the first figure.

Structs passed by value are trickier, since they sit in param space and the code may want to
take their address. The `NVPTXLowerArgs` pass handles those: it reads them in place when it can,
and copies them to local memory when the code writes to them
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXLowerArgs.cpp#L9-L41)).

### Special registers, intrinsics and NVVMReflect

CUDA's built-in variables map to PTX special registers through intrinsics, as the TableGen
section traced: `threadIdx.x` → `@llvm.nvvm.read.ptx.sreg.tid.x` → `INT_PTX_SREG_TID_x` →
`mov.u32 %r6, %tid.x;`. NVPTX defines over a thousand `llvm.nvvm.*` intrinsics this way, for
barriers, warp shuffles, atomics, asynchronous copies and tensor-core instructions. Clang exposes
most of them as builtins named `__nvvm_*`, and CUDA's headers build functions like
`__shfl_down_sync` on those builtins.

One more NVPTX pass is unusual. NVIDIA's math library, **libdevice**, ships as LLVM bitcode and
must behave differently depending on compiler options, such as whether denormal floats are
flushed to zero. It asks with `__nvvm_reflect("__CUDA_FTZ")`. The **NVVMReflect** pass replaces
each such call with a constant read from the module, here the flag `!{i32 4,
!"nvvm-reflect-ftz", i32 0}` that Clang put in `saxpy`'s module, and later passes delete the
branch not taken
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVVMReflect.cpp#L9-L18)).
It is conditional compilation, decided at link time instead of preprocessing time.

### Shared memory and barriers

`saxpy` only uses global memory. A kernel that cooperates within a block needs **shared memory**,
a scratchpad visible to every thread of the block, and **barriers** to order the threads' accesses
to it. The classic example is a block-level sum: 256 threads each load one element, then repeatedly
add the upper half of the array onto the lower half. Step through it from CUDA to PTX, and follow
the colours:

<CodeStages stages={reduceStages} tags={reduceTags} step={0} maxLines={30} title="A block sum: shared memory, barriers and launch bounds" />

Each CUDA feature becomes a specific piece of IR, and each piece a specific piece of PTX:

| CUDA | LLVM IR | PTX |
| ---- | ------- | --- |
| `__shared__ float buf[256]` | `@buf = internal addrspace(3) global [256 x float] undef` | `.shared .align 4 .b8 buf[1024]` |
| `buf[t]` | `ptr addrspace(3)` after InferAddressSpaces | `ld.shared.b32`, `st.shared.b32` |
| `__syncthreads()` | `call void @llvm.nvvm.barrier.cta.sync.aligned.all(i32 0)` | `bar.sync 0` |
| `__launch_bounds__(256)` | function attribute `"nvvm.maxntid"="256"` | `.maxntid 256` |
| `#pragma unroll 1` | `!llvm.loop` metadata with `llvm.loop.unroll.disable` | `.pragma "nounroll"` |

Three details are worth a closer look. First, C++ pointers are generic, so Clang's IR reaches
`buf` only through `addrspacecast (ptr addrspace(3) @buf to ptr)`; it is the backend's
`InferAddressSpaces` pass that strips the casts and lets the loads become `ld.shared`. Second,
the barrier intrinsic is declared `convergent` (attribute group `#1` in the IR), which forbids
the optimizer from moving it under a condition. Third, NVPTX **demotes** `buf` into the kernel:
the PTX declares it inside `block_sum`'s body, because it is an `internal` shared variable used by
only one function
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXAsmPrinter.cpp#L718-L730)).

Check the loop with numbers. The φ for `s` starts at 128 and `lshr` halves it, so the trips use
$s = 128, 64, \ldots, 1$: eight trips, after which $s = 0$ and the loop exits. In trip one, thread
5 adds `buf[133]` to `buf[5]`; the PTX computes that address as `buf + 4·5` plus `mul.wide.s32`
of $128 \cdot 4 = 512$ bytes.

### Warp shuffles and atomics

The 32 threads of a warp can exchange registers directly, without shared memory, using
**shuffles**. And threads anywhere on the GPU can update the same memory safely with **atomics**.
Here is a warp sum that uses both: five shuffles fold 32 values into lane 0, and lane 0 adds the
warp's total to a global counter.

<CodeStages stages={warpStages} tags={warpTags} step={0} maxLines={30} title="A warp sum: shuffles and an atomic add" />

The shuffle is a plain intrinsic, `@llvm.nvvm.shfl.sync.down.f32(i32 mask, float value, i32
offset, i32 clamp)`, and it becomes one `shfl.sync.down.b32` per call. Its arguments land in PTX
in a different order: value, offset, clamp, then the mask $-1$ (all 32 lanes, `0xffffffff`). The
`for` loop with `off /= 2` was fully unrolled, because its trip count, five, is known.<Sidenote>Clang
needs to know the PTX version to accept shuffle builtins, and without a CUDA installation it
can't find out; the listing was compiled with `-Xclang -target-feature -Xclang +ptx78`, the
version LLVM 23 targets for `sm_90` by default.</Sidenote>

The atomic is the surprise. `atomicrmw fadd` did not become one `atom.add.f32`: it became a load
followed by a loop of `atom.cas` (compare-and-swap) that retries until no other thread got in
between. The reason is in NVPTX's `shouldExpandAtomicRMWInIR`
([source](https://github.com/llvm/llvm-project/blob/85ac560262434c9ccfc0c183ec22d4138ed647fb/llvm/lib/Target/NVPTX/NVPTXISelLowering.cpp#L7467-L7500)):
PTX's `atom.add.f32` on global memory flushes denormal numbers to zero, while this function keeps
them, so using it would change results. The comment in the code puts it this way:

```cpp
  // Try to lower LLVM atomicrmw fadd to PTX atomic.add.  This is complicated
  // by the weird FTZ behavior PTX atom.add has:
  //   - atom.add.f32 on global memory flushes denormals
  //   - atom.add.f32 on shared memory does not flush denormals
  //   - atom.add.f16 and atomic.add.bf16 never flush denormals
```

Four hand-written atomics show the rule, and how the IR's ordering and scope reach PTX:

<CodeStages stages={atomicStages} tags={atomicTags} step={0} maxLines={30} title="Four atomicrmw instructions and the PTX they become" />

| IR | PTX |
| -- | --- |
| `fadd`, global, `syncscope("device")`, function keeps denormals | `ld` + `atom.relaxed.gpu.global.cas.b32` loop |
| the same, function has `denormal_fpenv(float: preservesign)` | `atom.relaxed.gpu.global.add.f32` |
| `fadd`, shared, `syncscope("block")` | `atom.relaxed.cta.shared.add.f32` |
| integer `add`, global, no syncscope | `atom.relaxed.sys.global.add.u32` |

`monotonic` became `.relaxed`, the scopes `"block"`, `"device"` and none became `.cta`, `.gpu` and
`.sys`. Compiling the CUDA kernel with `-fgpu-flush-denormals-to-zero` adds the
`denormal_fpenv(float: preservesign)` attribute to it, and its atomic then becomes a single
`atom.relaxed.sys.global.add.f32`. The flag also sets `nvvm-reflect-ftz` to 1 and turns every
`add.f32` into `add.ftz.f32`.<Sidenote>Real CUDA code calls `atomicAdd`. Under Clang, its
`float` version is `__fAtomicAdd` in Clang's `__clang_cuda_device_functions.h`, which calls the
same builtin used here, so it compiles the same way, at system scope. The PTX could not be run
here: macOS has no ptxas or GPU, so these kernels were compiled but not executed.</Sidenote>

### Writing NVPTX IR by hand

Nothing requires a front end. A file with the NVPTX triple, a `ptx_kernel` function and the right
address spaces is a complete GPU program, and `llc` compiles it like any other. This is how
compilers such as Triton use NVPTX, and the easiest way to see what one IR construct becomes:

<CodeStages stages={reluStages} tags={reluTags} step={0} maxLines={30} title="A hand-written kernel: vector loads, select and inline asm" />

- **No data layout**: `llc` fills in the target's default. Only `target triple` is needed.
- **Pointers already in `addrspace(1)`**: the PTX parameters are declared `.ptr .global`, and no
  `cvta.to.global` is needed, unlike `saxpy`.
- **Vector types**: a `load <4 x float>` with `align 16` becomes one 16-byte `ld.global.v4.b32`
  with four destination registers. Wider loads mean fewer instructions for the same bytes, which
  is what `float4` does in CUDA. The alignment is required: with `align 4` the backend has to
  split the access.
- **Compare and select**: `fcmp ogt` + `select` against zero is a ReLU, and the DAG combiner
  recognises it as a maximum, `max.f32 %r, %r, 0f00000000` (the PTX spelling of the float 0.0).
- **Inline asm**: `call i32 asm "mov.u32 $0, %laneid;", "=r"()` pastes PTX text into the output.
  The second string is the **constraint** list: `=r` means "output 0 is a 32-bit register", and
  `$0` in the template is replaced by the register LLVM picks, here `%r1`. CUDA's `asm("..." :
  "=r"(x))` produces exactly this.

The index check: thread 3 loads from `x + 3 · 16 = x + 48` bytes (`mul.wide.u32 %rd4, %r2, 16`),
which is `x[3]` when `x` is an array of `<4 x float>`.

### saxpy, line by line

Putting it together, here is the PTX of `saxpy` with the IR each line came from:

| PTX | From IR | Why it looks like this |
| --- | ------- | ---------------------- |
| `ld.param.b32 %r3, [saxpy_param_0]` | parameter `%0` (`n`) | kernel params live in param space |
| `ld.param.b64` + `cvta.to.global.u64` (×2) | parameters `x`, `y` | assumed global, so converted once |
| `mov.u32 %r4, %ctaid.x` (and `%ntid.x`, `%tid.x`) | `llvm.nvvm.read.ptx.sreg.*` | special registers, via `INT_PTX_SREG_*` |
| `mad.lo.s32 %r1, %r4, %r5, %r6` | `mul` + `add` | `MAD_LO_S32rrr` pattern covers both |
| `setp.ge.s32 %p1, %r1, %r3` + `@%p1 bra $L__BB0_2` | `icmp slt` + `br` | condition inverted: skip the body if $i \ge n$ |
| `ld.param.b32 %r2, [saxpy_param_1]` | parameter `%1` (`a`) | sunk into the only block that uses it |
| `mul.wide.s32 %rd5, %r1, 4` | `sext` + GEP scaling | DAG combine to `MUL_WIDE_SIGNED` |
| `add.s64` + `ld.global.b32` (×2) | GEP + `load` | global loads, thanks to the cast |
| `fma.rn.f32 %r9, %r2, %r7, %r8` | `fmul contract` + `fadd contract` | fused because of `contract` |
| `st.global.b32 [%rd7], %r9` | `store` | |

Check the index with numbers: in block 2 of 256 threads, thread 5 computes `mad.lo.s32` $= 2
\cdot 256 + 5 = 517$, and its loads read 4 bytes at byte offset `mul.wide.s32` $= 517 \cdot 4 =
2068$ from `x` and from `y`.<MarginNote>`setp.ge` has comparison mode 5 in Machine IR, `GE` in
NVPTX's `CmpMode` enum.</MarginNote> Note also that `%r9` holds a float: NVPTX uses one untyped
32-bit register class, `B32`, for both `i32` and `f32`, and the instruction (`fma.rn.f32`) says
how to treat the bits.

## Summary

- **LLVM IR** is a typed, SSA-form language of modules, functions and basic blocks. Names say
  what they are (`@` global, `%` local, `#` attributes, `!` metadata); every instruction names
  its types; flags (`nsw`, `contract`, `inbounds`) and attributes (`readonly`, `convergent`)
  give the optimizer facts it could not prove, and breaking a flag's promise produces poison.
- `getelementptr` only does address arithmetic, in units of a type, and φ-nodes merge values at
  control-flow joins. Hand-written IR runs with `lli`, and the verifier enforces that every
  definition dominates its uses.
- The **backend** builds a **SelectionDAG** per basic block, combines and legalizes it, and
  selects target instructions by pattern matching, then optimizes **Machine IR**, whose bare
  operands are decoded by the instruction's TableGen operand list.
- **TableGen** builds records from classes, multiclasses and `defm`, with bang operators and dag
  values; NVPTX's records describe each instruction's operands, asm string, pattern and
  predicates, and backends compile them into C++ such as the matcher table that turns `add (mul
  a, b), c` into `mad.lo.s32`.
- **NVPTX** emits PTX, a virtual ISA, so it skips register allocation. It infers address spaces
  (generic pointers into `ld.global` and `ld.shared`), maps CUDA built-ins, barriers and shuffles
  to intrinsics, and lowers atomics by their scope, ordering and floating-point mode.
