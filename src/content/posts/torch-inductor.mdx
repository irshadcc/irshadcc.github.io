## Background

In eager mode, PyTorch runs one kernel per operator. `torch.softmax(torch.relu(x @ w), -1) * 2`
launches a matrix multiply, then a ReLU kernel, a softmax kernel and a multiply kernel, and each
of the last three reads a full tensor from GPU memory and writes a full tensor back. The
arithmetic in those three is trivial, so their running time is almost entirely memory traffic.
The [dispatcher](/blog/pytorch-dispatcher/) picks a good kernel for every op, but it cannot merge
ops, because it only ever sees one at a time.

`torch.compile` sees the whole function at once. **TorchDynamo** captures the Python code as a
graph, **AOTAutograd** traces that graph down to ATen operators (and builds the backward graph
when training), and **TorchInductor**, the default backend, turns the ATen graph into new
kernels. On a GPU it writes [Triton](https://triton-lang.org) kernels; on a CPU it writes C++.
Inductor's main job is to **fuse** many small loops into one kernel, so that intermediate tensors
never reach memory.

This post follows one function through Inductor and opens up each step:

1. **Graph preparation**: decompositions and graph passes that shape the FX graph.
2. **The IR**: Inductor's define-by-run loop representation, buffers and layouts.
3. **Lowering**: turning each ATen op into IR, and deciding which results get a buffer.
4. **Scheduling**: dependencies, fusion and buffer reuse.
5. **Code generation**: the backend interface, the Triton kernel line by line, tiling,
   reductions, the C++ backend and the Python wrapper that calls everything.

Along the way each section shows the internal interfaces involved (the `ops` protocol, IR nodes,
`register_lowering`, scheduler nodes, `InductorChoices`, `BaseScheduling`, kernels and wrapper
lines) and, where Inductor offers one, the hook for plugging in your own code.

All the IR, logs and generated code below were produced by running torch 2.13.0, and every link
to Inductor's source points at the commit that build came from.<Sidenote>Version `2.13.0`, git
`cf30153c`. The installed Python files are byte-identical to the files at that commit on GitHub,
so the line numbers in the links match what ran.</Sidenote>

The code lives in `torch/_inductor`, and a handful of files hold most of what this post covers:

| File | Role |
| --- | --- |
| `compile_fx.py` | Entry point: runs the graph passes and drives everything below |
| `graph.py` | `GraphLowering`, the FX interpreter that lowers each node and then calls the scheduler |
| `lowering.py` | The table from ATen ops to the functions that build IR for them |
| `ir.py` | The IR classes: boxes, views, layouts, loops, buffers, extern kernels |
| `loop_body.py` | `LoopBody`, which traces an `inner_fn` into an FX graph that can be analyzed |
| `virtualized.py`, `ops_handler.py` | The `ops` and `V` globals, and the protocol every `ops` handler follows |
| `scheduler.py` | Dependencies, fusion, ordering, and dispatch to backends |
| `codegen/` | The Triton, C++ and other backends, and the wrapper generators |

## The running example

```python
import torch

def f(x, w):
    y = torch.relu(x @ w)
    return torch.softmax(y, dim=-1) * 2

x = torch.randn(8, 16)
w = torch.randn(16, 32)
out = torch.compile(f)(x, w)
```

The shapes are tiny on purpose: an $8 \times 32$ output keeps every printout short. The
interesting part is everything after the matmul: a ReLU, a softmax along each row of 32, and a
scale. Step through what Inductor does with it below. Each stage is explained in its own section
later, so for now just watch the eight rows turn into two kernels.

Three things to notice. In stage 3, relu, sub and div lose their buffers: they are **inlined**
into whatever uses them. In stages 5 and 6, the four remaining nodes after the matmul fuse into
one. And in stage 7 that fused node is a single Triton kernel, whose only memory traffic is
reading the matmul's output and writing the result.

### Where the graph comes from

You can print every intermediate artifact Inductor produces by setting
`TORCH_COMPILE_DEBUG=1`. For one compiled graph it writes a directory with these files:

| File | What it holds |
| --- | --- |
| `fx_graph_readable.py` | The ATen graph Inductor received |
| `fx_graph_transformed.py` | The same graph after Inductor's graph passes |
| `ir_pre_fusion.txt` | Scheduler nodes, their loop bodies and dependencies, before fusion |
| `ir_post_fusion.txt` | The same after fusion |
| `output_code.py` | The generated module: kernels plus the Python wrapper |

The first one, for our function, is this:

```python
def forward(self, arg0_1: "f32[8, 16]", arg1_1: "f32[16, 32]"):
    mm: "f32[8, 32]" = torch.ops.aten.mm.default(arg0_1, arg1_1)
    relu: "f32[8, 32]" = torch.ops.aten.relu.default(mm)
    amax: "f32[8, 1]" = torch.ops.aten.amax.default(relu, [-1], True)
    sub: "f32[8, 32]" = torch.ops.aten.sub.Tensor(relu, amax)
    exp: "f32[8, 32]" = torch.ops.aten.exp.default(sub)
    sum_1: "f32[8, 1]" = torch.ops.aten.sum.dim_IntList(exp, [-1], True)
    div: "f32[8, 32]" = torch.ops.aten.div.Tensor(exp, sum_1)
    mul: "f32[8, 32]" = torch.ops.aten.mul.Tensor(div, 2)
    return (mul,)
```

`x @ w` became `aten.mm`, and `torch.softmax` is gone: in its place are five simpler ops. That
is the first job of graph preparation.

## Preparing the graph

[`compile_fx`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/compile_fx.py#L2873)
is Inductor's entry point. Its docstring lists the steps:

```python
"""
(1) apply pre-grad passes
(2) create `fw_compiler` and `bw_compiler` functions out of `inner_compile`
(3) call aot_autograd, which:
- (3a) creates a joint graph with `decompositions`,
- (3b) partitions it with `partition_fn` into fw and bw graphs (applying joint-graph passes),
- (3c) calls `fw_compiler` and `bw_compiler` on those graphs (applying post-grad passes)
- (3d) finally, assembles the fw and bw compiled functions back together and returns.
"""
```

### Decompositions

Before decomposing, AOTAutograd **functionalizes** the program: in-place ops such as `add_`
become out-of-place ones, and views become explicit view ops, so almost all of the graph Inductor
receives is free of mutation. That is what lets Inductor treat every node as a value it can
inline, reorder or fuse.

A **decomposition** rewrites an ATen op as a small graph of simpler ATen ops. AOTAutograd applies
them while tracing, using the table from
[`select_decomp_table`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/decomposition.py#L972),
which in this build holds 1,098 entries. `aten._softmax` is one of them, and its decomposition is
three lines of Python
([`_decomp/decompositions.py`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_decomp/decompositions.py#L1295)):

```python
x_max = _softmax_unbacked_safe_amax(x, dim)
unnormalized = torch.exp(x - x_max)
result = unnormalized / torch.sum(unnormalized, dim, keepdim=True)
```

which is exactly the amax, sub, exp, sum and div in the graph. Decomposing looks like a step
backwards, since one kernel became five ops. It is a good trade for a fusing compiler for two
reasons. Inductor needs code for far fewer distinct ops: everything reduces to pointwise math,
reductions and a few special cases. And once the ops are small, the scheduler can fuse them with
their neighbours, here with the ReLU before and the multiply after, which a monolithic softmax
kernel never could.<Sidenote>Not every op is decomposed. `aten.relu` has its own lowering and no
entry in the table; `aten.mm` is kept whole because a hand-written GEMM beats anything assembled
from pointwise pieces.</Sidenote>

### Graph passes

Before and after AOTAutograd, Inductor rewrites the FX graph with passes. **Pre-grad passes**
run on the Torch-level graph Dynamo captured, **joint-graph passes** on the forward and backward
graph together, and
[**post-grad passes**](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/fx_passes/post_grad.py#L144)
on the final ATen graph. Most of them are written with a **pattern matcher**: a pattern is a
small FX graph, a replacement is another, and the pass swaps every match. They remove no-op
views and copies, fold constants, reorder nodes for locality, and replace known subgraphs with
better kernels. For our
function no pass fires: `fx_graph_transformed.py` is identical to the graph above.

#### Custom passes

You can add your own passes without editing Inductor. `torch._inductor.config` has one slot per
stage: `pre_grad_custom_pass`, `joint_custom_pre_pass`, `joint_custom_post_pass`,
`post_grad_custom_pre_pass` and `post_grad_custom_post_pass` (the post-grad pair run before and
after the built-in pattern matcher). A pass implements
[`CustomGraphPass`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/custom_graph_pass.py#L53):
`__call__` edits the `torch.fx.Graph` in place, and `uuid` returns a value that goes into the
compiled-graph cache key, so that changing the pass invalidates cached results. This one
rewrites `x * 2` as `x + x`:

```python
from torch._inductor.custom_graph_pass import CustomGraphPass, get_hash_for_files

class MulTwoToAdd(CustomGraphPass):
    def __call__(self, graph: torch.fx.Graph) -> None:
        aten = torch.ops.aten
        for node in list(graph.nodes):
            if node.target == aten.mul.Tensor and node.args[1] == 2:
                with graph.inserting_before(node):
                    add = graph.call_function(aten.add.Tensor, (node.args[0], node.args[0]))
                add.meta = dict(node.meta)      # keep the fake tensor in meta["val"]
                node.replace_all_uses_with(add)
                graph.erase_node(node)

    def uuid(self):
        return get_hash_for_files((__file__,))

with torch._inductor.config.patch(post_grad_custom_post_pass=MulTwoToAdd()):
    torch.compile(f)(x, w)
```

The graph the pass leaves behind ends in `add_tensor = aten.add.Tensor(div, div)`, and the last
two lines of the fused kernel change from a multiply by the constant `2.0` to
`tmp14 = tmp13 + tmp13`. Copying `meta` matters: lowering reads each node's shape and dtype from
`meta["val"]`.

## The IR

Inductor does not compile the FX graph directly. It first lowers it into its own **IR**
(intermediate representation), whose central idea is unusual, so it gets its own section.

### Define-by-run loop bodies

Most compilers represent a loop body as a tree of instruction objects. Inductor represents it as
a **Python function**. A pointwise op is an `inner_fn(index)` that computes one output element
by calling methods on a global object `ops`:

```python
def inner_fn(index):
    i0, i1 = index
    tmp0 = ops.load(buf0, i1 + 32 * i0)
    tmp1 = ops.relu(tmp0)
    tmp2 = ops.load(buf1, i0)
    tmp3 = tmp1 - tmp2
    tmp4 = ops.exp(tmp3)
    return tmp4
```

This is the IR for `exp` in our example, as Inductor prints it. `ops` is not a fixed library. It
is a **virtualized** handler: whoever calls `inner_fn` first installs their own implementation of
`ops`, and that decides what "running" the body means. The
[`virtualized.py`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/virtualized.py#L30)
docstring puts it this way:

> A commonly used IR in Inductor is define-by-run: instead of maintaining explicit syntax data
> structures, we instead represent loop bodies as callable functions, which internally invoke
> operations defined on `V.ops`. To perform semantic analysis, print or code generate these
> operations, we dynamically patch `V.ops` with an alternate handler with the intended semantics
> and then run the callable function.

Here is that idea run by hand. The script below intercepts the `exp` node during lowering and
calls its `inner_fn` twice: once with a handler that records each call as text, and once with a
handler that computes real numbers.

```python
class Printer:                       # every ops.* call becomes a line of text
    def __init__(self): self.n, self.lines = 0, []
    def __getattr__(self, name):
        def op(*args):
            v = f"t{self.n}"; self.n += 1
            self.lines.append(f"{v} = {name}({', '.join(map(str, args))})")
            return v
        return op

class Evaluator:                     # every ops.* call computes a float
    def __init__(self, bufs): self.bufs = bufs
    def load(self, name, index): return self.bufs[name].flatten()[int(index)].item()
    def relu(self, x): return max(x, 0.0)
    def sub(self, a, b): return a - b
    def exp(self, x): return math.exp(x)

p = Printer()
with V.set_ops_handler(p):
    pw.inner_fn([i0, i1])            # symbolic index: sympy symbols
with V.set_ops_handler(Evaluator({"buf0": buf0, "buf1": buf1})):
    v = pw.inner_fn([1, 0])          # a concrete index
```

```text
t0 = load(buf0, 32*i0 + i1)
t1 = relu(t0)
t2 = load(buf1, i0)
t3 = sub(t1, t2)
t4 = exp(t3)

at (1, 0): 5.388799722540896e-05     eager: 5.388799763750285e-05
```

The same function printed itself and computed element $(1, 0)$, matching eager to float32
precision. Check it by hand: $\text{buf0}(1, 0) = -0.0867$, so relu gives $0$; the row maximum
$\text{buf1}(1) = 9.8286$; and $e^{0 - 9.8286} = 5.39 \times 10^{-5}$.<Sidenote>The full script
wraps the calls in `patch.object(FlexibleLayout, "allow_indexing", True)`. Without it the first
`load` fails with `convert FlexibleLayout to FixedLayout first`, a guard explained in the layouts
section below.</Sidenote>

Inductor uses the same trick throughout. To find which buffers a node reads, it runs the body
with a handler that records every `load` and `store`
([`extract_read_writes`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/dependencies.py#L660)).
To analyze and simplify loops, it runs it with a tracer that builds an FX graph, a
[`LoopBody`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/loop_body.py#L94).
And to generate code, it runs it with a handler whose `ops.exp(x)` returns the string
`"libdevice.exp(x)"` (Triton) or `"x.exp()"` (vectorized C++). One representation, many
interpretations.

#### The `ops` protocol

What a handler must provide is written down in
[`OpsHandler[T]`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ops_handler.py#L64),
a class with 154 ops in this build. `T` is the handler's **domain**, the type every method
takes and returns: `str` for a printer, a `CSEVariable` for code generation, a `ValueRanges`
interval for bounds analysis. The docstring sets the rules: every op works on **one element** at
a time, and none of them promote types, because type promotion was already done during lowering.
The methods fall into a few groups:

| Group | Methods | Notes |
| --- | --- | --- |
| Memory | `load(name, index)`, `store(name, index, value, mode)` | `index` is a sympy expression; `mode` can ask for an atomic store |
| Reductions | `reduction(dtype, src_dtype, reduction_type, value)`, `store_reduction(name, index, value)` | `reduction_type` is one of 16 strings, such as `"sum"`, `"max"`, `"argmax"`, `"welford_reduce"` |
| Indexing | `index_expr(expr, dtype)`, `indirect_indexing(x, size, check)` | Turn an index into a value, or a loaded value into an index (for gather) |
| Control | `masked(mask, body, other)`, `where(cond, a, b)` | `masked` skips the loads in `body` where `mask` is false |
| Values | `constant(value, dtype)`, `to_dtype(x, dtype)` | |
| Math | `exp`, `relu`, `add`, `maximum`, `erf`, `bitwise_and`, ... | Pointwise ops with torch semantics |

Most handlers don't implement all 154 by hand. They subclass
[`DefaultHandler`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ops_handler.py#L786),
which routes every op to one method, `_default(name, args, kwargs)`, and override only the ops
that need special treatment. The `Printer` above, written that way:

```python
from torch._inductor.ops_handler import DefaultHandler

class Printer(DefaultHandler):
    def __init__(self): self.n, self.lines = 0, []
    def _default(self, name, args, kwargs):
        v = f"t{self.n}"; self.n += 1
        self.lines.append(f"{v} = {name}({', '.join(map(str, args))})")
        return v
```

Two more pieces make `inner_fn` read like ordinary Python. The global `ops` is an
[`OpsWrapper`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/virtualized.py#L329):
it forwards each call to the current handler and wraps the result in an
[`OpsValue`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/virtualized.py#L243),
whose `__sub__`, `__mul__` and friends call `ops.sub`, `ops.mul` and so on. That is why the IR
prints `tmp3 = tmp1 - tmp2` and not `ops.sub(tmp1, tmp2)`. And "the current handler" is a
[`Virtualized`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/virtualized.py#L112)
variable: a thread-local slot that `V.set_ops_handler(h)` fills and that the returned context
manager restores on exit, so handlers nest. `V` holds other such slots too, among them
`V.graph` (the `GraphLowering` being compiled), `V.kernel` (the kernel being generated) and
`V.choices` (the heuristics, below).

Here are the handlers Inductor itself installs, and what each one turns a loop body into:

| Handler | File | Running `inner_fn` under it gives |
| --- | --- | --- |
| `RecordLoadStore` | `dependencies.py` | The `MemoryDep`s the scheduler uses |
| `CaptureIndexing` | `loop_body.py` | A `LoopBody`: an FX graph of the ops, with every index pulled out as a named sympy expression |
| `OpCounterCSE` | `ops_handler.py` | Op counts, which the realize heuristic uses to spot large bodies |
| `ValueRangeAnalysis` | `bounds.py` | An interval for every value, which lets codegen drop some bounds checks |
| `SimplifyIndexing` | `sizevars.py` | The same calls, with indices simplified using the loop ranges |
| `CSEProxy` | `codegen/common.py` | Deduplicated kernel variables (see the backend section) |
| `TritonKernelOverrides`, `CppOverrides`, `CppVecOverrides`, `MetalOverrides`, `HalideOverrides` | `codegen/` | A line of source code in the backend's language |

### Nodes, buffers and layouts

The IR classes live in
[`ir.py`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py).
The ones that matter here:

| Class | Represents |
| --- | --- |
| `Pointwise` | `inner_fn(index)` over `ranges`: one value per output element |
| `Reduction` | `inner_fn(index, rindex)` over `ranges` and `reduction_ranges`, plus a `reduction_type` such as `"max"` or `"sum"` |
| `Scan`, `Sort` | The other two loop kinds, for `cumsum`-style scans and sorts along one dimension |
| `ComputedBuffer` | A `Pointwise` or `Reduction` that has been given memory: a name like `buf2` and a layout |
| `InputBuffer` | A graph input |
| `ExternKernel` | A call to an existing kernel (ATen, cuBLAS) instead of generated code |
| `PermuteView`, `ReinterpretView`, ... | Views: another node read through an index transformation |
| `TensorBox`, `StorageBox` | Mutable wrappers that let the IR under them be replaced |

A `Pointwise` is a promise, not a tensor: nothing is computed and no memory exists until
something **realizes** it. Every lowered value is wrapped as `TensorBox(StorageBox(node))`
([`TensorBox.create`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L9981)).
The `StorageBox` is the hook for realization: its
[`realize`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L10012)
method swaps the `Pointwise` it holds for a `ComputedBuffer` wrapping it, and registers the new
buffer with the graph:

```python
def realize(self) -> str | None:
    if IRNode.is_realized_node(self.data):
        return self.data.get_name()
    ...
    self.data = ComputedBuffer(
        name=None,
        layout=FlexibleLayout(device=device, dtype=self.data.get_dtype(),
                              size=self.data.get_size(), is_pinned=False),
        data=self.data,
    )
    self.data.name = V.graph.register_buffer(self.data)
    V.graph.register_operation(self.data)
    ...
```

Because the swap happens inside the box, every IR node that already holds this `StorageBox` now
sees a buffer, without being rebuilt.

Views add one more layer. The
[note at the top of `ir.py`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L168)
describes the two shapes a tensor can take:

> Tensors that directly own storage are represented as a chain of:
> TensorBox -> StorageBox -> Buffer
> ...
> Tensors backed by views add one more indirection to the IR.
> TensorBox -> View -> StorageBox -> Buffer
> In these cases, the underlying StorageBox/Buffer will be shared with the pre-view TensorBox.

Lowering `x.t() + (y + 1).t()` and printing the class chain of each result shows both forms, and
shows that the view's class depends on what it views:

| FX node | IR chain |
| --- | --- |
| `permute` (`x.t()`, `x` an input) | `TensorBox → ReinterpretView → StorageBox → InputBuffer` |
| `add` (`y + 1`) | `TensorBox → StorageBox → Pointwise` |
| `permute_1` (`(y + 1).t()`) | `TensorBox → PermuteView → StorageBox → Pointwise` |
| `add_1` (the output) | `TensorBox → StorageBox → ComputedBuffer → Pointwise` |

An input has a fixed layout, so its transpose can be a `ReinterpretView`: the same storage under
new strides. `y + 1` has no storage yet, so its transpose is a `PermuteView`, which only remaps
the index when something loads through it. The same note explains mutation: an in-place op on a
tensor swings its `StorageBox` to a new buffer, leaving the old one unchanged, which is how
mutation stays functional inside the IR.

#### Buffers and operations

A realized node plays two roles, and Inductor gives each its own base class. A **buffer** is
named memory with a layout: what other nodes read. An
[**operation**](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L909)
is the work that writes it: what the scheduler schedules. Most realized nodes are both. The class
hierarchy of `buf2` (our realized `exp`) is:

```text
ComputedBuffer → OperationBuffer → Buffer → IRNode
                                 ↘ Operation
```

So it has two names. As a buffer it is `buf2`; as an operation it is `op2`, the name the
scheduler logs use. After lowering, `V.graph.buffers` lists `buf0` to `buf4` and
`V.graph.operations` lists `op0` to `op4`. An extern kernel such as the matmul is also both, an
`ExternKernelOut` that is `op0` and `buf0`. Here is what the main
[`IRNode`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L559)
methods return for `buf2`, captured during compilation:

| Method | Returns for `buf2` |
| --- | --- |
| `get_name()` / `get_operation_name()` | `"buf2"` / `"op2"` |
| `get_size()`, `get_stride()` | `[8, 32]`, `[32, 1]` |
| `get_layout()` | `FixedLayout('cpu', torch.float32, size=[8, 32], stride=[32, 1])` |
| `get_dtype()`, `get_device()` | `torch.float32`, `cpu` |
| `data` | the `Pointwise` it wraps |
| `get_read_names()` | `{"buf0", "buf1"}` |
| `make_loader()` | a function `index → ops.load("buf2", 32*i0 + i1)` |
| `get_read_writes()` | reads `MemoryDep('buf0', 32*d0 + d1, {d0: 8, d1: 32})` and `MemoryDep('buf1', d0, {d0: 8})`; writes `buf2` at `32*d0 + d1` |

`get_read_writes` returns `MemoryDep`s, the access records the scheduling section explains, and
it comes from the define-by-run trick again. A `ComputedBuffer` has a
[**store function**](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L5342)
that computes one element and stores it into the buffer's layout:

```python
def get_store_function(self) -> Callable[..., None]:
    indexer = self.get_layout().as_fixed().make_indexer()
    if isinstance(self.data, (Reduction, Scan, Sort)):
        return partial(self.data.store_reduction, self.name, indexer)
    else:
        assert isinstance(self.data, Pointwise), type(self.data)
        return partial(self.data.store_output, self.name, indexer)
```

For a `Pointwise`, `store_output` is a single line, `ops.store(name, indexer(vars),
self.inner_fn(vars))`. Run `buf2`'s store function under the `Printer` handler from the define-by-run section and the whole contract of the node appears, ending in the store:

```text
t0 = load(buf0, 32*i0 + i1)
t1 = relu(t0)
t2 = load(buf1, i0)
t3 = sub(t1, t2)
t4 = exp(t3)
t5 = store(buf2, 32*i0 + i1, t4)
```

Run it under `RecordLoadStore` instead and the loads and the store become the `MemoryDep`s in
the table. A `Reduction`'s store function calls `ops.reduction(dtype, src_dtype, reduction_type,
inner_fn(index, rindex))` and then `ops.store_reduction`. Every later stage (dependency
analysis, fusion, code generation) starts from this store function.

#### Layouts

A **layout** gives a buffer its device, dtype, size and strides (see
[strided tensors](/blog/strided-tensors/) for how strides map an index to a memory offset). A
new buffer starts with a **`FlexibleLayout`**: its strides are only a proposal (contiguous by
default), and Inductor may still change them, for example to make an output match a consumer's
preferred order, or to pad rows. A **`FixedLayout`** is final. Inputs, outputs and anything an
external kernel touches have fixed layouts.

Indexing into a flexible layout is forbidden. If generated code computed `32*i0 + i1` from a
proposed stride that later changed, the code would be wrong, so
[`Layout.make_indexer`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L4527)
asserts `FlexibleLayout.allow_indexing`. Code that needs the offsets first freezes the layout
into a `FixedLayout`, which is the moment Inductor commits to strides.

#### Views are index expressions

A view never copies in Inductor: it only changes the index expression its readers compute. Take
`x.t() + y` with `x` of shape $32 \times 64$ (decomposed into `aten.permute`). Since `x` is an
input with a fixed layout, the
[`permute`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L1453)
lowering becomes a `ReinterpretView`: the same storage under a new layout, size `[64, 32]` with
stride `[1, 64]`. The add then lowers to:

```python
def inner_fn(index):
    i0, i1 = index
    tmp0 = ops.load(arg0_1, i0 + 64 * i1)    # x.t()[i0, i1] = x[i1, i0]
    tmp1 = ops.load(arg1_1, i1 + 32 * i0)    # y[i0, i1]
    tmp2 = tmp0 + tmp1
    return tmp2
```

The transpose is entirely inside `i0 + 64 * i1`. Scaled down to a $4 \times 8$ `x`, the view
looks like this: each cell shows the offset into `x`'s storage that the view reads. Look at row 0
of `xt`: it walks down column 0 of `x`, offsets 0, 8, 16, 24.

## Lowering

**Lowering** turns the FX graph into IR.
[`GraphLowering`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/graph.py#L362)
is a subclass of `torch.fx.Interpreter`: it runs the graph node by node, but instead of
computing tensors, each node produces IR. `compile_fx` builds one and calls
`graph.run(*example_inputs)`
([source](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/compile_fx.py#L1523)).

### The lowering table

For each `call_function` node,
[`GraphLowering.call_function`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/graph.py#L1361)
looks the ATen op up in a global dict,
[`lowerings`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L125),
and calls the function it finds with the IR of the node's inputs:

```python
if target not in lowerings:
    ...
    if base_name in FALLBACK_ALLOW_LIST:
        make_fallback(target, ...)
    elif config.implicit_fallbacks:
        ...
        make_fallback(target, layout_constraint=decided_constraint, ...)
...
out = lowerings[target](*args, **kwargs)
```

That is the shape of it; the real method does a few more things, in this order. If the op has no
lowering, it creates a fallback, choosing a **layout constraint** from the op's tags (for example
that inputs must be contiguous, or must have the strides eager would give them). Then it applies
the op's layout constraint, if any, to the IR arguments, which can force a realize or a copy. If
the FX node asks to run in eager mode (`should_fallback`, or `fallback_to_eager` in its custom
metadata), it calls the eager kernel. Otherwise it tries `user_lowerings` first and the built-in
`lowerings` table second.

In this build `lowerings` has 1,345 `OpOverload` keys. An op with no lowering gets a
**fallback**: an `ExternKernel` that calls the eager ATen kernel at run time. Fallbacks are
correct but opaque, since nothing can fuse into or out of them; 357 ops are registered as
fallbacks on purpose.

Our eight nodes are lowered by these functions:

| FX node | Lowering | IR produced |
| --- | --- | --- |
| `mm` | `tuned_mm` (`kernel/mm.py`) | `ExternKernelOut` calling `extern_kernels.mm` |
| `relu`, `sub`, `exp` | `register_pointwise` → `make_pointwise` | `Pointwise` |
| `amax` | `make_reduction("max")` | `Reduction` |
| `sum_1` | `sum_` → `make_reduction("sum")` | `Reduction` |
| `div`, `mul` | `div`, `mul` → `make_pointwise` | `Pointwise` |

#### Pointwise lowerings

Most pointwise ops are one line each, for example
[`relu = register_pointwise(aten.relu)`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L7972).
`register_pointwise` wraps `ops.relu` with
[`make_pointwise`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L707),
which builds the closure that becomes `inner_fn`. Stripped of dtype handling, it is:

```python
def inner(*inputs):
    loaders = [x.make_loader() for x in inputs]
    ranges = inputs[0].get_size()

    def inner_fn(index):
        return fn(*[load(index) for load in loaders])   # fn = ops.relu

    return Pointwise.create(device=device, dtype=dtype, inner_fn=inner_fn, ranges=ranges)
```

The key line is `x.make_loader()`. For a realized buffer, the loader is `ops.load(name,
indexer(index))`. For an unrealized `Pointwise`, the loader **is that node's own `inner_fn`**.
So when `sub` is lowered on top of an unrealized `relu`, sub's `inner_fn` calls relu's
`inner_fn`, and relu's body ends up inside sub's. That is how inlining works: it is not a pass,
just function composition. It is also why `register_lowering` handles broadcasting and type
promotion before the lowering runs: by the time `inner_fn` is built, all inputs have the same
rank.

#### Reductions

[`make_reduction`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L6971)
builds a `Reduction` whose `inner_fn(index, rindex)` takes a second index over the reduced
dimension. For `amax` over a row of 32, `ranges=[8, 1]` and `reduction_ranges=[32]`:

```python
def inner_fn(index, rindex):
    i0, _ = index
    r0_0 = rindex
    tmp0 = ops.load(buf0, r0_0 + 32 * i0)
    tmp1 = ops.relu(tmp0)          # relu, inlined
    return tmp1
```

The body says what to reduce, and `reduction_type="max"` says how. Unlike pointwise nodes, a
reduction is always realized right away, unless it is small enough to unroll into pointwise
code:

```python
result = Reduction.create(reduction_type=reduction_type, input_node=x, **kwargs)
if isinstance(result.data.data, Reduction):  # Only realize if reduction isn't unrolled
    result.realize()
```

The reason is the change of iteration space. `amax` turns $8 \times 32$ values into 8, and its
consumer `sub` runs over all 256 elements. If the reduction were inlined like a pointwise node,
each of the 256 elements would recompute the max of its whole row, 32 times more work than
needed. Realized, the max is computed once per row and read back, and the scheduler can still
fuse the two loops into one kernel, as it does here.

The reduced dimension does not have to be the last. For `x.sum(dim=1)` with `x` of shape
$4 \times 8 \times 16$, the kept dimensions become `ranges` and the reduced one becomes
`reduction_ranges`:

```python
# ranges=[4, 16], reduction_ranges=[8], reduction_type=sum
def inner_fn(index, rindex):
    i0, i1 = index
    r0_0 = rindex
    tmp0 = ops.load(arg0_1, i1 + 16 * r0_0 + 128 * i0)    # x[i0, r0_0, i1]
    return tmp0
```

With strides $(128, 16, 1)$, the load reads $x(i_0, r_0, i_1)$; check one entry: output
$(1, 3)$ sums offsets $3 + 16 r_0 + 128$ for $r_0 = 0, \dots, 7$, that is 131, 147, ..., 243. In
the Triton kernel the two kept dimensions are flattened into one `x` index of 64 and split back
with `x0 = xindex % 16` and `x1 = xindex // 16`, and the load becomes
`in_ptr0 + (x0 + 16*r0_2 + 128*x1)`. Consecutive reduction steps are 16 elements apart in memory,
unlike the contiguous rows of the softmax example.

#### Writing a lowering

Almost every entry in `lowerings` is added by the
[`register_lowering`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L532)
decorator:

```python
def register_lowering(
    aten_fn,                    # an OpOverload, an OpOverloadPacket, or a list of them
    broadcast=False,            # broadcast tensor inputs to a common shape first
    type_promotion_kind=ELEMENTWISE_TYPE_PROMOTION_KIND.DEFAULT,  # None: no promotion
    convert_input_to_bool=False,
    lowering_dict=lowerings,
)
```

The function it decorates receives the inputs as IR nodes (`TensorBox`es), plus any plain Python
arguments, and must return IR. The wrapper
[`_register_lowering`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/lowering.py#L479)
puts around it first broadcasts and promotes the inputs as requested (`transform_args`), and
afterwards checks that the result is valid IR (`validate_ir`). An overload packet registers every
overload at once.

The same decorator works for your own ops, which is the most useful way to see the interface at
work. Take a custom op that eager PyTorch knows but Inductor doesn't:

```python
@torch.library.custom_op("blog::scaled_relu", mutates_args=())
def scaled_relu(x: torch.Tensor, alpha: float) -> torch.Tensor:
    return torch.relu(x) * alpha

@scaled_relu.register_fake          # shape and dtype, so tracing can run
def _(x, alpha):
    return torch.empty_like(x)

def g(x):
    return torch.ops.blog.scaled_relu(x, 2.0) + 1
```

Compiled as is, for an $8 \times 32$ `x`, the op has no lowering and becomes a fallback. The
wrapper calls the eager op, then a Triton kernel adds 1 in place:

```python
buf0 = torch.ops.blog.scaled_relu.default(arg0_1, 2.0)
...
triton_poi_fused_add_0.run(buf2, 256, stream=raw_streamNone)   # tmp2 = tmp0 + 1.0
```

Now give it a lowering. It builds a `Pointwise` from the input's loader, just as `make_pointwise`
does:

```python
from torch._inductor.ir import Pointwise
from torch._inductor.lowering import register_lowering
from torch._inductor.virtualized import ops

@register_lowering(torch.ops.blog.scaled_relu.default)
def lower_scaled_relu(x, alpha):
    load = x.make_loader()

    def inner_fn(index):
        return ops.relu(load(index)) * ops.constant(alpha, x.get_dtype())

    return Pointwise.create(device=x.get_device(), dtype=x.get_dtype(),
                            inner_fn=inner_fn, ranges=x.get_size())
```

Compiled again, the op is inlined into the add and both run in one kernel:

```python
@triton.jit
def triton_poi_fused_add_scaled_relu_0(in_ptr0, out_ptr0, xnumel, XBLOCK : tl.constexpr):
    xnumel = 256
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    xmask = xindex < xnumel
    x0 = xindex
    tmp0 = tl.load(in_ptr0 + (x0), xmask)
    tmp1 = tl.full([1], 0, tl.int32)
    tmp2 = triton_helpers.maximum(tmp1, tmp0)       # relu
    tmp3 = tl.full([1], 2.0, tl.float32)
    tmp4 = tmp2 * tmp3                              # * alpha
    tmp5 = tl.full([1], 1.0, tl.float32)
    tmp6 = tmp4 + tmp5                              # + 1
    tl.store(out_ptr0 + (x0), tmp6, xmask)
```

Memory traffic halves, from 4,096 bytes (the fallback reads and writes `x`, then the add reads
and writes it again) to 2,048. `alpha` reached the lowering as a plain float and was baked into
the kernel as a constant.<Sidenote>`register_lowering` writes to Inductor's global table, so the
lowering above applies to every later compilation in the process. There is also a second table,
`user_lowerings`, that `GraphLowering.call_function` checks first; in this build it is filled by
`register_custom_op_autotuning` in `kernel/custom_op.py`, which lets Inductor benchmark several
implementations of a custom op.</Sidenote>

### Realize or inline

Inlining saves memory traffic but can repeat work: if two users inline the same node, its body
runs twice. After each node is lowered,
[`GraphLowering.run_node`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/graph.py#L2030)
decides whether to realize it, mainly through
[`StorageBox.should_realize_on_reuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L10093):

```python
def should_realize_on_reuse(self, users: int, *, graph_reuse: bool = True) -> bool:
    if users > 1 and isinstance(self.data, (Pointwise, Reduction)):
        if is_cpu(self.data):
            # Heuristic for realizing reused result of heavy ops on cpu
            opcount = self.data.inner_fn_opcount()
            heavy_ops = ["exp", "log", "log10", "log1p", "log2", "sigmoid", "tanh"]
            if any(x in opcount.used_ops for x in heavy_ops):
                return True
        if self.has_large_inner_fn():
            return True
        return graph_reuse and self.num_reads() > config.realize_reads_threshold
    return False
```

A node with one user is never realized for reuse; there is nothing to share. A node with several
users is realized if it is expensive to recompute, or if it reads more than
`realize_reads_threshold = 4` buffers. A few other rules realize nodes too: graph outputs get the
strides eager would give them, inputs to ops that need a fixed layout (like `mm`) are realized,
a pointwise node that has accumulated too many reads or too big a body is realized to keep
`inner_fn` from growing without bound, and inputs coming from a different CUDA stream are
realized
([`_realize_inputs_at_stream_boundaries`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/graph.py#L1805)),
since a node inlined across streams could no longer be split into kernels on separate streams. Applied to our graph:

| Node | Users | Decision |
| --- | ---: | --- |
| `mm` | 1 | Extern kernels always own a buffer: `buf0` |
| `relu` | 2 | 1 read, no heavy op: **inlined** into `amax` and `sub` |
| `amax` | 1 | Reduction: `buf1` |
| `sub` | 1 | **inlined** into `exp` |
| `exp` | 2 | Body calls `exp`, and the device is a CPU: `buf2` |
| `sum_1` | 1 | Reduction: `buf3` |
| `div` | 1 | **inlined** into `mul` |
| `mul` | 1 | Graph output, strides fixed to match eager: `buf4` |

Stage 3 of the figure shows the result; click `exp` to see its body, which now starts from a
`load` of `buf0`. The heavy-op rule only applies on CPU.<Sidenote>On a GPU device, `exp` (2
reads) would stay inlined and be recomputed by both of its users. I checked what that changes by
patching `ir.is_cpu` to return `False`: the fused Triton kernel for this example comes out

### Extern kernels

`aten.mm` lowers through
[`tuned_mm`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/kernel/mm.py#L314).
It collects candidate implementations ("choices") for the GEMM and lets
`autotune_select_algorithm` pick one. Without max-autotune, the only choice is ATen's `mm`, so
the result is an `ExternKernelOut` that calls `extern_kernels.mm(x, w, out=buf0)` (cuBLAS on a
GPU). With `mode="max-autotune"`, Inductor adds Triton GEMM templates (and CUTLASS or C++ ones
where enabled), benchmarks them all on the real shapes, and keeps the fastest. A winning
template is a `TritonTemplateBuffer`, and unlike an extern kernel it can absorb pointwise
**epilogues**: the relu after the matmul could then run inside the GEMM
kernel.<Sidenote>I did not run max-autotune for this post: it benchmarks GEMM kernels on a GPU,
and the machine I used has none. The description follows `tuned_mm` and
`Scheduler.can_fuse`, which only lets an extern node fuse when it is a template or a
user-defined Triton kernel that allows epilogues.</Sidenote>

## Scheduling

After lowering, `GraphLowering.codegen` builds a
[`Scheduler`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L4038)
from the list of operations (realized buffers and extern kernels) and asks it to generate code.
The scheduler decides **which operations share a kernel** and **in what order** kernels run.

### Nodes and dependencies

Each operation becomes a **scheduler node**: `SchedulerNode` for generated loops,
`ExternKernelSchedulerNode` for extern calls. Its dependencies come from the define-by-run trick:
running the loop body with a handler that records loads and stores. A **`MemoryDep`** records a
buffer, the index expression used, and the loop ranges; a **`StarDep`** means "the whole buffer,
in an unknown pattern", which is all Inductor knows about an extern kernel. From
`ir_pre_fusion.txt`:

```text
op0: ExternKernelSchedulerNode(ExternKernelOut)
op0.writes = [StarDep(name='buf0', mode=None)]
op0.met_dependencies = [StarDep(name='arg0_1', mode=None), StarDep(name='arg1_1', mode=None)]

op2: SchedulerNode(ComputedBuffer)
op2.writes = [MemoryDep('buf2', c0, {c0: 256})]
op2.unmet_dependencies = [MemoryDep('buf0', c0, {c0: 256}), MemoryDep('buf1', c0, {c0: 8})]
op2.group.iteration = ((8, 32), ())
```

`MemoryDep('buf0', c0, {c0: 256})` reads: "op2 reads `buf0` at index `c0` for `c0` in
$[0, 256)$". The $8 \times 32$ loop was collapsed into one dimension of 256, because the two
dimensions are contiguous in memory. That normalization happens in
[`ComputedBuffer.simplify_and_reorder`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/ir.py#L5430),
which removes size-1 dimensions, merges contiguous ones and orders loops by stride. It matters
because two nodes can only share a memory access if their dependencies compare equal.

"Unmet" dependencies are buffers produced by other nodes in this graph; "met" ones (graph
inputs) are available from the start. The scheduler topologically sorts nodes by unmet
dependencies, removes dead nodes, and logs the result as `ir_pre_fusion.txt`.

#### Scheduler node classes

Every scheduler node derives from
[`BaseSchedulerNode`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L1167),
which wraps one IR `Operation` and adds what scheduling needs:

| Field | Holds |
| --- | --- |
| `node` | The IR `Operation` (`None` for fused nodes, which hold a list of nodes instead) |
| `read_writes` | The `MemoryDep`s and `StarDep`s read and written |
| `unmet_dependencies` | The reads produced by other nodes in this graph |
| `ancestors` | Names of every operation this node depends on, directly or not; used for the cycle check |
| `group` | `(device, (numel, rnumel))`, the key for backend fusion rules |
| `outputs` | One [`SchedulerBuffer`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L1055) per output buffer, each with its list of `users` |
| `last_usage` | Buffers whose last read is in this node, which the wrapper may free after it |
| `min_order`, `max_order` | Positions in the original order, used by the proximity part of the fusion score |

The subclasses differ in what code they produce:

| Class | Becomes |
| --- | --- |
| `SchedulerNode` | One loop nest: a `ComputedBuffer`, or a template |
| `ExternKernelSchedulerNode` | One call to an existing kernel; never fused, except templates that accept epilogues |
| `NopKernelSchedulerNode` | Nothing: a node with no work, such as a buffer that only aliases another |
| `FusedSchedulerNode` | Several `SchedulerNode`s that become one kernel |
| `ForeachKernelSchedulerNode` | Independent nodes launched together as one **combo kernel** (for example the per-parameter updates of an optimizer) |

### Fusion

Inductor fuses in two separate places, and it helps to keep them apart. **Lowering-time
inlining** happens before any buffer exists: an unrealized node's `inner_fn` is called from its
consumer's, so relu, sub and div never get a buffer or a scheduler node. **Scheduler fusion**
happens after realization: nodes that did get buffers (`op1` to `op4`) are merged into one
kernel, and their intermediate buffers are removed afterwards. Inlining can repeat work (each user
recomputes the inlined body) but never adds memory traffic; scheduler fusion never repeats work
but only applies to nodes with compatible loops. This section is about the second.

[`Scheduler.fuse_nodes`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L4986)
runs up to ten rounds of
[`fuse_nodes_once`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L5978),
whose docstring names its two levers:

```python
"""
This relies on two key functions to control the logic:
    - self.can_fuse(): checks if a fusion is legal
    - self.score_fusion(): assigns priority to a given fusion
"""
```

Each round
[collects candidate pairs](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L6399)
among nodes that use a common buffer, keeps the legal ones, sorts them by score, and fuses
greedily, best first. A round ends when no pair is left, and fusion ends when a round changes
nothing.

#### Legality

[`Scheduler.can_fuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L7327)
checks rules that hold for every backend: same device, no extern kernel (unless it is a template
accepting an epilogue), and no **cycle**. Fusing two nodes is illegal if some third node needs the
first one's output and produces an input of the second, since the fused kernel would have to run
both before and after it.

Then the check splits in two. If the second node depends on the first, the fusion is
**vertical** (producer into consumer). Otherwise it is **horizontal**: two nodes that only share
reads, merged so the shared input is loaded once. Each kind asks three layers in turn, and all
three must agree:

```python
if node1.get_operation_names() & node2.ancestors:
    # node2 depends on node1 outputs
    if (
        self.can_fuse_vertical(node1, node2, ...)          # scheduler: correctness
        and V.choices.can_fuse_vertical(self, node1, node2, shared_data_score)  # heuristics
        and self.get_backend(device).can_fuse_vertical(node1, node2)            # backend
    ):
        return True
    ...
else:  # nodes don't depend on each other, but may have common reads
    return V.choices.can_fuse_horizontal(
        self, node1, node2, shared_data_score
    ) and self.get_backend(device).can_fuse_horizontal(node1, node2)
```

The middle layer, `V.choices`, is an `InductorChoices` object, Inductor's collection of
performance heuristics (its docstring: "We try to not put correctness requirements in this
file"). Before either branch,
[`InductorChoices.can_fuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/choices.py#L569)
has already rejected pairs that share no data, pairs that would put more than
`config.max_fusion_size = 64` nodes in one kernel, and pairs whose fusion would raise peak
memory. For Triton the backend rule is in
[`SIMDScheduling.can_fuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L1998)
(the class sets `can_fuse_vertical = can_fuse_horizontal = can_fuse`) and compares each node's
**group** `(numel, rnumel)`: the number of output elements and the length of the reduction loop
(1 for pointwise nodes).

- Two pointwise nodes fuse if their `numel` match.
- Two reductions fuse if both `numel` and `rnumel` match.
- A pointwise node and a reduction fuse if the pointwise `numel` equals `numel * rnumel` of the
  reduction: the pointwise loop can then be split to run inside the reduction loop.

Check the last rule on our graph: `op1` (amax) has group $(8, 32)$ and `op2` (exp) has
$(256, 1)$, and $256 = 8 \times 32$, so they may fuse.

#### Scoring

[`InductorChoices.score_fusion`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/choices.py#L671)
returns a `FusionScore` tuple. Its most important part is the **memory score**, from
[`score_fusion_memory`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L8099):
the bytes of the dependencies the two nodes have in common, which is roughly the memory traffic
fusion saves. Capturing the scores during compilation gives:

| Pair | Shared dependencies | `memory_score` | Fused |
| --- | --- | ---: | --- |
| `op1` + `op2` | `buf0` (256 × 4 B), `buf1` (8 × 4 B) | 1056 | first |
| `op3` + `op4` | `buf2` (256 × 4 B), `buf3` (8 × 4 B) | 1056 | second |
| `op2` + `op3` | `buf2` (256 × 4 B) | 1024 | third, as `op1_op2` + `op3_op4` |

Check the first row: `op1` and `op2` both read `buf0` through the same `MemoryDep`, $256 \times 4 =
1024$ bytes, and `op2` reads the `buf1` that `op1` writes, $8 \times 4 = 32$ bytes, total 1056.
Other parts of the score break ties: whether a template is involved, whether both nodes are the
same kind (pointwise or reduction), and how close the nodes are in the original
order.<Sidenote>`FusionScore.__lt__` compares the memory scores directly when they differ by
more than 16×. Otherwise it compares `(node_type_score, memory_score, buffer_overlap_score,
proximity_score)` as a tuple.</Sidenote>

`op2` + `op4` also share `buf2` but is not a candidate at all: the fusion log says `cannot fuse
op2 with op4: intermediate nodes between node1 & node2`, because `op3` (sum) needs `op2`'s
output and produces `op4`'s input. The whole run, from `TORCH_LOGS="fusion"`:

#### What fusion saves

The payoff is memory traffic. Here are the bytes read and written by everything after the matmul,
for float32, at the example's size and at a realistic $4096 \times 4096$, assuming each kernel
reads its inputs and writes its outputs once:

| Plan | Kernels | Bytes at 8 × 32 | MiB at 4096 × 4096 |
| --- | ---: | ---: | ---: |
| Decomposed graph, one kernel per op, no fusion | 7 | 12,416 | 768 |
| Eager: relu, softmax, mul | 3 | ≥ 6,144 | ≥ 384 |
| Inductor: one fused kernel | 1 | 2,048 | 128 |

The fused kernel reads the matmul output once and writes the result once: the minimum possible.
Decomposition alone would make things up to twice as bad as eager; decomposition plus fusion
makes them three times better.<Sidenote>Eager's softmax kernel reads its input at least once and writes its
output once; depending on the row length it may read the input more than once, hence the ≥. The
other numbers were computed by summing input and output sizes per kernel.</Sidenote>

#### Changing the heuristics

Because the heuristics live in one object, you can swap them out: subclass
[`InductorChoices`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/choices.py#L115),
override a method, and install the instance with `V.set_choices_handler`. Its other methods
cover the decisions seen earlier, such as `should_use_persistent_reduction`,
`reduction_split_factor` and `score_fusion`. To see how much the single kernel depends on
vertical fusion, here is a rule that never fuses a reduction into a pointwise consumer:

```python
from torch._inductor.choices import InductorChoices
from torch._inductor.virtualized import V

class NoEpilogueAfterReduction(InductorChoices):
    @staticmethod
    def can_fuse_vertical(scheduler, node1, node2, shared_data_score):
        return not (node1.is_reduction() and not node2.is_reduction())

with V.set_choices_handler(NoEpilogueAfterReduction()):
    torch.compile(f)(x, w)
```

The fusion rounds change. In round 1 the rule refuses `op1` + `op2` (amax into exp) and `op3` +
`op4` (sum into div), so the best remaining pair, `op2` + `op3` (exp into sum), fuses. In round 2
`op1` fuses with `op2_op3`: a fused node counts as a reduction if any node in it is one, so the
rule lets it through. `op4` stays alone, and the result is two kernels:

```python
triton_per_fused__softmax_relu_0.run(buf2, buf3, 8, 32, ...)   # amax, exp, sum: writes exp and the row sums
buf4 = buf2; del buf2  # reuse
triton_poi_fused__softmax_mul_1.run(buf4, buf3, 256, ...)      # reads them back, divides, scales
```

`exp(x - max)` now makes a round trip through memory, so traffic grows from 2,048 to 4,160 bytes
($1024 + 1056$ for the first kernel, $1056 + 1024$ for the second), and at $4096 \times 4096$
from 128 MiB to 256 MiB. For a cached, reusable setting, set `config.inductor_choices_class`
to a factory that returns your object; the class must then implement `uuid()`, which becomes part
of the cache key.

### Buffer planning

After fusion, some buffers no longer need memory. `buf1`, `buf2` and `buf3` are created and last
used inside the fused kernel, so
[`remove_kernel_local_buffers`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L2394)
deletes them: they live only in registers. And `buf4`, the output, has the same size as `buf0`,
which the kernel reads for the last time. With `config.inplace_buffers` on, the kernel takes a
single **in-out pointer** and overwrites `buf0` in place, and the wrapper renames the buffer
instead of allocating a new one:

```python
buf2 = buf0; del buf0  # reuse
buf4 = buf2; del buf2  # reuse
```

Freed buffers are also reused for later allocations of the same size. Together these keep peak
memory close to what eager would use, often lower.

## Code generation

Each scheduler node, fused or not, becomes one kernel. The scheduler hands each node to the
**backend** for its device:
[`TritonScheduling`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/triton.py#L7153)
for GPUs (on CUDA, by way of a `CUDACombinedScheduling` that delegates to it), `CppScheduling`
for CPUs by default. The backend creates a **kernel** object, installs it as the `ops` handler,
and runs every loop body in the node through it. Each `ops` call appends a line of code and
returns the name of a variable holding the result. The next section shows these interfaces in
detail; the sections after it look at the code they produce.

The Triton output below was captured by running the same function through Inductor's Triton
backend for CPU (`cpu_backend="triton"`).<Sidenote>Triton cannot be installed on the macOS

```python
    device_cpp_wrapper_codegen: WrapperConstructor | None = None,   # for cpp_wrapper=True

```

[`init_backend_registration`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L499)
registers the built-in backends, each only if nothing is registered for that device yet, so an
out-of-tree backend registered first takes precedence:

| Device | Scheduling class | Alternatives |
| --- | --- | --- |
| `cpu` | `CppScheduling` | `HalideScheduling`, `TritonScheduling`, `PallasScheduling`, chosen by `config.cpu_backend` |
| `cuda` | `CUDACombinedScheduling` | `HalideScheduling`, `PallasScheduling`, chosen by `config.cuda_backend` |
| `xpu` | `XPUCombinedScheduling` | |
| `mps` | `MetalScheduling` | |
| `mtia` | `TritonScheduling` | |
| `tpu` | `PallasScheduling` | |

`CUDACombinedScheduling` is a dispatcher, not a code generator. It sends ordinary nodes to a
`TritonScheduling` and GEMM templates to the CUTLASS, CuTe DSL or ROCm C++ backends, which is how
max-autotune can mix kernel languages in one graph. A device added through PyTorch's
`PrivateUse1` mechanism gets its classes from the device's own Python module.

#### `BaseScheduling`

A backend is a subclass of
[`BaseScheduling`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L9722).
The scheduler calls these methods:

| Method | Called for |
| --- | --- |
| `group_fn(sizes)` | Turning a node's loop sizes into its group. Triton multiplies them out into `(numel, rnumel)`; C++ keeps the size tuples |
| `can_fuse_vertical(n1, n2)`, `can_fuse_horizontal(n1, n2)` | The backend layer of the fusion check |
| `codegen_node(node)` | Writing and launching the kernel for a `SchedulerNode` or `FusedSchedulerNode` |
| `codegen_template(template, epilogue, prologue)` | Template kernels (GEMMs) with fused prologues and epilogues |
| `ready_to_flush()`, `flush()` | Writing out batched kernels. The C++ backend collects several nodes into one kernel group and emits it at a flush; Triton writes each kernel at once and its `flush` does nothing |
| `codegen_sync()` | A device synchronize after each kernel, for debugging (`config.triton.debug_sync_kernel`) |
| `benchmark_fused_nodes(nodes)` | Timing a candidate fusion, with `config.benchmark_fusion` on |

The scheduler's main loop,
[`Scheduler._codegen`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/scheduler.py#L9368),
walks the fused nodes in order and dispatches each one by kind (abridged):

```python
for node in nodes:
    ...
    if device != self.current_device or node.is_extern() or node.is_template():
        self.flush()
    ...
    if node.is_template():
        prologue, template_node, epilogue = node.get_prologue_template_epilogue(...)
        self.get_backend(device).codegen_template(template_node, epilogue, prologue)
    elif node.is_extern():
        self.codegen_extern_call(node)        # the scheduler writes extern calls itself
    elif node.is_foreach():
        backend.codegen_combo_kernel(node)
    elif isinstance(node, (FusedSchedulerNode, SchedulerNode)):
        self.get_backend(device).codegen_node(node)
    else:
        assert isinstance(node, NopKernelSchedulerNode)
        node.mark_run()
    self.available_buffer_names.update(node.get_buffer_names())
```

#### From `codegen_node` to a kernel

For Triton,
[`SIMDScheduling.codegen_node`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L2943)
unpacks the fused node into its `SchedulerNode`s and orders them into a **node schedule**, a
list of nodes with markers where the code leaves the reduction loop. Then
[`codegen_node_schedule`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L3036)
does four things: picks a tiling, creates the kernel object, runs every node's body inside it,
and turns the kernel into source:

```python
tiling, tiling_score = self.get_tiling_and_scores(node_schedule, numel, rnumel, ...)
kernels = self.create_kernel_choices(kernel_features, [tiling], {...})   # usually one TritonKernel
for kernel in kernels:
    self.codegen_node_schedule_with_kernel(node_schedule, kernel)
for kernel in kernels:
    src_code = kernel.codegen_kernel()                          # the @triton.jit text
    kernel_name = self.define_kernel(src_code, node_schedule, kernel)
...
self._launch_kernel_and_cleanup(final_kernel, ...)              # kernel.call_kernel(): a wrapper line
```

The middle step is where the loop bodies run. Its core, from
[`codegen_node_schedule_with_kernel`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L3150),
is:

```python
with kernel:
    for node in node_schedule:
        ...
        index_vars = kernel.split_and_set_ranges(node.get_ranges())
        node.codegen(index_vars)      # calls node._body(*index_vars) under SimplifyIndexing
```

`split_and_set_ranges` maps the node's loop sizes onto the kernel's dimensions, which is how
`buf2`'s `[8, 32]` loop becomes the index variables `x0` and `r0_1`.

#### Inside a kernel object

A [`Kernel`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L2160)
collects code in several `IndentedBuffer`s: `loads`, `compute` and `stores` in the base class,
and `TritonKernel` adds others such as `post_loop_store`, for code that runs after the
reduction. It also has `args`, a `KernelArgs` that maps buffer names to the kernel's parameters
(`buf0` to `in_out_ptr0`, for example), and `cse`, the cache of expressions already computed.
Entering the kernel with `with kernel:` installs the handlers:

```python
def __enter__(self) -> Self:
    super().__enter__()
    assert self.overrides
    self.exit_stack.enter_context(
        V.set_ops_handler(CSEProxy(self, self.overrides()))
    )
    self.exit_stack.enter_context(V.set_kernel_handler(self))
    return self
```

So while a loop body runs, an `ops.exp(...)` call passes through a chain of handlers. I recorded
the chain at the moment `exp` was generated for our kernel: the global `OpsWrapper`, then
`SimplifyIndexing` (installed by `node.codegen`), then
[`CSEProxy`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L2653),
then `TritonKernelOverrides`. `CSEProxy` does the bookkeeping. For a math op it computes value
bounds, asks `TritonKernelOverrides` for the expression text (`"libdevice.exp(tmp7)"`), works out
the result's dtype and shape, and hands the text to `kernel.cse.generate(kernel.compute, ...)`.
That method returns the existing variable if the same text was generated before, and otherwise
writes `tmp8 = libdevice.exp(tmp7)` to `compute` and returns a new `CSEVariable` named `tmp8`.
Loads, stores and reductions skip the overrides and go to the kernel's own `load`, `store` and
`reduction` methods. Before a load, `CSEProxy` checks a **store cache**: if this kernel already
stored the buffer, the load returns the stored variable instead of reading memory.

Three mechanisms keep the kernel small. The CSE cache makes `op2`'s load and relu free, since
`op1` already generated them. The store cache turns every read of `buf1`, `buf2` and `buf3`
into a register reference. And because each store is written as a
[`DeferredLine`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L1516),
a line that renders as nothing once its buffer is marked removed, `Kernel.__exit__` can delete
the stores to `buf1`, `buf2` and `buf3` after the fact. This is
`remove_kernel_local_buffers` from the buffer planning section, seen from inside the kernel.

### Triton kernels

First the fused kernel for our example, then three variations on it: 2D tiling, reductions too
long for one block, and how block sizes are chosen.

#### The fused kernel, line by line

The fused kernel, `triton_per_fused__softmax_mul_relu_0`. The name says it is a **persistent
reduction** (`per`) that fused `_softmax`, `mul` and `relu`.

```python
@triton.jit
def triton_per_fused__softmax_mul_relu_0(in_out_ptr0, xnumel, r0_numel, XBLOCK : tl.constexpr):
    xnumel = 8
    r0_numel = 32
    R0_BLOCK: tl.constexpr = 32
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:, None]
    xmask = xindex < xnumel
    r0_index = tl.arange(0, R0_BLOCK)[None, :]
    r0_1 = r0_index
    x0 = xindex
    tmp0 = tl.load(in_out_ptr0 + (r0_1 + 32*x0), xmask, eviction_policy='evict_first', other=0.0)
    tmp1 = tl.full([1, 1], 0, tl.int32)
    tmp2 = triton_helpers.maximum(tmp1, tmp0)                         # relu
    tmp3 = tl.broadcast_to(tmp2, [XBLOCK, R0_BLOCK])
    tmp5 = tl.where(xmask, tmp3, float("-inf"))
    tmp6 = triton_helpers.max2(tmp5, 1)[:, None].to(tl.float32)       # amax
    tmp7 = tmp2 - tmp6                                                # sub
    tmp8 = libdevice.exp(tmp7)                                        # exp
    tmp9 = tl.broadcast_to(tmp8, [XBLOCK, R0_BLOCK])
    tmp11 = tl.where(xmask, tmp9, 0)
    tmp12 = tl.sum(tmp11, 1)[:, None].to(tl.float32)                  # sum
    tmp13 = (tmp8 / tmp12)                                            # div
    tmp14 = tl.full([1, 1], 2.0, tl.float32)
    tmp15 = tmp13 * tmp14                                             # mul
    tl.store(in_out_ptr0 + (r0_1 + 32*x0), tmp15, xmask)
```

I removed a few unused aliases (`rnumel`, `RBLOCK`, `r0_offset`, `r0_mask`, `roffset`, `rindex`)
and added the comments; otherwise it is verbatim.

**The index space.** A Triton kernel is a **program** run once per block of the iteration
space; `tl.program_id(0)` says which block. Inductor names each dimension of the space with a
prefix: `x` for output elements (here the 8 rows), `r0_` for the reduction (the 32 columns).
These come from
[`IterationRangesRoot`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L164)
objects, one per dimension, that the SIMD kernel creates from the node's group. `xindex` is a
column vector of `XBLOCK` row numbers and `r0_index` a row vector of 32 column numbers, so
`r0_1 + 32*x0` broadcasts to an `XBLOCK` × 32 tile of offsets: the same `32*i0 + i1` as in the
IR, with the IR's index variables renamed to the kernel's.

**Masks.** `xmask = xindex < xnumel` switches off rows past the end, for when `XBLOCK` does not
divide `xnumel`. Every load and store takes the mask; masked-out loads return `other`.

**Persistent reduction.** Since a row has only 32 elements, the whole row fits in one block
(`R0_BLOCK = 32`, a constant): each program loads its rows once, reduces them in registers, and
reuses the loaded values for the pointwise math after the reduction. That is why the fused
kernel needs no intermediate buffers. Inductor makes this choice in
[`should_use_persistent_reduction`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/choices.py#L412):
for a reduction over the contiguous dimension (`ReductionHint.INNER`) the row may be up to 1024
elements, otherwise up to 64. `XBLOCK`, the number of rows per program, is left as a parameter
for the autotuner.

and which offsets of `in_out_ptr0` each one reads. Every program reads one contiguous run, the
best case for memory coalescing.

**From `ops` calls to lines.** Each line comes from a method of
[`TritonOverrides`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/triton.py#L1270),

```python
@staticmethod
def relu(x):
    ...
    return ops.maximum(ops.constant(0, torch.int32), x)

@staticmethod
@maybe_upcast_float32()
def exp(x):
    if config.use_fast_math:
        return f"tl_math.exp({x})"
    else:
        return f"libdevice.exp({x})"
```

`relu` is itself written in `ops`, which is where `tmp1 = tl.full([1, 1], 0, tl.int32)` and
`tmp2 = triton_helpers.maximum(tmp1, tmp0)` come from. Loads, stores and reductions are methods
of the kernel itself
([`TritonKernel.load`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/triton.py#L4139)
turns the sympy index into a pointer expression and a mask).

**Common subexpression elimination.** Every generated expression goes through a
[`CSE`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/common.py#L1973)
cache, keyed on the expression's text. Recall that relu was inlined into both `op1` (amax) and
`op2` (exp): the fused kernel runs both bodies, and both ask for `load(buf0, ...)` and then
`relu` of it. The second request hits the cache, so the load and the relu appear once, as `tmp0`
and `tmp2`. Inlining duplicates work in the IR; CSE removes the duplicates inside a kernel.

#### Tiling

The `x.t() + y` example from the views section needs a different kernel. One of its loads walks
memory along rows and the other along columns, so any 1D order makes one of them strided.
Inductor's
[`select_tiling`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/simd.py#L4324)
scores the loop dimensions by how much memory traffic is contiguous along each, and here picks a
2D tiling, `y` by `x`:

```python
@triton.jit
def triton_poi_fused_add_t_0(in_ptr0, in_ptr1, out_ptr0, ynumel, xnumel,
                             YBLOCK : tl.constexpr, XBLOCK : tl.constexpr):
    ynumel = 32
    xnumel = 64
    yoffset = tl.program_id(1) * YBLOCK
    yindex = yoffset + tl.arange(0, YBLOCK)[:, None]
    ymask = yindex < ynumel
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[None, :]
    xmask = xindex < xnumel
    x1 = xindex
    y0 = yindex
    tmp0 = tl.load(in_ptr0 + (x1 + 64*y0), xmask & ymask)
    tmp1 = tl.load(in_ptr1 + (y0 + 32*x1), xmask & ymask)
    tmp2 = tmp0 + tmp1
    tl.store(out_ptr0 + (x1 + 64*y0), tmp2, xmask & ymask)
```

`poi` marks a pointwise kernel. Each program now owns a `YBLOCK` × `XBLOCK` tile:
`in_ptr0` (`x`) is contiguous along `x1`, and `in_ptr1` (`y`) along `y0`. Inductor also chose the
output strides `(1, 64)`, the same order as `x`, so the store is contiguous too; eager
`x.t() + y` gives the same strides.

tiles, both loads read runs of 4 consecutive elements. The last row of tiles hangs over the edge,
and its masked lanes are dashed.

#### Looped reductions

When a row is too long to keep in registers, Inductor writes a **looped reduction** (`red`)
that walks the row in chunks of `R0_BLOCK`. Here is `torch.softmax(x, dim=-1)` for `x` of shape
$8 \times 8192$, with the realization heuristic set to behave as it would for a GPU (see the
sidenote in the realize section):

```python
@triton.jit
def triton_red_fused__softmax_0(in_ptr0, out_ptr2, xnumel, r0_numel,
                                XBLOCK : tl.constexpr, R0_BLOCK : tl.constexpr):
    ...
    _tmp2 = tl.full([XBLOCK, R0_BLOCK], float("-inf"), tl.float32)
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):          # pass 1: row max
        ...
        tmp0 = tl.load(in_ptr0 + (r0_1 + 8192*x0), r0_mask & xmask, eviction_policy='evict_last', other=0.0)
        tmp1 = tl.broadcast_to(tmp0, [XBLOCK, R0_BLOCK])
        tmp3 = triton_helpers.maximum(_tmp2, tmp1)
        _tmp2 = tl.where(r0_mask & xmask, tmp3, _tmp2)
    tmp2 = triton_helpers.max2(_tmp2, 1)[:, None]
    _tmp8 = tl.full([XBLOCK, R0_BLOCK], 0, tl.float32)
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):          # pass 2: sum of exp
        ...
        tmp4 = tl.load(in_ptr0 + (r0_1 + 8192*x0), r0_mask & xmask, eviction_policy='evict_last', other=0.0)
        tmp5 = tmp4 - tmp2
        tmp6 = libdevice.exp(tmp5)
        tmp7 = tl.broadcast_to(tmp6, [XBLOCK, R0_BLOCK])
        tmp9 = _tmp8 + tmp7
        _tmp8 = tl.where(r0_mask & xmask, tmp9, _tmp8)
    tmp8 = tl.sum(_tmp8, 1)[:, None]
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):          # pass 3: normalize
        ...
        tmp10 = tl.load(in_ptr0 + (r0_1 + 8192*x0), r0_mask & xmask, eviction_policy='evict_first', other=0.0)
        tmp11 = tmp10 - tmp2
        tmp12 = libdevice.exp(tmp11)
        tmp13 = (tmp12 / tmp8)
        tl.store(out_ptr2 + (r0_1 + 8192*x0), tmp13, r0_mask & xmask)
```

Three things differ from the persistent version. Each reduction keeps a **vector accumulator**
`_tmp2` of shape `XBLOCK` × `R0_BLOCK` and only collapses it to one value per row after the
loop. The input is read three times, once per pass. And the eviction hints tell the cache what
to keep: `evict_last` in the first two passes, because the row will be read again, and
`evict_first` in the last.

This is also where the realize-or-inline choice shows. With the GPU rule, `exp` is inlined and
pass 3 recomputes it. With the CPU rule (the actual setting for a CPU device), `exp` is realized:
pass 2 stores `exp(x - max)` to the output buffer and pass 3 reloads it and divides in place.
Recomputing an `exp` is cheap on a GPU next to an extra round trip to memory.<MarginNote>This
"read the row several times" structure is what [FlashAttention](/blog/flash-attention/)'s
online softmax avoids, by rescaling a running sum when the maximum changes.</MarginNote>

#### Autotuning

The decorator above each kernel, for example
`@triton_heuristics.persistent_reduction(size_hints={'x': 8, 'r0_': 32}, ...)`, is not Triton's.
It is Inductor's launcher, from
[`triton_heuristics.py`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/runtime/triton_heuristics.py#L3894).
From the size hints it builds a short list of `triton.Config`s (block sizes, `num_warps`), and on
the first call it benchmarks each one on the real inputs and caches the winner. For a 1D
pointwise kernel the default list has two configs; `mode="max-autotune"` widens the search. The
decorator also computes the launch grid, for example `ceil(xnumel / XBLOCK)` programs.

### The C++ backend

On a CPU, the default backend is C++, from
[`CppScheduling`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/cpp.py#L4862).
The same fused node becomes this kernel (lightly abridged: I dropped `static_cast<int64_t>`
around constants and the integer-division error check, and shortened two reduction helpers):

```cpp
extern "C" void kernel(const float* in_ptr0, float* out_ptr0, float* out_ptr1, float* out_ptr2)
{
    std::unique_ptr<float []> buf_local_buffer_data_0 = std::make_unique<float []>(32LL);
    float* local_buffer_data_0 = buf_local_buffer_data_0.get();
    for(int64_t x0=0; x0<8; x0+=1)                         // one row at a time
    {
        {   // amax: vectorized max of relu(row)
            float tmp_acc0 = -std::numeric_limits<float>::infinity();
            at::vec::Vectorized<float> tmp_acc0_vec = at::vec::Vectorized<float>(-std::numeric_limits<float>::infinity());
            for(int64_t x1=0; x1<32; x1+=4)
            {
                auto tmp0 = at::vec::Vectorized<float>::loadu(in_ptr0 + (x1 + 32LL*x0), 4);
                auto tmp1 = at::vec::clamp_min(tmp0, decltype(tmp0)(0));
                tmp_acc0_vec = at::vec::maximum(tmp_acc0_vec, tmp1);
            }
            tmp_acc0 = max_propagate_nan(tmp_acc0, vec_reduce_all(maximum, tmp_acc0_vec));
            out_ptr0[x0] = tmp_acc0;
        }
        {   // exp(relu(row) - max) into a 32-float local buffer, and its sum
            float tmp_acc0 = 0;
            at::vec::Vectorized<float> tmp_acc0_vec = at::vec::Vectorized<float>(0);
            for(int64_t x1=0; x1<32; x1+=4)
            {
                auto tmp0 = at::vec::Vectorized<float>::loadu(in_ptr0 + (x1 + 32LL*x0), 4);
                auto tmp2 = out_ptr0[x0];
                auto tmp1 = at::vec::clamp_min(tmp0, decltype(tmp0)(0));
                auto tmp3 = at::vec::Vectorized<float>(tmp2);
                auto tmp4 = tmp1 - tmp3;
                auto tmp5 = tmp4.exp();
                tmp5.store(local_buffer_data_0 + x1);
                tmp_acc0_vec = tmp_acc0_vec + tmp5;
            }
            tmp_acc0 = tmp_acc0 + vec_reduce_all(plus, tmp_acc0_vec);
            out_ptr1[x0] = tmp_acc0;
        }
        for(int64_t x1=0; x1<32; x1+=4)                     // divide and scale
        {
            auto tmp0 = at::vec::Vectorized<float>::loadu(local_buffer_data_0 + x1, 4);
            auto tmp1 = out_ptr1[x0];
            auto tmp2 = at::vec::Vectorized<float>(tmp1);
            auto tmp3 = tmp0 / tmp2;
            auto tmp4 = static_cast<float>(2.0);
            auto tmp5 = at::vec::Vectorized<float>(tmp4);
            auto tmp6 = tmp3 * tmp5;
            tmp6.store(out_ptr2 + (x1 + 32LL*x0));
        }
    }
}
```

The structure differs from Triton's. On CPU the scheduler made an
**`OuterLoopFusedSchedulerNode`** (see `ir_post_fusion.txt`): the four nodes share the outer loop
over rows `x0`, and each keeps its own inner loop over columns. The inner loops are vectorized
with ATen's `at::vec::Vectorized<float>`, which here is 4 floats wide (ARM NEON, 128-bit) and 8
or 16 on x86 with AVX2 or AVX-512; the backend is
[`CppVecKernel`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/cpp.py#L2720).
`buf2` (exp) was realized under the CPU rule, but only one row of it is alive at a time, so it
shrank to a 32-float **local buffer** instead of a $8 \times 32$ tensor. `buf1` and `buf3` (max
and sum) are still passed in as `out_ptr0` and `out_ptr1`. Unlike Triton, the C++ kernel
recomputes relu in the first two inner loops: they are separate loops, so CSE cannot share a value
between them.

### The wrapper

Kernels are half of the output. The other half is the **wrapper**: a Python function `call` that
allocates buffers and launches kernels in order, written by
[`PythonWrapperCodegen`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/wrapper.py#L1257).
For our example on the Triton backend:

```python
def call(self, args):
    arg0_1, arg1_1 = args
    args.clear()
    assert_size_stride(arg0_1, (8, 16), (16, 1), 'input')
    assert_size_stride(arg1_1, (16, 32), (32, 1), 'input')
    buf0 = empty_strided_cpu((8, 32), (32, 1), torch.float32)
    # Topologically Sorted Source Nodes: [matmul], Original ATen: [aten.mm]
    extern_kernels.mm(arg0_1, arg1_1, out=buf0)
    del arg0_1
    del arg1_1
    buf2 = buf0; del buf0  # reuse
    buf4 = buf2; del buf2  # reuse
    # Topologically Sorted Source Nodes: [y, softmax, mul], Original ATen: [aten.relu, aten._softmax, aten.mul]
    raw_streamNone = get_raw_stream(None)
    triton_per_fused__softmax_mul_relu_0.run(buf4, 8, 32, stream=raw_streamNone)
    return (buf4, )
```

Everything decided earlier is visible here. The inputs' sizes and strides are asserted, because
the kernels were specialized to them. `args.clear()` and `del` drop references as early as
possible so memory is freed. One buffer is allocated, `buf0` is reused in place as `buf4`, and
two kernels run. `buf1` and `buf3` never appear, and `buf2` is only a name in the reuse chain.
The comments map each kernel back to the user's code.

#### Wrapper lines and memory planning

The wrapper is not written as text straight away. While the scheduler generates code, the
wrapper object collects a list of **line objects**, and the text is produced at the end. Most
are simple: an `ExternKernelOutLine` for the matmul call, a `KernelDefinitionLine` and a
`KernelCallLine` for each generated kernel, an `AssertSizeStrideLine` per input. Allocation and
freeing are
[`MemoryPlanningLine`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/wrapper.py#L759)s,
which have a two-pass interface:

```python
class MemoryPlanningLine(WrapperLine):
    def plan(self, state: MemoryPlanningState) -> MemoryPlanningLine:
        """First pass to find reuse"""
        return self

    def codegen(self, code: IndentedBuffer) -> None:
        """Second pass to output code"""
```

[`memory_plan_reuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/wrapper.py#L2306)
calls `plan` on every line in order, threading one `MemoryPlanningState` through them, and
replaces each line with what `plan` returns. A `FreeIfNotReusedLine` puts its buffer in the
state's reuse pool, keyed by device, dtype, symbolic storage size, alignment and stream. A later `AllocateLine` with the same key
takes the buffer from the pool and turns into a `ReuseLine`. An `AllocateLine` for a buffer that
codegen removed turns into a `NullLine`, which prints nothing. Here are the memory lines of our
example before and after planning, captured from the run:

| Before `plan` | After `plan` | Printed as |
| --- | --- | --- |
| `AllocateLine(buf0)` | unchanged | `buf0 = empty_strided_cpu((8, 32), (32, 1), torch.float32)` |
| `AllocateLine(buf1)` | `NullLine` | nothing: `buf1` lives in registers |
| `ReuseLine(buf0 → buf2)` | unchanged | `buf2 = buf0; del buf0  # reuse` |
| `AllocateLine(buf3)` | `NullLine` | nothing |
| `ReuseLine(buf2 → buf4)` | unchanged | `buf4 = buf2; del buf2  # reuse` |

The two `ReuseLine`s existed before planning. They come from the in-place decision made during
kernel codegen: when a node's output can overwrite an input that dies in the same kernel,
`SchedulerBuffer.allocate` calls
[`codegen_inplace_reuse`](https://github.com/pytorch/pytorch/blob/cf30153c4c131c8164ee7798e5022d810682e2cb/torch/_inductor/codegen/wrapper.py#L3951)
instead of allocating. Planning handles the reuse that needs the whole program in view: an
allocation can take over a buffer freed earlier, as long as that does not raise the estimated
peak memory.

The wrapper costs some Python overhead per call. Two options remove it: **CUDA graphs**
(`mode="reduce-overhead"`) record the kernel launches once and replay them, and
`cpp_wrapper=True` generates the wrapper in C++. **AOTInductor** uses the C++ wrapper to compile
a model ahead of time into a shared library that runs without Python.

### Dynamic shapes

Everything above was specialized to fixed sizes. With `torch.compile(f, dynamic=True)`, sizes are
**symbols** (sympy symbols from the shape environment), and the generated code carries them as
arguments. For `torch.sigmoid(x) * x`:

```python
@triton.jit
def triton_poi_fused_mul_sigmoid_0(in_ptr0, out_ptr0, xnumel, XBLOCK : tl.constexpr):
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    xmask = xindex < xnumel
    x0 = xindex
    tmp0 = tl.load(in_ptr0 + (x0), xmask)
    tmp1 = tl.sigmoid(tmp0)
    tmp2 = tmp1 * tmp0
    tl.store(out_ptr0 + (x0), tmp2, xmask)
```

```python
def call(self, args):  # abridged
    arg0_1, arg1_1, arg2_1 = args
    s77 = arg0_1
    s27 = arg1_1
    assert_size_stride(arg2_1, (s77, s27), (s27, 1), 'input')
    buf0 = empty_strided_cpu((s77, s27), (s27, 1), torch.float32)
    triton_poi_fused_mul_sigmoid_0_xnumel = s27*s77
    triton_poi_fused_mul_sigmoid_0.run(arg2_1, buf0, triton_poi_fused_mul_sigmoid_0_xnumel, ...)
    return (buf0, )
```

`xnumel` is no longer a constant in the kernel, and the wrapper computes it as `s27*s77` from the
sizes passed in. Indexing, fusion and buffer reuse all work on sympy expressions, using the
shape environment's guards to answer questions like "is `s77 * s27` equal to this other size?".
The mask is now essential, since `xnumel` is unknown when the kernel is compiled.

## Summary

- Inductor receives an ATen graph from AOTAutograd. **Decompositions** shrink it to a few kinds
  of simple ops, and graph passes rewrite known patterns, so everything left is pointwise math,
  reductions or extern calls.
- Its IR is **define-by-run**: a loop body is a Python function calling `ops.*`, and installing
  a different `OpsHandler` turns the same function into a dependency analysis, an FX graph, or
  Triton or C++ source. A realized node is both a buffer (`buf2`) and an operation (`op2`), and
  its store function is what every later stage runs.
- **Lowering** composes those functions, so unrealized nodes are inlined for free. A node is
  **realized** into a buffer only when it is reused and expensive, is a reduction or extern
  call, or is an output.
- The **scheduler** fuses nodes greedily: legal pairs (same device, no cycle, compatible
  `(numel, rnumel)`) ranked by the bytes they share. Buffers that become kernel-local disappear,
  and outputs reuse dead inputs in place.
- **Codegen** writes one kernel per fused node. A device's `BaseScheduling` runs each node's body
  inside a kernel object, where `CSEProxy` deduplicates expressions and serves reloads from a store
  cache; a Python wrapper, built from line objects and memory-planned, launches everything. Your
  own code plugs in through `register_lowering`, `CustomGraphPass`, `InductorChoices` and
  `register_backend_for_device`.
