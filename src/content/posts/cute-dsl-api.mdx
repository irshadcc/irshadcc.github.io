## Background

The [`cutlass.cute` API page](https://docs.nvidia.com/cutlass/4.8.0/media/docs/pythonDSL/cute_dsl_api/cute.html)
for CUTLASS 4.8.0 lists about 200 functions and classes, from `depth` to `make_tiled_copy_C_atom`.
Many have no docstring, and few have a picture. That makes the page hard to learn from: you can
see that `nullspace` exists, but not what it returns or when you would want it.

This post goes through that page group by group and explains each function, with a small,
concrete example and a figure wherever a picture helps. It builds on
[A Tour of the CuTe DSL](/blog/cute-dsl/), which covers the core path through a kernel:
`make_layout`, composition, division, products, TV layouts, and copy and MMA atoms. Where the tour
already draws a function, this post links to it rather than drawing it again.

The groups, in order: **tuples** (the data structure under every shape and stride),
**coordinates**, **building**, **simplifying** and **swizzling** layouts, more **layout algebra**,
**pointers and tensors**, **register values** (`TensorSSA`), **copies**, **TMA** bulk copies,
**MMA** (including the `wgmma` and `tcgen05` tensor-core atoms), **structs**,
**math**, **fast integer division**, and **compilation and FFI**. The post ends with a list of
places where the 4.8.0 documentation disagrees with what the code does.<Sidenote>Every output
printed here was produced by running `nvidia-cutlass-dsl==4.8.0` on an RTX 5070 Ti (sm_120).
Layout and tuple results come from tracing (`print` inside `@cute.jit`); register values, math
results and struct offsets come from kernels that ran on the GPU and printed with `cute.printf`.
The figure data is generated by the same script, so the pictures match the printed results.
TMA loads, stores and multicast also ran on this GPU. The `wgmma` and `tcgen05` atoms
need Hopper or data-centre Blackwell, so they were only traced, and are marked as such.</Sidenote>

**Reading the figures.** Grids draw a rank-2 layout with mode 0 down the rows and mode 1 across
the columns. The big number in a cell is what the figure is about (usually an offset), and the
small grey label groups cells: cells with the same label share a colour. Trees draw a nested
tuple: each dot is a tuple, each chip a leaf, and the small number on an edge is the child's
index.

## Tuples

Every shape, stride and coordinate in CuTe is an **IntTuple**: an integer, or a tuple of
IntTuples. A layout is just two IntTuples with the same nesting. So before any layout function, the
API has a set of functions that only look at nesting. We will use one running example:

```python
t = ((2, 3), 4, (5, (6, 7)))
```

<TupleTree trees={[{ label: "t", tuple: R.t }]} name="t has rank 3 (three top-level modes) and depth 3" />

#### `depth`, `rank`, `is_congruent`, `is_weakly_congruent`

- **`cute.rank(t)`** is the number of top-level modes: 3 here.
- **`cute.depth(t)`** is the nesting depth: 0 for a plain integer, 1 for a flat tuple, and 3
  here, because the leaf 6 sits inside three tuples.
- **`cute.is_congruent(a, b)`** is true when `a` and `b` have exactly the same tree:
  `(2,(3,4))` and `(5,(6,7))` are congruent, `(2,(3,4))` and `(5,6)` are not. A layout's shape
  and stride must be congruent.
- **`cute.is_weakly_congruent(a, b)`** allows a leaf of `a` to stand for a whole subtree of `b`.
  `(5,6)` is weakly congruent to `(2,(3,4))`, because the leaf 6 can stand for `(3,4)`, but not
  the other way round. Every integer is weakly congruent to everything. This is the rule for
  **profiles** such as `target_profile` in `coalesce`: a coarser tuple that says how far down to
  go.

#### `flatten`, `flatten_to_tuple`, `unflatten`, `group_modes`

**`cute.flatten(t)`** removes all nesting and keeps the leaves in order. It also works on a layout
(flattening shape and stride together) and on a tensor (flattening its layout).
**`flatten_to_tuple`** does the same but always returns a tuple, even for a single integer.
**`cute.unflatten(seq, profile)`** goes back the other way: it pours a flat sequence into the
nesting of `profile`, ignoring the profile's values. Colours follow leaf values, so you can watch
each leaf move:

<TupleTree

/>

**`cute.group_modes(x, begin, end)`** wraps the modes `begin` to `end - 1` into one nested mode.
It is how a kernel turns, say, `(M, N, K)` into `(M, (N, K))` before a division. On a layout it
groups shape and stride together:

```python
cute.group_modes((2, 3, 4, 5), 1, 3)                   # (2, (3, 4), 5)
cute.group_modes(cute.make_layout((2, 3, 4, 5)), 1, 3) # (2,(3,4),5):(1,(2,6),24)
```

#### `get`, `select`, `find`, `find_if`, `front`

A path from the root to a node is a list of child indices, which CuTe calls a **mode** path.

- **`cute.get(x, mode=[2, 1, 0])`** follows a path: child 2, then its child 1, then its child 0,
  which is the leaf 6. On a layout, `get(L, mode=[0])` returns mode 0 as a layout.
- **`cute.select(x, mode=[2, 0])`** picks top-level modes, in the order given, to build a new tuple
  or layout: `select((2,3,4), mode=[2,0])` is `(4, 2)`. It is a cheap way to permute modes.
- **`cute.find(t, x)`** returns the path to the first leaf equal to `x`, or `None`. With
  `hierarchical=False` it only returns the top-level index.
- **`cute.find_if(t, pred)`** does the same for the first leaf where `pred(leaf, path)` is true.
- **`cute.front(x)`** returns the first leaf, here 2. Kernels use `front(stride)` to read the
  first stride of a mode when deciding whether it is contiguous.

<TupleTree
	trees={[
		{ label: "find(t, 6) = (2,1,0)", tuple: R.t, highlight: [R.find6], text: false },
		{ label: "find_if(t, x > 4) = (2,0)", tuple: R.t, highlight: [R.find_if], text: false },
	]}
/>

Check the first one by hand: 6 is in mode 2, `(5,(6,7))`; inside that it is in child 1, `(6,7)`;
and it is child 0 there. So the path is `(2,1,0)`, and `get(t, mode=[2,1,0])` gives back
6. With `hierarchical=False`, `find(t, 6)` returns just 2.

#### `prepend`, `append`, `wrap`, `unwrap`, `tuple_cat`, `repeat`, `repeat_like`

These build tuples:

| Call | Result | Note |
| --- | --- | --- |
| `prepend((4, 4), 2)` | `(2, 4, 4)` | Add one mode at the front |
| `prepend((1, 1), 0, up_to_rank=4)` | `(0, 0, 1, 1)` | Pad up to a rank |
| `append((1, 1), 0, up_to_rank=4)` | `(1, 1, 0, 0)` | Pad at the back |
| `append(make_layout((8, 8)), make_layout(2))` | `(8,8,2):(1,8,1)` | Works on layouts |
| `append_ones(make_layout((8, 8)), 4)` | `(8,8,1,1):(1,8,0,0)` | Size-1 modes with stride 0 |
| `tuple_cat((1, 2), 3, (4, (5, 6)))` | `(1, 2, 3, 4, (5, 6))` | Concatenate one level |
| `wrap(5)`, `unwrap((5,))` | `(5,)`, `5` | Add or remove one level of tuple |
| `repeat(1, 3)`, `repeat(1, 1)` | `(1, 1, 1)`, `1` | One copy is returned bare |
| `repeat_as_tuple(1, 1)` | `(1,)` | Always a tuple |
| `repeat_like(0, ((1, 2), 3))` | `((0, 0), 0)` | Same tree, every leaf replaced |

`append_ones` and `prepend_ones` pad a layout or tensor with size-1, stride-0 modes. Kernels use
them so that two tensors have the same rank before a copy, without changing which elements they
hold.

#### `transform_leaf`, `transform_apply`, `filter_tuple`

These are the `map`, `map-reduce` and `filter` of CuTe tuples:

| Call | Result |
| --- | --- |
| `transform_leaf(lambda x: x * 2, t)` | `((4, 6), 8, (10, (12, 14)))` |
| `transform_leaf(lambda x, y: x + y, (1, (2, 3)), (10, (20, 30)))` | `(11, (22, 33))` |
| `transform_apply((1, 2, 3), f=lambda x: x * 2, g=lambda *a: sum(a))` | `12` |
| `filter_tuple((1, 2, 3, 4), f=lambda x: (x,) if x % 2 == 0 else ())` | `(2, 4)` |

`transform_leaf` keeps the tree and maps every leaf; with several tuples, they must be congruent.
`transform_apply` maps each **top-level** element with `f`, then combines the results with `g`.
`filter_tuple` maps each element to a tuple and concatenates them, so returning `()` drops an
element.

#### `product`, `product_each`, `product_like`, `shape_div`, `ceil_div`, `round_up`

These are arithmetic on shapes. **`product(t)`** multiplies every leaf: 5040, the number of
coordinates. **`product_each(t)`** multiplies within each top-level mode: `(6, 4, 210)`, the size
of each mode. **`product_like(t, profile)`** stops at the depth of `profile`:

<TupleTree
	trees={[
		{ label: "t", tuple: R.t },
		{ label: "product_each(t)", tuple: R.product_each, op: "product_each" },
		{ label: "product_like(t, ((0,0),0,0))", tuple: R.product_like, op: "product_like" },
	]}
/>

**`shape_div(a, b)`** divides a shape by another. When `b` is a single number and `a` is a tuple,
it walks the leaves from left to right, dividing each one as far as it goes and passing on the
rest of the divisor. That is how CuTe divides a nested mode by a tile size:

<TupleTree
	trees={[
		{ label: "((2,6),8)", tuple: R.shape_div_in },
		{ label: "shape_div(·, 4)", tuple: R.shape_div, op: "÷ 4" },
	]}
/>

Check it: 2 into 4 goes as $2 / 2 = 1$ with 2 of the divisor left over; then $6 / 2 = 3$ uses up
the rest; 8 is untouched. So `((2,6),8) / 4 = ((1,3),8)`, a shape of size $24 = 96 / 4$.
`shape_div((12, 8), (4, 2))` divides mode by mode, giving `(3, 4)`.

**`ceil_div(shape, tiler)`** is the number of tiles needed to cover a shape, rounding up:
`ceil_div((10, 6), (3, 4)) = (4, 2)`. **`round_up((10, 6), (3, 4))`** rounds each mode up to a
multiple: `(12, 8)`. Both are pictured in [Uneven tiles](#uneven-tiles-ceil_div-round_up-and-zipped_divide).

#### `elem_less`, `has_underscore`, `is_static`

- **`cute.elem_less(a, b)`** is true when every leaf of `a` is less than the matching leaf of
  `b`. It is the bounds check for predication: `elem_less((1, 2), (2, 3))` is true,
  `elem_less((1, 3), (2, 3))` is false. It returns a run-time `Boolean` even for constant
  inputs, so it prints as `?` while tracing; the values above were printed on the GPU.
- **`cute.has_underscore(x)`** is true if `x` contains `None`, CuTe's "keep this whole mode"
  marker (written `_` in C++).
- **`cute.is_static(x)`** is true when `x` is fully known while tracing: `(2, 3)` is static,
  `cutlass.Int32(2)` is not.

## Coordinates

A layout can be indexed in two ways: with a **natural coordinate** that has the same nesting as
the shape, such as `((1, 2), 1)`, or with a single **1-D index**. CuTe converts between them
**colexicographically**: the leftmost leaf varies fastest, like column-major order.

#### `crd2idx`, `idx2crd`, `increment_coord`

- **`cute.crd2idx(coord, layout)`** is the layout applied to a coordinate: the sum of each
  coordinate times its stride. For `(5,4):(4,1)`, `(2, 3)` gives $2 \cdot 4 + 3 = 11$.
- **`cute.idx2crd(idx, shape)`** splits a 1-D index into a natural coordinate of `shape`.
- **`cute.increment_coord(coord, shape)`** steps to the next coordinate in the same order,
  carrying into the next mode when a mode wraps.

The figure draws the shape `((2,3),4)`. The number in each cell is its 1-D index, the label is
the natural coordinate `idx2crd` returns for it:

<Matrix2D {...F.idx2crd} caption="shape ((2,3),4): 1-D index (big) and idx2crd of it (small)" />

Check index 11: $11 \bmod 2 = 1$, then $\lfloor 11/2 \rfloor = 5$, $5 \bmod 3 = 2$, then
$\lfloor 5/3 \rfloor = 1$. So `idx2crd(11, ((2,3),4))` is `((1,2),1)`, the cell in the
bottom row of the second column. `increment_coord(((1,2),1), ((2,3),4))` wraps both inner
leaves and returns `((0,0),2)`, which is index 12.

#### `slice_`, `slice_and_offset`, `dice`

**`cute.slice_(x, coord)`** keeps the modes where `coord` is `None` and fixes the rest. The result
forgets the fixed part. **`cute.slice_and_offset(coord, layout)`** returns that sliced layout
together with the offset the fixed coordinates contribute, which is what you add to a pointer.
On the 4×6 column-major layout `(4,6):(1,4)`:

```python
M = cute.make_layout((4, 6))
cute.slice_and_offset((1, None), M)    # ((6):(4), 1)   row 1
cute.slice_and_offset((None, 2), M)    # ((4):(1), 8)   column 2
```

<Matrix2D name="M" {...F.slice} />

Row 1 is six elements 4 apart, starting at 1; column 2 is four contiguous elements starting at
$2 \cdot 4 = 8$. Slicing a tensor does the same and moves the tensor's pointer by the offset.

**`cute.dice(layout, dicer)`** is the opposite selection: it keeps the modes where `dicer` has an
integer and drops the modes marked `None`, without fixing any coordinate.
`dice(make_layout((32,16,8)), (1, None, 1))` is `(32,8):(1,512)`: modes 0 and 2, with their
strides. The `local_tile` projection `proj=(1, None, 1)` from the tour is a dice.

## Building layouts

The tour covers [`make_layout` and `make_ordered_layout`](/blog/cute-dsl/#make_layout-and-make_ordered_layout).
Two more details from the API page:

- **`make_layout([L0, L1])`** with a list of layouts makes one mode per layout:
  `make_layout([make_layout(8, stride=1), make_layout(4, stride=16)])` is `(8,4):(1,16)`.
- **`make_ordered_layout(shape, order)`** works for any rank. `order` gives each mode's rank in
  the stride order, 0 for fastest: `make_ordered_layout((32,16,8), order=(2,0,1))` is
  `(32,16,8):(128,1,16)`, so mode 1 is contiguous, then mode 2, then mode 0.

#### `make_identity_layout`, `E`, `ScaledBasis`, `basis_value`, `basis_get`

Strides do not have to be integers. A **scaled basis** `k@i` means "add $k$ to the $i$-th entry
of a coordinate". **`cute.E(i)`** is `1@i`, and `3 * E(1)` is `3@1`. A layout with these strides
maps a coordinate to another coordinate instead of to an offset.

**`cute.make_identity_layout(shape)`** uses strides `(1@0, 1@1, ...)`, so it maps every
coordinate to itself. It is the layout behind `make_identity_tensor`, which the tour uses for
[bounds checks](/blog/cute-dsl/#make_identity_tensor-and-elem_less).

<Matrix2D {...F.identity} caption="make_identity_layout((4,3)) = (4,3):(1@0,1@1), value of each cell" />

With `(2@0, 1@1)` as strides, every row step adds 2 to the first entry instead:

<Matrix2D {...F.scaled} caption="(4,6):(2@0,1@1), value of each cell" />

Check one cell: row 3, column 5 gives $3 \cdot (2@0) + 5 \cdot (1@1) = (6, 0) + (0, 5) = (6, 5)$.
Kernels use these layouts with TMA, whose copies are addressed by tensor coordinates rather than
by memory offsets.

**`cute.basis_value(e)`** returns the scale (`basis_value(5 * E(0))` is 5), and
**`cute.basis_get(e, t)`** uses the basis's mode path to index a tuple:
`basis_get(2 * E(1), (10, 20, 30))` is 20, and `basis_get(E([0, 1]), ((10, 20), (30, 40)))` is
20 too, because `E([0, 1])` means "mode 0, then its child 1". `ScaledBasis(value, mode)` is the
class behind all of this, and `Ratio(n, d)` is the rational number type CuTe uses when a stride
divides unevenly: `Ratio(1,2) * Ratio(3,4)` prints `3/8`.

#### `make_layout_like`

**`cute.make_layout_like(L)`** builds a **compact** layout with the same shape as `L` and the same
order of strides. Gaps are squeezed out, and zero (broadcast) strides stay zero:

```python
cute.make_layout_like(cute.make_layout((4, 8), stride=(16, 2)))   # (4,8):(8,1)
cute.make_layout_like(cute.make_layout((4, 8), stride=(0, 1)))    # (4,8):(0,1)
```

<LayoutGrid name="L" shape={[4, 8]} stride={[16, 2]} />

<LayoutGrid name="make_layout_like(L)" shape={[4, 8]} stride={[8, 1]} />

`L` spans 63 elements of memory for 32 values; the compact version spans 32 and is still
row-major. This is what you want for a register copy of a tile: same iteration order, no wasted
registers. The tensor versions, `make_fragment_like` and `make_rmem_tensor_like`, are covered
[below](#make_fragment_like-make_rmem_tensor-make_rmem_tensor_like).

#### `is_major`, `leading_dim`, `size_in_bytes`

| Call | Result | Meaning |
| --- | --- | --- |
| `is_major(0, (1, 4))` | `True` | Mode 0 has a static stride of 1 |
| `is_major(1, (1, 4))` | `False` | |
| `leading_dim((4, 8), (1, 4))` | `0` | The mode with stride 1 |
| `leading_dim((4, 8), (8, 1))` | `1` | |
| `leading_dim(((2, 4), 8), ((8, 1), 16))` | `(0, 1)` | A path, when the unit stride is nested |
| `leading_dim((4, 8), (16, 2))` | `None` | No unit stride |
| `size_in_bytes(Float16, (4,8):(1,4))` | `64` | `cosize` × 2 bytes |
| `size_in_bytes(Float16, (4,8):(2,8))` | `126` | `cosize` is 63, gaps included |
| `size_in_bytes(Int4, 5:1)` | `3` | 20 bits, rounded up to whole bytes |

"Major" is CuTe's word for "contiguous": a K-major operand has stride 1 along K. A dynamic stride
is never major, because the compiler can't rely on it being 1.

#### `recast_layout`

The tour [explains `recast_layout`](/blog/cute-dsl/#recast_layout). Two more examples that run
the other direction and with a wider type:

```python
L16 = cute.make_layout((2, 4), stride=(4, 1))
cute.recast_layout(8, 16, L16)      # (2,8):(8,1)      fp16 -> bytes
L16 = cute.make_layout((4, 8), stride=(8, 1))
cute.recast_layout(32, 16, L16)     # (4,4):(4,1)      fp16 -> fp32
L8 = cute.make_layout((2, 3, 4))
cute.recast_layout(16, 8, L8)       # (1,3,4):(1,1,3)  bytes -> fp16
```

The last one is the API page's own example. The page says the result is `(2, 3, 4)`, but 4.8.0
prints `(1,3,4):(1,1,3)`: two bytes become one 16-bit element, so the contiguous mode of size 2
shrinks to 1 and the other strides halve.

## Simplifying layouts

[`coalesce`](/blog/cute-dsl/#coalesce) merges modes without changing the function. The functions
here change the **domain** instead: they remove coordinates that do not reach new memory.

#### `filter_zeros`, `filter`, `nullspace`

A stride of 0 means **broadcast**: every coordinate along that mode reads the same element. Take

```python
# 24 coordinates, 2 distinct offsets
B = cute.make_layout((4, (2, 3)), stride=(0, (1, 0)))
```

<Matrix2D {...F.nullspace} caption="B = (4,(2,3)):(0,(1,0)): offset (big), and whether the 1-D index is in nullspace(B) (small)" />

Only the middle mode moves through memory, so the grid alternates between offset 0 and offset 1.

- **`cute.filter_zeros(B)`** replaces every stride-0 mode by a size-1 mode:
  `(1,(2,1)):(0,(1,0))`. The rank and nesting stay the same, so it can still be used alongside
  the original, but each distinct element is now visited once.
- **`cute.filter(B)`** goes further: it drops the size-1 modes and coalesces what is left, giving
  `2:1`. That is the minimal layout over the same elements.
- **`cute.nullspace(B)`** returns a layout over the **1-D indices** of `B` whose image under `B` is
  0: `(4,3):(1,8)`, which lists indices 0–3, 8–11 and 16–19. Those are the cells labelled
  "B → 0". Its size is $24 / 2 = 12$, as the docstring says: the size of `B` divided by the size
  of `filter_zeros(B)`.

Check one: index 9 is coordinate `(1, (0, 1))`, and $1 \cdot 0 + 0 \cdot 1 + 1 \cdot 0 = 0$.
For a layout with no zero strides, such as `(4,8):(1,4)`, `nullspace` returns `1:0`, a single
index 0.

#### `max_common_layout`, `max_common_vector`

Before vectorizing a copy, a kernel needs to know how many elements in a row are contiguous in
**both** the source and the destination. **`cute.max_common_vector(a, b)`** answers that, and
**`cute.max_common_layout(a, b)`** returns those elements as a layout over the 1-D index.

| `a` | `b` | `max_common_layout` | `max_common_vector` |
| --- | --- | --- | ---: |
| `(8,8):(8,1)` | `(8,8):(8,1)` | `(8,8):(8,1)` | 64 |
| `(8,8):(8,1)` | `(8,8):(16,1)` | `8:8` | 8 |
| `(8,8):(8,1)` | `(8,8):(1,8)` | `1:0` | 1 |

<LayoutGrid name="b" shape={[8, 8]} stride={[16, 1]} />

In the middle row, `b` is row-major with padded rows. Each row of 8 is contiguous in both
layouts, but the next row starts at 16 in `b` instead of 8, so the common run stops at 8.
`8:8` lists the 1-D indices 0, 8, ..., 56: the eight coordinates of row 0, because consecutive
columns are 8 apart in the column-major 1-D index. With one layout column-major and the other
row-major, no two neighbours line up, and the answer is a single element.

## Swizzles and composed layouts

Shared memory is split into 32 4-byte **banks**, and two threads that read different addresses
in the same bank at once are serialised. In a tile of `Float32` stored row by row with rows of
32 elements, a whole column sits in one bank. A
**swizzle** fixes this by XOR-ing some bits of the offset into others, which permutes each row
differently.

#### `Swizzle`, `make_swizzle`

**`cute.make_swizzle(b, m, s)`** builds `S<b,m,s>`. Reading the offset in binary, it takes the
`b` bits starting at bit `m + s` and XORs them into the `b` bits starting at bit `m`:

$$
\text{swizzle}(x) = x \oplus \big((x \gg s) \mathbin{\&} (\text{mask}_b \ll m)\big),
\qquad \text{mask}_b = 2^b - 1 .
$$

`m` keeps the lowest bits fixed (elements that must stay together, such as a 16-byte vector),
`b` is how many bits are permuted, and `s` is how far away the bits that drive the permutation
are. `swizzle.num_bits`, `num_base` and `num_shift` return `b`, `m` and `s`.

A scaled-down example: an 8×8 tile stored row-major, `(8,8):(8,1)`, with 8 **bank groups**
standing in for banks (offset mod 8). Unswizzled, every element of a column is in the same
group:

<Matrix2D name="unswizzled tile, labelled by bank group" {...F.noswizzle} />

With `S<3,0,3>`, bits 3–5 of the offset (the row) are XORed into bits 0–2 (the column), so row
$i$ stores column $j$ at column $j \oplus i$:

<Matrix2D {...F.swizzle} caption="S<3,0,3> o (8,8):(8,1), swizzled offset and its bank group" />

Now every column touches all 8 groups exactly once, so a column read is conflict-free. Check one
cell: row 3, column 5 is offset $29 = 011\,101_2$. The row bits `011` XORed into the column bits
`101` give `110`, so the swizzled offset is $011\,110_2 = 30$, in group 6. Real kernels use
`S<3,4,3>` on byte offsets: the lowest 4 bits stay fixed so each 16-byte vector stays whole, and
the 8 vectors of a 128-byte line are permuted by the row.

#### `make_composed_layout`, `get_swizzle_portion`, `get_nonswizzle_portion`

A swizzle is not a layout, so CuTe combines them as a **composed layout**
`inner ∘ offset ∘ outer`: apply `outer` to the coordinate, add `offset`, then apply `inner`.

```python
sw = cute.make_swizzle(3, 0, 3)
C = cute.make_composed_layout(sw, 0, cute.make_layout((8, 8), stride=(8, 1)))
print(C)                          # S<3,0,3> o 0 o (8,8):(8,1)
C.inner, C.offset, C.outer        # the three parts; C.is_normal is False
cute.get_swizzle_portion(C)       # S<3,0,3>
cute.get_nonswizzle_portion(C)    # (8,8):(8,1)
```

On a plain layout, `get_swizzle_portion` returns the identity swizzle `S<0,4,3>` and
`get_nonswizzle_portion` returns the layout itself, so code can handle both cases the same way.
Layout algebra on a composed layout acts on the `outer` part and keeps the swizzle:
`composition(C, (4,4))` is `S<3,0,3> o 0 o (4,4):(8,1)`, and `zipped_divide(C, (4,4))` is
`S<3,0,3> o 0 o ((4,4),(2,2)):((8,1),(32,4))`. `recast_layout` adjusts the swizzle too:
recasting `S<3,4,3> o (8,64):(64,1)` from bytes to 16-bit elements gives
`S<3,3,3> o (8,32):(32,1)`, because the 16 fixed bytes are now 8 elements.

## More layout algebra

The tour covers [composition](/blog/cute-dsl/#composition), [complement](/blog/cute-dsl/#complement),
the [four divides](/blog/cute-dsl/#division-splitting-into-tiles),
[products](/blog/cute-dsl/#products-repeating-a-tile), [inverses](/blog/cute-dsl/#right_inverse-and-left_inverse)
and [`make_layout_tv`](/blog/cute-dsl/#thread-value-layouts). This section fills in the rest.

#### `tiled_product`, `flat_product`

These regroup `logical_product`, the way `tiled_divide` and `flat_divide` regroup
`logical_divide`. For the tour's 2×2 tile repeated 2×3 times:

```python
tile, reps = cute.make_layout((2, 2)), cute.make_layout((2, 3))
cute.tiled_product(tile, reps)   # ((2,2),2,3):((1,2),4,8)
cute.flat_product(tile, reps)    # (2,2,2,3):(1,2,4,8)
```

In 4.8.0 every product needs a single layout as the second argument. A tuple of per-mode
layouts, which the divides accept, failed to build for all of them, including `logical_product`,
whose signature says it takes a `Tile`.

#### `tile_to_shape`

**`cute.tile_to_shape(atom, shape, order)`** repeats a small layout until it fills `shape`, laying
the copies out in the mode order `order`. It is how kernels build a shared-memory layout from a
swizzled 8×64 atom. Tiling a 2×2 row-major atom `(2,2):(2,1)` to 4×6:

<Matrix2D {...F.tts01} caption="tile_to_shape(atom, (4,6), order=(0,1)) = ((2,2),(2,3)):((2,4),(1,8))" />

<Matrix2D {...F.tts10} caption="tile_to_shape(atom, (4,6), order=(1,0)) = ((2,2),(2,3)):((2,12),(1,4))" />

Each copy of the atom is a contiguous block of 4 offsets, and inside it the atom's row-major
order is kept. With `order=(0,1)` the copies go down first (atom 1 is below atom 0); with
`order=(1,0)` they go across first.

#### Uneven tiles: `ceil_div`, `round_up` and `zipped_divide`

Divisions do not need the tile to divide the shape. `zipped_divide` rounds the number of tiles
up, and the extra coordinates fall outside the tensor:

```python
M = cute.make_layout((10, 6))
cute.zipped_divide(M, (3, 4))     # ((3,4),(4,2)):((1,10),(3,40))
cute.ceil_div((10, 6), (3, 4))    # (4, 2)  tiles
cute.round_up((10, 6), (3, 4))    # (12, 8) padded extent
```

<Matrix2D {...F.ceil_div} caption="10×6 tensor in 3×4 tiles, padded to round_up = 12×8: offset (big) and tile (small)" />

The bottom tile row and the right tile column stick out. Reading them would go out of bounds, so
a kernel must predicate those elements, using an identity tensor and `elem_less` as in the
tour's [bounds-check example](/blog/cute-dsl/#make_identity_tensor-and-elem_less).

#### `local_tile` and `local_partition` details

Two details not in the tour. Passing `None` in a `local_tile` coordinate keeps every tile along
that mode, as an extra mode at the end:

```python
x = cute.make_tensor(ptr, cute.make_layout((16, 24)))
cute.local_tile(x, (2, 4), (1, 1))      # (2,4):(1,16)       one tile
cute.local_tile(x, (2, 4), (1, None))   # (2,4,6):(1,16,64)  all 6 in tile row 1
```

And `local_partition`'s thread index must be a run-time value such as `cutlass.Int32(5)` (a
thread index usually is); a plain Python `5` fails to build in 4.8.0.

#### `make_layout_image_mask`

Thread-block clusters can **multicast** a TMA load to several blocks at once, and the
instruction takes a 16-bit mask of the target blocks. **`cute.make_layout_image_mask(L, coord, mode)`**
builds that mask from a layout of block ranks: it fixes every mode of `coord` except `mode`,
walks `mode` fully, and sets bit `L(c)` for each coordinate `c` reached.

<Matrix2D {...F.image_mask} caption="cluster layout (2,4):(1,2): the rank each block's bit stands for" />

For `coord=(1, 2)` and `mode=1`, the row is fixed to 1 and the column varies, which reaches ranks
1, 3, 5 and 7 (the cells labelled "row 1"), so the mask is
$2^1 + 2^3 + 2^5 + 2^7 = 170$. With `mode=0` instead, the column is fixed to 2 and the mask is
$2^4 + 2^5 = 48$. A kernel can use it, for example, to send one A tile to every block in a cluster row.

## Pointers and tensors

#### `make_ptr`, `recast_ptr`, `AddressSpace`

A **pointer** in the DSL carries its element type, its memory space and its known alignment.
`cute.make_ptr(Float32, address, cute.AddressSpace.gmem, assumed_align=16)` prints as
`ptr<f32, gmem, align<16>>`. The address spaces are:

| `AddressSpace` | Memory |
| --- | --- |
| `gmem` | Global (device) memory |
| `smem` | Shared memory of this thread block |
| `dsmem` | Shared memory of another block in the cluster |
| `rmem` | Registers |
| `tmem` | Blackwell tensor memory |
| `cmem` | Constant memory |
| `generic` | Unknown; resolved at run time |

Alignment is what lets the compiler emit vector loads, and the DSL tracks it through arithmetic:
`ptr + 4` keeps `align<16>` because 4 floats are 16 bytes, but `ptr + 5` drops it.
**`cute.recast_ptr(ptr, dtype=Float16)`** reinterprets the element type, giving
`ptr<f16, gmem, align<16>>`.

#### `make_tensor` and coordinate tensors

**`cute.make_tensor(iterator, layout)`** pairs a pointer with a layout. The iterator can also be
an integer or a coordinate, which gives a **coordinate tensor**: instead of reading memory, it
returns `iterator + layout(c)`. `make_tensor(5, make_layout(4, stride=16 * E(0)))` prints as
`tensor<5 o 4:16@0>`, and `make_identity_tensor((3,2))` is `tensor<(0,0) o (3,2):(1@0,1@1)>`.
Dividing an identity tensor keeps track of where each tile starts: `zipped_divide` of a 6×7
identity tensor by 4×4 is `tensor<(0,0) o ((4,4),(2,2)):((1@0,1@1),(4@0,4@1))>`.

A tensor's parts are available as `t.layout`, `t.shape`, `t.stride`, `t.element_type`,
`t.iterator` and `t.memspace`.

#### `domain_offset`

**`cute.domain_offset(coord, t)`** moves a tensor's origin to `coord`: it adds `t.layout(coord)`
to the pointer and keeps the layout. The new tensor's `(0, 0)` is the old `(1, 2)`:

```python
t = cute.make_tensor(ptr, cute.make_layout((4, 6)))   # (4,6):(1,4)
u = cute.domain_offset((1, 2), t)                     # same layout, pointer + 9
```

<Matrix2D name="t, labelled with coordinates in u" {...F.domain_offset} />

The offset is $1 \cdot 1 + 2 \cdot 4 = 9$. `u` keeps the shape `(4, 6)`, so its last rows and
columns run past `t`; the cells labelled "new" are the ones still inside. Kernels use
`domain_offset` to step a coordinate tensor to the current tile, and they rely on predicates for
the part that hangs over.

#### `recast_tensor`

**`cute.recast_tensor(t, dtype)`** reinterprets a tensor's memory as another type, rescaling the
contiguous mode. A 4×6 `Float32` tensor `(4,6):(1,4)` read as `Float16` is `(8,6):(1,8)`: twice as
many elements down each column, because each float is now two halves.

<Matrix2D {...F.recast_tensor} caption="recast_tensor(t, Float16) = (8,6):(1,8), labelled by the Float32 element each half came from" />

Recasting to `Int32` keeps the layout `(4,6):(1,4)`, since the width is the same.

#### `make_fragment_like`, `make_rmem_tensor`, `make_rmem_tensor_like`

These allocate a **register tensor**, a small per-thread array that the compiler keeps in
registers. All three use 32-byte alignment, and booleans are stored as 8-bit integers.

| Call | Result |
| --- | --- |
| `make_rmem_tensor((4, 8), Float16)` | `tensor<ptr<f16, rmem, align<32>> o (4,8):(1,4)>` |
| `make_rmem_tensor_like(t)` for `t` with layout `(4,8):(16,2)` | `... f32, rmem ... o (4,8):(8,1)` |
| `make_rmem_tensor_like(t, Boolean)` | `... i8, rmem ... o (4,8):(8,1)` |
| `make_fragment_like(t)` for the same `t` | `... f32, rmem ... o (4,8):(8,1)` |
| `make_fragment_like(t)` for a broadcast `(4,(2,4)):(1,(0,4))` | keeps `(4,(2,4)):(1,(0,4))` |
| `make_fragment_like(L)` for a **layout** `(4,8):(16,2)` | `(4,8):(1,4)` |

The tensor versions follow `make_layout_like`: compact, same stride order, broadcast modes kept
(so a broadcast tensor gets one register per distinct element). The API page says
`make_rmem_tensor_like` uses "compact column-major strides", but for a row-major source 4.8.0
keeps it row-major. Given a bare layout, `make_fragment_like` does return a column-major one.

## Values in registers: `TensorSSA`

`t.load()` returns a **`TensorSSA`**: an immutable value with a shape, held in registers, that the
compiler sees as one vector. Arithmetic on it is elementwise, and `t.store(v)` writes it back. The
examples below start from a 2×3 register tensor holding 0 to 5 in column-major order, and every
result was printed on the GPU:

```python
a = cute.make_rmem_tensor((2, 3), Float32)
# a[i] = i, so the rows are [0, 2, 4] and [1, 3, 5]
v = a.load()
```

#### Arithmetic, `apply_op`, `broadcast_to`

`v + w`, `v * 2.0`, `v > 2.5` and so on work elementwise and return a `TensorSSA` (comparisons
return booleans). **`v.apply_op(op, w)`** applies any binary function, for example
`operator.mul`. **`v.broadcast_to(shape)`** stretches size-1 modes, NumPy style. Broadcasting the
row `[10, 20, 30]`, of shape `(1, 3)`, to `(2, 3)` reads each value once per row, exactly as a
stride-0 row mode would:

<Matrix2D {...F.broadcast} caption="the row [10,20,30] broadcast to (2,3), drawn as the layout (2,3):(0,1)" />

| Expression | Rows of the result |
| --- | --- |
| `v` | `[0, 2, 4]`, `[1, 3, 5]` |
| `v + row.broadcast_to((2, 3))` | `[10, 22, 34]`, `[11, 23, 35]` |
| `v.apply_op(operator.mul, row.broadcast_to((2, 3)))` | `[0, 40, 120]`, `[10, 60, 150]` |

#### `reduce`

**`v.reduce(op, init, reduction_profile)`** folds with `cute.ReductionOp.ADD`, `MAX` and so on.
The profile marks the modes to reduce with `1` and the modes to keep with `None`; a profile of
`0` reduces everything to a scalar.

| Call | Result | Reading |
| --- | --- | --- |
| `v.reduce(ADD, 0.0, reduction_profile=(None, 1))` | `[6, 9]` | Sum of each row: $0+2+4$, $1+3+5$ |
| `v.reduce(MAX, -1e30, reduction_profile=(1, None))` | `[1, 3, 5]` | Max of each column |
| `v.reduce(ADD, 0.0, reduction_profile=0)` | `15` | Sum of everything |

According to the docstring, the profile can also be nested: on a shape `(4, (5, 4))`, `(None, (None, 1))` keeps mode 0 and the
first part of mode 1, giving shape `(4, (5,))`.

#### `reshape`, `to`, `bitcast`

- **`v.reshape((3, 2))`** reinterprets the same elements in column-major order:
  `[[0, 3], [1, 4], [2, 5]]`.
- **`v.to(Float16)`** converts each value to another type (0 to 5 again, now in half precision).
- **`v.bitcast(Int32)`** keeps the bits and changes the type: 1.0 becomes 1065353216
  (`0x3F800000`) and 2.0 becomes 1073741824. Bitcasting to a narrower type multiplies the
  element count, so the 6 floats become a `(12,)` vector of `Float16`.

#### `full`, `full_like`, `empty_like`, `ones_like`, `zeros_like`, `where`, `any_`, `all_`

| Call | Result |
| --- | --- |
| `cute.full((2, 2), 3, Int32)` | `[[3, 3], [3, 3]]` |
| `cute.zeros_like(v) + cute.ones_like(v) * 7.0` | all 7 |
| `cute.where(v > 2.5, v, cute.full_like(v, -1.0))` | `[-1, -1, 4]`, `[-1, 3, 5]` |
| `cute.any_(v > 4.0)`, `cute.all_(v >= 0.0)`, `cute.all_(v > 0.0)` | `True`, `True`, `False` |

`empty_like` returns a value of the same shape and type whose contents are undefined, for when
every element will be overwritten. `where` is the branch-free select: both sides are computed and
each element picks one, which is how kernels apply a mask such as causal attention without
divergent branches.

## Copies

The tour introduces [copy atoms and tiled copies](/blog/cute-dsl/#make_copy_atom-make_tiled_copy_tv-and-copy).
This section goes through the whole family.

#### `make_copy_atom` and `CopyAtom`

**`cute.make_copy_atom(op, dtype, **kwargs)`** pairs a copy instruction with an element type. Its
properties describe one instruction: `thr_id` (which threads take part) and `layout_src_tv` /
`layout_dst_tv` (which (thread, value) holds which element). A universal copy of 64 bits of
`Float32` is a one-thread atom that moves 2 values:

```python
op = cute.nvgpu.CopyUniversalOp()
atom = cute.make_copy_atom(op, Float32, num_bits_per_copy=64)
# ThrID 1:0, TV Layout Src (1,2):(0,1), TV Layout Dst (1,2):(0,1)
```

A warp-wide instruction looks different. The `ldmatrix` atom
`LdMatrix8x8x16bOp(num_matrices=4)` has `thr_id = 32:1`, a source layout `(32,8):(8,1)` (each
lane supplies the address of one 16-byte row) and a destination layout `(32,(2,4)):(2,(1,64))`
(each lane receives 8 halves spread over the four matrices).

#### `make_tiled_copy_tv`, `make_tiled_copy`, `make_cotiled_copy`

A **tiled copy** repeats the atom over many threads. There are three ways to describe how:

- **`make_tiled_copy_tv(atom, thr_layout, val_layout)`**: give the arrangement of threads and of
  each thread's values, and let CuTe build the TV layout with `make_layout_tv`.
- **`make_tiled_copy(atom, layout_tv, tiler_mn)`**: give a TV layout and tile shape you already
  have.
- **`make_cotiled_copy(atom, atom_layout_tv, data_layout)`**: give the TV layout as **offsets**
  into `data_layout`, when only vector width and addresses matter.

With 8 threads arranged row-major over a 4×2 grid, `(4,2):(2,1)`, and 2 values each along N,
`(1,2)`:

```python
thr = cute.make_layout((4, 2), stride=(2, 1))
val = cute.make_layout((1, 2))
tc = cute.make_tiled_copy_tv(atom, thr, val)
tc.tiler_mn          # (4:1, 4:1)
tc.layout_tv_tiled   # ((2,4),2):((8,1),4)
tc.size              # 8 threads
```

<Matrix2D {...F.copy_tv} caption="4×4 tile of the tiled copy: value index (big) and thread (small)" />

Each thread copies two horizontally adjacent elements, one 64-bit instruction, and threads 0 and
1 sit side by side in row 0. Check thread 1 in `((2,4),2):((8,1),4)`: thread 1 is coordinate
`(1, 0)` of `(2,4)`, so its first value is at 1-D index 8, which is row 0, column 2 of the
column-major 4×4 tile; its second value adds 4, column 3.

#### `get_slice`, `partition_S`, `partition_D`, `retile`

**`tc.get_slice(tid)`** returns a `ThrCopy`, one thread's view. **`partition_S(src)`** and
**`partition_D(dst)`** cut a source or destination tensor into that thread's pieces, shaped
`(CPY, CPY_M, CPY_N)`: the values of one instruction, then how many times the tile repeats along
M and N. On a 4×8 tensor (two copy tiles side by side), thread 3 gets:

```python
thr = tc.get_slice(cutlass.Int32(3))
idt = cute.make_identity_tensor((4, 8))
thr.partition_S(idt)    # ((2,1),1,2):((1@1,0),0,4@1)
```

<Matrix2D {...F.copy_part} caption="4×8 tensor, two copy tiles: value index (big), thread 3's cells labelled" />

Thread 3 owns two adjacent columns in each of the two tiles, 4 columns apart: that is the `4@1`
stride of the last mode. **`tc.retile(frag)`** reshapes a register tensor that was built for a
different partition (for example, from an MMA) into this copy's `(CPY, CPY_M, CPY_N)` shape, so
the same registers can be fed to `cute.copy`.

#### Copies that match another layout

These functions build a tiled copy whose TV layout matches an existing one, so the data lands in
the registers the next instruction expects:

| Function | Matches |
| --- | --- |
| `make_tiled_copy_A(atom, tiled_mma)` | the A operand layout of an MMA |
| `make_tiled_copy_B(atom, tiled_mma)` | the B operand layout |
| `make_tiled_copy_C(atom, tiled_mma)` | the C accumulator layout |
| `make_tiled_copy_C_atom(atom, tiled_mma)` | the smallest piece of the C layout the atom can copy, for epilogues that store C in sub-tiles |
| `make_tiled_copy_S(atom, tiled_copy)` | the source layout of another tiled copy |
| `make_tiled_copy_D(atom, tiled_copy)` | its destination layout |

For the Ampere `m16n8k16` MMA below, `make_tiled_copy_A(ldmatrix_atom, mma)` has the tile
`(16, 16)` and exactly the MMA's A layout, `((4,8),((2,2,2),(1,1))):((32,1),((16,8,128),(0,0)))`.
`make_tiled_copy_C_atom(atom, mma)` with the 2-value universal atom covers an 8 × 8 piece
(`tiler_mn = (8:1, (4,2):(2,1))`) instead of the whole 16×8 accumulator.

#### `copy`, `copy_atom_call`, `basic_copy`, `basic_copy_if`, `autovec_copy`, `prefetch`

| Function | What it does |
| --- | --- |
| `cute.copy(atom, src, dst, pred=None)` | Copies `(V, Rest...)` tensors: one atom call per position in `Rest`. `pred` masks whole positions |
| `cute.copy_atom_call(atom, src, dst, pred=None)` | One atom call on one `(V)` fragment |
| `cute.basic_copy(src, dst)` | Elementwise loop, no atom |
| `cute.basic_copy_if(pred, src, dst)` | The same, skipping elements where `pred` is false |
| `cute.autovec_copy(src, dst)` | Elementwise, but picks the widest safe vector width for static shapes |
| `cute.prefetch(atom, src)` | Prefetches global memory into L2; TMA atoms only (not run here) |

Run on 8 elements `0..7` into a destination filled with `-1`:

| Call | Destination |
| --- | --- |
| `basic_copy_if(pred, src, dst)` with `pred = i < 5` | `0 1 2 3 4 -1 -1 -1` |
| `copy(atom, src, dst, pred=...)` on `(1,8)` tensors with `pred = i` even | `0 -1 2 -1 4 -1 6 -1` |
| `basic_copy(src, dst)`, `autovec_copy(src, dst)` | `0 1 2 3 4 5 6 7` |

TMA copies take extra keyword arguments, such as `tma_bar_ptr`, `mcast_mask` and
`cache_policy`. The next section runs them.

## TMA: bulk tensor copies

The copies above are done by threads: each thread computes addresses and moves a few bytes. The
**Tensor Memory Accelerator (TMA)** is a copy engine in each SM of Hopper and Blackwell GPUs that
does the whole job itself. A kernel hands it a **tensor map**, a 128-byte descriptor of a global
tensor (base address, shape, strides, box size and swizzle), plus the coordinates of a **box**,
one tile of that tensor. The TMA unit then copies the box between global and shared memory,
handles the edges of the tensor, and reports the bytes it has written to an mbarrier.

This matters because one thread now moves a whole tile. The other threads and their registers are
free for math, and edge tiles need no special code. The functions live in
`cutlass.cute.nvgpu.cpasync` and `cute.arch`. This section builds a TMA atom, partitions with it,
synchronises a load with an mbarrier, and then looks at edges, stores, swizzled boxes and
multicast. The [Hopper and Blackwell Q&A](/blog/hopper-blackwell-kernel-qa/) covers the hardware
side.<Sidenote>Every kernel in this section ran on the RTX 5070 Ti (sm_120, driver 590.48.01).
It supports TMA and 2-CTA clusters. The tables and figures are generated from what those kernels
printed. The scripts allocate memory with `cuda.bindings.runtime.cudaMalloc` and wrap it with
`make_ptr`, so neither NumPy nor PyTorch is needed.</Sidenote>

#### `make_tiled_tma_atom` and the TMA tensor

The example tensor has 6 × 10 Float32 values, value $10r + c$ at row $r$, column $c$. It is
stored row-major with a row stride of 12, so each row ends in two padding columns that hold 999.
**`cpasync.make_tiled_tma_atom(op, gmem_tensor, smem_layout, cta_tiler, num_multicast=1)`**
builds the tensor map on the host. It returns a `TmaInfo` that unpacks into the copy atom and a
**TMA tensor**:

```python
g = cute.make_tensor(ptr, cute.make_layout((6, 10), stride=(12, 1)))
s_layout = cute.make_layout((4, 4), stride=(4, 1))
atom, tma_t = cpasync.make_tiled_tma_atom(
    cpasync.CopyBulkTensorTileG2SOp(), g, s_layout, (4, 4))
# atom:  ThrID 1:0, TV Layout Src (1,16):(0,1), Value type f32
# tma_t: tensor<(0,0) o (6,10):(1@1,1@0)>
```

The atom has a single "thread" moving 16 values, because one instruction copies the whole box.
The TMA tensor holds no data: it is a coordinate tensor whose strides are scaled bases. It maps
element $(r, c)$ to the TMA coordinate $(c, r)$, column first, because TMA's dimension 0 is the
contiguous one. The row stride 12 does not appear anywhere in it; it is stored in the descriptor.
The figure shows the tensor and the 4 × 4 boxes it is cut into:

<Matrix2D {...T.gmem} caption="the 6×10 tensor in a 6×12 allocation: value (big) and the TMA box it falls in (small)" />

Boxes in the last row and column hang over the edge. Box (1,2), for example, covers rows 4–7 and
columns 8–11, but only rows 4–5 and columns 8–9 exist.

#### `tma_partition`

A kernel picks its box with `local_tile` on the TMA tensor, then calls
**`cpasync.tma_partition(atom, cta_coord, cta_layout, smem_tensor, gmem_tensor)`**. It returns
the shared and global sides of the copy, `(tAsA, tAgA)`:

```python
gT = cute.local_tile(tma_t, (4, 4), (bm, bn))
tAsA, tAgA = cpasync.tma_partition(
    atom, 0, cute.make_layout(1),
    cute.group_modes(sA, 0, 2), cute.group_modes(gT, 0, 2))
# gT   = tensor<(?{div=4},?{div=4}) o (4,4):(1@1,1@0)>
# tAgA = tensor<(?{div=4},?{div=4}) o (((4,4),1)):(((1@0,1@1),0))>
# tAsA = tensor<ptr<f32, smem, align<128>> o ((16,1)):((1,0))>
```

`group_modes(..., 0, 2)` makes the whole box mode 0. TMA moves mode 0 in one instruction, and
any further modes (here a single `1`) count separate boxes, such as the k-blocks of a GEMM. The
coordinate `(?{div=4},?{div=4})` is the box corner, $(4 \cdot bn, 4 \cdot bm)$: unknown at
compile time, but known to be a multiple of 4. `cta_coord` and `cta_layout` place this CTA in a
multicast group; with no multicast they are `0` and a layout of size 1.

#### Synchronising a load with an mbarrier

A TMA load is asynchronous, so the kernel needs to know when the bytes have landed. It uses an
**mbarrier**, a 64-bit object in shared memory that counts two things: thread arrivals and
**transaction bytes**. A phase of the barrier completes when both counts reach zero. Step through
the load:

<SequenceSteps participants={tmaParticipants} messages={tmaMessages} title="One TMA load, one mbarrier phase" />

In code, with the barrier allocated in a struct as `MemRange[Int64, 1]`:

```python
if tidx == 0:
    cute.arch.mbarrier_init(bar, 1)
cute.arch.mbarrier_init_fence()
cute.arch.barrier()
if tidx == 0:
    cute.arch.mbarrier_arrive_and_expect_tx(bar, 64)
cute.copy(atom, tAgA, tAsA, tma_bar_ptr=bar)   # the whole warp
cute.arch.mbarrier_wait(bar, 0)
```

Call `cute.copy` from a whole warp, not from one thread. The DSL wraps the TMA instruction in an
`elect.sync` over all 32 lanes, so it picks the issuing lane itself.<Sidenote>My first version
called `cute.copy` inside `if tidx == 0:`. The kernel never finished, and I stopped it after 120
seconds. The PTX showed the reason: inside that branch, `elect.sync` with a full member mask runs
with only lane 0 active. Moving the call out of the branch fixed it.</Sidenote> The phase passed
to `mbarrier_wait` is the one being waited for, 0 for the first use. A kernel that reuses the
barrier flips it each round.

Here are box (0,0) and the edge box (1,2), as printed from shared memory after the wait:

<Matrix2D {...T.box00} caption="box (0,0) in shared memory: value (big), global (row, column) (small)" />

<Matrix2D {...T.box12} caption="box (1,2) in shared memory: value (big), global (row, column) or why it is out of bounds (small)" />

Check one entry: cell (1,1) of box (1,2) is global $(4 + 1, 8 + 1) = (5, 9)$, so it holds
$10 \cdot 5 + 9 = 59$. The other twelve cells are zero, including columns 10 and 11, whose
padding in memory holds 999. TMA clips the box against the tensor's shape, not the allocation's.
The barrier still counts the full 64 bytes: `expect_tx` takes the box size even for an edge
box. Before the load, the threads had filled the tile with $-1$. A
`cute.arch.fence_proxy("async.shared", space="cta")` orders those ordinary writes before the TMA
unit's.

#### Stores, and how far clipping goes

A store uses **`CopyBulkTensorTileS2GOp`** with the same atom and partition calls. It needs no
mbarrier; the issuing warp waits on a **bulk group** instead:

```python
# threads wrote the tile to sA, then
cute.arch.fence_proxy("async.shared", space="cta")
cute.arch.barrier()
cute.copy(st_atom, tBsA, tBgO)                  # smem -> gmem
cute.arch.cp_async_bulk_commit_group()
cute.arch.cp_async_bulk_wait_group(0, read=False)
```

`wait_group(0, read=False)` waits until the writes have completed. With `read=True` it waits only
until shared memory has been read, which is enough to reuse the buffer. Storing a tile of
$100 + r + 4c$ to box (1,2) of a fresh output tensor gave:

<Matrix2D {...T.store} caption="rows 4–7 of the output after storing box (1,2): value (big; −7 = not written), position against N (small)" />

Rows 6 and 7 are past $M = 6$ and were not written. Columns 10 and 11 are past $N = 10$, but they
were written. I expected those columns to be left alone, so I repeated the store with an
8-wide box over columns 8–15. With $N = 9$, columns 8–11 were written and 12–15 were not. With
$N = 13$, all of 8–15 were written. On this GPU, then, a store is clipped exactly in rows but in
**16-byte chunks** (four Float32) along the contiguous dimension.<Sidenote>This contradicts the
usual description, that out-of-bounds elements of a TMA store are not written (for example
[Q37 of the Q&A post](/blog/hopper-blackwell-kernel-qa/)). I saw it only on sm_120 with driver
590.48.01, and did not test a Hopper or data-centre Blackwell GPU. Loads were clipped exactly in
both dimensions.</Sidenote> To be safe, make the contiguous extent of a stored tensor a multiple of
16 bytes, or give the padding room to be overwritten.

#### Swizzled boxes

The descriptor can also swizzle the box as it lands, so that a later MMA or `ldmatrix` reads
shared memory without bank conflicts. The swizzle comes from the shared memory layout passed to
`make_tiled_tma_atom`. For a K-major fp16 operand with the 128-byte swizzle:

```python
atom_l = warpgroup.make_smem_layout_atom(
    warpgroup.SmemLayoutAtomKind.K_SW128, Float16)
# S<3,4,3> o 0 o (8,64):(64,1)
s_layout = cute.tile_to_shape(atom_l, (8, 64), (0, 1))
# S<3,4,3> o 0 o ((8,1),(64,1)):((64,0),(1,0))
```

One row of 64 fp16 values is 128 bytes, eight 16-byte chunks. `S<3,4,3>` counts in bytes: it
XORs the row index (bits 7–9) into the chunk index (bits 4–6). After loading an $8 \times 64$
tile with values $64r + c$, the kernel read shared memory raw and printed which logical chunk sat
in each physical slot:

<Matrix2D {...T.swizzle} caption="8 rows × 8 physical slots of 16 bytes: the logical chunk stored there, coloured by chunk" />

Slot $q$ of row $r$ holds chunk $q \oplus r$. Row 0 is unchanged, and row 7 is reversed. Each
column of the figure holds all eight chunks, which is what spreads a column read across the
banks. See [`Swizzle`](#swizzle-make_swizzle) above for the general rule.

To read the tile back through its logical coordinates, build the tensor the way NVIDIA's examples
do, with **`get_tensor(layout.outer, swizzle=layout.inner)`**. That gives a pointer that carries
the swizzle, `ptr<f16, smem, align<1024>, S<3,4,3>>`, and element (3,13) reads 205 $= 64 \cdot 3 +
13$, as it should. Passing the composed layout itself, `get_tensor(s_layout)`, read 197 for the
same element.<Sidenote>197 is what you get by applying `S<3,4,3>` to the *element* offset
instead of the byte offset. Element offset 205 has bits 4–6 equal to 4 and bits 7–9 equal to 1,
so the swizzle turns it into 221, which is physical (3, 29). Slot 3 of row 3 holds logical chunk
0, so element (3, 29) holds logical (3, 5) = 197.</Sidenote>

#### Multicast across a cluster

In a **cluster**, CTAs on different SMs can share loads. With **`CopyBulkTensorTileG2SMulticastOp`**
one CTA's TMA load writes the same box into the shared memory of every CTA in a mask. In practice
each CTA of the group issues a slice of the box, and every CTA receives all of it. The run used a
cluster of 2 CTAs and an $8 \times 32$ Float32 box (rows 0–7, columns 32–63 of an $8 \times 64$
tensor holding $100r + c$):

```python
atom, t = cpasync.make_tiled_tma_atom(
    cpasync.CopyBulkTensorTileG2SMulticastOp(), g, s_layout, (8, 32),
    num_multicast=2)
rank = cute.arch.block_idx_in_cluster()
tAsA, tAgA = cpasync.tma_partition(atom, rank, cute.make_layout(2), sA_, gT_)
cute.arch.mbarrier_arrive_and_expect_tx(bar, 1024)  # thread 0 of each CTA
cute.copy(atom, tAgA, tAsA, tma_bar_ptr=bar, mcast_mask=Int16(3))
```

`tma_partition` now takes the CTA's rank in the multicast group. CTA $v$'s copy starts at row
$4v$ (the corner prints as `(32,?{div=4})`), so each CTA issues 4 rows. The mask `0b11` sends
each slice to both CTAs, and each CTA's barrier expects the whole 1,024-byte box, because it is
counted as bytes arrive from either CTA. The figures show column 32 of each row in each CTA's
shared memory, first with both CTAs issuing, then with only CTA 0 issuing (and 512 bytes
expected):

<Matrix2D {...T.mcast_both} caption="both CTAs issue: what each CTA (column) received in each box row (row)" />

<Matrix2D {...T.mcast_only0} caption="only CTA 0 issues: rows 4–7 never arrive in either CTA" />

In a real kernel the mask comes from `cpasync.create_tma_multicast_mask(cta_layout_vmnk,
cta_coord_vmnk, mcast_mode)`, or from [`make_layout_image_mask`](#make_layout_image_mask), which
picks the CTAs that share this CTA's row or column of the cluster.<Sidenote>A first attempt
used a 4 × 4 Float32 box, so each CTA's half was 2 rows, 32 bytes. It failed with the device
assertion `SHARED_REMOTE_MISALIGNED_ADDR_128B`, which the driver reported from a routine named
`emulate_tma`. Each CTA's slice must start on a 128-byte boundary in shared memory. I did not
find out whether multicast on sm_120 is emulated in software.</Sidenote>

## MMA

#### `make_mma_atom` and `MmaAtom`

An **MMA atom** is one matrix-multiply instruction. Its properties say how the instruction's
operands are spread over threads: `shape_mnk`, `thr_id`, and `tv_layout_A`, `tv_layout_B`,
`tv_layout_C`, each mapping (thread, value) to a coordinate in that operand. For Ampere's
`mma.sync` with fp16 inputs and fp32 accumulators:

```python
op = cute.nvgpu.warp.MmaF16BF16Op(Float16, Float32, (16, 8, 16))
atom = cute.make_mma_atom(op)
# ThrID 32:1, Shape MNK (16,8,16)
# TV Layout A: ((4,8),(2,2,2)):((32,1),(16,8,128))
# TV Layout C: ((4,8),(2,2)):((32,1),(16,8))
```

Drawing the C layout over the 16×8 accumulator shows the hardware's register assignment:

<Matrix2D {...F.mma_c} caption="m16n8k16 accumulator: register c0–c3 (big) and lane (small)" />

Lane $\ell$ holds `c0` and `c1` at row $\lfloor \ell / 4 \rfloor$, columns $2(\ell \bmod 4)$ and
$2(\ell \bmod 4) + 1$, and `c2`, `c3` eight rows lower. Check lane 5: rows 1 and 9, columns 2
and 3.<Sidenote>The generator script checks all 128 (lane, register) pairs of this C layout,
and all 256 of the A layout, against the fragment formulas for `mma.m16n8k16` in NVIDIA's PTX ISA
documentation (row = groupID or groupID + 8, column = threadID_in_group × 2 + (i & 1)). They
match.</Sidenote> This is why CuTe expresses TV layouts as layouts: the irregular hardware
pattern is just the stride `((32,1),(16,8))`.

#### `make_tiled_mma` and `TiledMma`

**`cute.make_tiled_mma(op_or_atom, atom_layout_mnk=(1,1,1), permutation_mnk=None)`** repeats the
atom over more threads (`atom_layout_mnk`) and optionally permutes which rows and columns each
copy covers (`permutation_mnk`). Its properties:

| Property / method | For 4 `MmaUniversalOp` threads, `atom_layout_mnk = (2,2,1)` |
| --- | --- |
| `size` | 4 threads |
| `thr_layout_vmnk` | `(1,2,2,1):(0,1,2,0)`: (threads per atom, M, N, K) |
| `get_tile_size(0)`, `(1)`, `(2)` | 2, 2, 1 |
| `tv_layout_C_tiled` | `(4,(1,(1,1))):(1,(0,(0,0)))` |
| `partition_shape_C((8, 8))` | `(1, 4, 4)`: each thread's share of an 8×8 C |

With a scalar FMA as the atom, the 2×2 threads tile C, and the tile repeats 4 × 4 times over an
8×8 C:

<Matrix2D {...F.uni_c} caption="8×8 C over a 2×2 tiled MMA: thread (small) and the repeat it is in (big)" />

Each thread's elements are 2 apart in both directions. The tour shows how a
[permutation](/blog/cute-dsl/#make_tiled_mma-partitions-and-gemm) makes them contiguous instead.

#### `get_slice`, `partition_A/B/C`, `make_fragment_A/B/C`

**`mma.get_slice(tid)`** returns a `ThrMma`. Its **`partition_A(sA)`**, **`partition_B(sB)`** and
**`partition_C(gC)`** return the thread's share of each operand, shaped
`(MMA, MMA_M, MMA_K)` for A and `(MMA, MMA_M, MMA_N)` for C. For thread 1 of the tiled MMA above,
`partition_C` of an 8×8 identity tensor is `(1,4,4):(0,2@0,2@1)`: one value per atom, 4 atoms
down with row stride 2, 4 across with column stride 2. **`make_fragment_A/B/C`** then allocate
matching register tensors, here `(1,4,4):(0,1,4)`. **`partition_shape_A/B/C`** give the same
shapes from a shape alone, before any tensor exists.

#### `gemm` and `mma_atom_call`

**`cute.gemm(mma, D, A, B, C)`** computes $D = A B + C$, looping over the modes of the fragments.
It accepts five combinations of operand ranks:

| A | B | C, D |
| --- | --- | --- |
| `(V)` | `(V)` | `(V)` |
| `(M)` | `(N)` | `(M, N)` |
| `(M, K)` | `(N, K)` | `(M, N)` |
| `(V, M)` | `(V, N)` | `(V, M, N)` |
| `(V, M, K)` | `(V, N, K)` | `(V, M, N)` |

B is given as `(N, K)`, so this is $C_{mn} \mathrel{+}= \sum_k A_{mk} B_{nk}$. A 2×3 by 2×3 example
run with `MmaUniversalOp`:

| | |
| --- | --- |
| A (M × K) | `[[1, 3, 5], [2, 4, 6]]` |
| B (N × K) | `[[1, 0, 0], [0, 1, 0]]` |
| C before | all 0.5 |
| C after `gemm(mma, C, A, B, C)` | `[[1.5, 3.5], [2.5, 4.5]]` |

Check $C_{01} = A_{00} B_{10} + A_{01} B_{11} + A_{02} B_{12} + 0.5 = 0 + 3 + 0 + 0.5 = 3.5$.

**`cute.mma_atom_call(atom, D, A, B, C)`** issues a single instruction on one fragment of each.
Block-scaled and sparse MMAs take extra operands as lists, such as `a=[A, SFA]`.

Always pass the same tensor as `C` and `D`, as NVIDIA's examples do. With `MmaUniversalOp` in
4.8.0, both `gemm` and `mma_atom_call` accumulated into `C` and left a separate `D` untouched:
with $A = 2$, $B = 3$, $C = 1$ and $D = -9$, `gemm` left $D = -9$ and set $C = 7$.

#### Tensor-core generations: `mma.sync`, `wgmma`, `tcgen05`

The `mma.sync` atom above is the Ampere instruction: a warp issues it, and A, B and C all live in
registers. Hopper and Blackwell move work off the threads in two steps. `wgmma` is issued by a
**warpgroup** of four warps and reads B, and usually A, straight from shared memory. Blackwell's
`tcgen05.mma` is issued by **one thread**, and it also keeps the accumulator out of the
registers, in **Tensor Memory (TMEM)**. The ops are built the same way:

```python
K = cute.nvgpu.OperandMajorMode.K
wg = warpgroup.MmaF16BF16Op(Float16, Float32, (64, 32, 16),
                            warpgroup.OperandSource.SMEM, K, K)
tc = tcgen05.MmaF16BF16Op(Float16, Float32, (128, 64, 16),
                          tcgen05.CtaGroup.ONE, tcgen05.OperandSource.SMEM, K, K)
```

The DSL refuses to build these ops for the wrong GPU ("expects arch to be sm_90a, but got
sm_120a"). Setting `CUTE_DSL_ARCH=sm_90a` or `sm_100a` lets the atoms be traced and printed on
any machine, but not run. This table is their printout, next to the warp atom:

| | `mma.sync` m16n8k16 | `wgmma` m64n32k16 | `tcgen05` m128n64k16 |
| --- | --- | --- | --- |
| Issued by | a warp, synchronously | a warpgroup, asynchronously | one thread, asynchronously |
| `ThrID` | `32:1` | `128:1` | `1:0` |
| A from | registers | shared memory (or registers) | shared memory (or TMEM) |
| TV layout A | `((4,8),(2,2,2)):((32,1),(16,8,128))` | `(128,(64,16)):(0,(1,64))` | `(1,(128,16)):(128,(1,128))` |
| B from | registers | shared memory | shared memory |
| Accumulator in | registers, 4 per thread | registers, $N / 2$ per thread | TMEM, none in registers |
| TV layout C | `((4,8),(2,2)):((32,1),(16,8))` | `((4,8,4),(2,2,4)):((128,1,16),(64,8,512))` | `(1,(128,64)):(128,(1,128))` |
| Completion | when the instruction returns | `warpgroup.commit_group()`, `wait_group(n)` | `tcgen05.commit` to an mbarrier |

Two layouts in the table stand out. The wgmma A layout has thread stride 0, so all 128 threads
map to the whole of A: no thread owns a piece, because A is read from shared memory through a
descriptor. The tcgen05 layouts have a single thread, which owns the whole tile. The wgmma C layout
is the only one still spread over threads. Drawn over the $64 \times 32$ accumulator in
$8 \times 8$ blocks:

<Matrix2D {...T.wgmma_c} caption="wgmma m64n32k16 accumulator in 8×8 blocks: owning warp (small) and the thread's value indices there (big)" />

Warp $w$ owns rows $16w$ to $16w + 15$, and within its 16 rows the pattern is the m16n8
accumulator from the figure above, repeated every 8 columns (values 4–7 at columns 8–15, and so
on). Check one: thread 37 is lane 5 of warp 1, and its value 6 lands at row $16 + 1 + 8 = 25$,
column $2 + 8 = 10$.<Sidenote>The generator evaluates the traced C layout for all 2,048

## Structs and unions

Shared memory is often one block holding several buffers and barriers. **`@cute.struct`** describes
such a block as a C struct, and an allocator places it:

```python
@cute.struct
class Complex:
    re: cutlass.Float32
    im: cutlass.Float32

@cute.struct
class Storage:
    flag: cutlass.Int8
    bars: cute.struct.MemRange[cutlass.Int64, 2]      # an array of 2
    z: Complex                                         # a nested struct
    buf: cute.struct.Align[                            # aligned to 32 bytes
        cute.struct.MemRange[cutlass.Float16, 8], 32]

s = cutlass.memory.SmemAllocator().allocate(Storage)
s.z.re.ptr                                  # pointer to one field
s.buf.get_tensor(cute.make_layout((2, 4)))  # f16 smem tensor (2,4):(1,2)
```

Fields follow C rules: each starts at a multiple of its alignment, and the size rounds up to the
largest alignment. The offsets measured on the GPU:

<Matrix2D {...F.struct} caption="Storage, 64 bytes in rows of 8: byte offset (big) and field (small)" />

`flag` takes byte 0, then 7 bytes of padding, because `bars` holds 8-byte integers. `z` follows
at 24. `buf` would fit at 32 anyway, and the struct's size is rounded up from 48 to 64 because
`Align[..., 32]` makes the whole struct 32-byte aligned (`Storage.__sizeof__()` is 64,
`__alignof__()` is 32). `MemRange` fields give `data_ptr()`, `get_tensor(layout)` and indexing.

**`@cute.union`** puts every member at offset 0. Storing `1.0` through `as_float` and reading
`as_int` gives 1065353216, the bits of 1.0; the size is that of the largest member.

#### `fastmath`, `approx`, `ftz` and `rounding`

Most functions take flags that trade accuracy for speed. Compiling them and reading the PTX shows
what each one does:

| Call | PTX |
| --- | --- |
| `sqrt(x)` / `sqrt(x, approx=True)` | `sqrt.rn.f32` / `sqrt.approx.f32` |
| `div(x, y)` / `div(x, y, approx=True)` | `div.rn.f32` / `div.approx.f32` |
| `sin(x)` / `sin(x, approx=True)` | about 120 lines of range reduction and polynomial / one `sin.approx.f32` |
| `exp2(x)` / `exp2(x, approx=True)` | `ex2.approx.f32` for both: PTX has no other f32 form |
| `exp2(x, approx=True, ftz=True)` | `ex2.approx.ftz.f32` |
| `exp(x)` / `exp(x, fastmath=True)` | a range-reduction sequence of FMAs around `ex2.approx.ftz` / one multiply by $\log_2 e$, then `ex2.approx.ftz` |

**`ftz`** flushes subnormal inputs and outputs to zero. **`rounding`** takes a `RoundingMode`:
`NEAREST_EVEN` (`rn`), `ZERO` (`rz`), `UP` (`rp`) or `DOWN` (`rm`). For $1/3$, the two nearest
floats are 0.3333333135 and 0.3333333433:

| `div(1, 3, rounding=...)` | `ZERO` | `NEAREST_EVEN` | `UP` | `DOWN` |
| --- | ---: | ---: | ---: | ---: |
| $1/3$ | 0.3333333135 | 0.3333333433 | 0.3333333433 | 0.3333333135 |
| $-1/3$ | −0.3333333135 | −0.3333333433 | −0.3333333135 | −0.3333333433 |

#### Rounding functions

The five rounding functions differ only on ties and on the sign of the direction:

| $x$ | −2.5 | −1.5 | −0.5 | 0.5 | 1.5 | 2.5 | 2.7 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `floor` | −3 | −2 | −1 | 0 | 1 | 2 | 2 |
| `ceil` | −2 | −1 | −0 | 1 | 2 | 3 | 3 |
| `trunc` | −2 | −1 | −0 | 0 | 1 | 2 | 2 |
| `round` (ties away from 0) | −3 | −2 | −1 | 1 | 2 | 3 | 3 |
| `roundeven` (ties to even) | −2 | −2 | −0 | 0 | 2 | 2 | 3 |

`roundeven` is the IEEE default and has no bias on average; `round` is what C's `roundf` does.

#### NaN handling, `clamp`, `expm1` and `log1p`

- **`min` and `max`** ignore a NaN by default (`min(NaN, 1)` is 1) and return NaN with
  `propagate_nan=True`. Pick deliberately: a max-reduction for softmax should usually propagate,
  so a NaN shows up instead of being hidden.
- **`clamp(x, lo, hi)`** is `max(lo, min(x, hi))`: `clamp(5, 0, 3)` is 3 and `clamp(-1, 0, 3)` is 0.
- **`expm1(x)`** and **`log1p(x)`** keep precision near 0. For $x = 10^{-7}$, `exp(x) - 1` gives
  $1.192 \times 10^{-7}$, off by 19%, because $1 + 10^{-7}$ rounds to the float just above 1;
  `expm1(x)` gives $1.000 \times 10^{-7}$. `log(1 + x)` and `log1p(x)` show the same difference.
- **`sincos(x)`** returns both at once: `sincos(0.5)` is `(0.479426, 0.877583)`.
- **`fpowi`** (float to an integer power) crashed the compiler in my test on 4.8.0; `ipowi(3, 4)`
  gives 81.

## Fast integer division

Integer division is slow on a GPU: there is no divide instruction, so `a // b` with a run-time `b`
compiles to a long sequence. Kernels divide constantly, for example to turn a linear tile index
into `(m, n)` coordinates. **`cute.fast_divmod_create_divisor_v2(b)`** precomputes a magic
multiplier and shift for `b` once on the host, and `divmod`, `//` and `%` with the result then
compile to a multiply-high and a shift.

```python
@cute.jit
def host(n: cutlass.Int32):
    d = cute.fast_divmod_create_divisor_v2(n)      # once, on the host
    kernel(d).launch(...)

@cute.kernel
def kernel(d: cute.FastDivmodDivisorV2):
    q, r = divmod(linear_idx, d)                   # cheap, in every thread
```

With $b = 6$, the kernel printed `divmod(22, 6) = (3, 4)` and `divmod(23, 6) = (3, 5)`. Use the
`v2` versions: the original `FastDivmodDivisor` cannot read `.divisor` back inside a kernel, and
the API page marks it as deprecated.

## Compilation, debugging and FFI

The tour covers [`@cute.jit`, `@cute.kernel` and `cute.compile`](/blog/cute-dsl/#a-first-kernel)
and [static versus dynamic values](/blog/cute-dsl/#tracing-static-and-dynamic-values). The
remaining functions in this group:

| Function | What it does |
| --- | --- |
| `cute.printf(fmt, *args)` | Prints from the GPU. Accepts `{}` placeholders or C formats: `"n=%d f=%.2f"` printed `n=12 f=1.23` |
| `cute.print_tensor(t)` | Prints a tensor's pointer, layout and values (registers or memory), from the GPU |
| `cute.pretty_str(x)` | The compact string `print` uses, such as `((2,3),4)` |
| `cute.assume(x, divby=8)` | Promises the compiler that `x` is a multiple of 8; it prints as `?{div=8}` |
| `cute.get_divisibility(x)` | What the compiler knows: 1 for an unknown `Int32`, 8 after `assume`, 32 for `assume(n, divby=8) * 4` |
| `cute.compile(f, *args, options="--keep-ptx")` | Compiles once; options can keep the PTX, SASS or CUBIN for inspection |
| `cute.register_jit_arg_adapter` | Registers an adapter for a custom argument type of `@cute.jit` (no docstring; not run here) |
| `cute.ffi`, `@cute.extern`, `BitCode` | Call external device functions, optionally linking an LLVM bitcode file (not run here) |

`assume` matters for vectorization. A dynamic size prints as `?`, and the compiler must assume the
worst; `?{div=8}` lets it use 8-wide loads. Sizes that come out of layout arithmetic carry their
divisibility automatically: `size(make_layout((4, n)))` prints `?{div=4}`.

| Item | The page says | 4.8.0 does |

## Summary

- Shapes, strides and coordinates are nested integer tuples. Functions such as `flatten`,
  `group_modes`, `find`, `product_each` and `shape_div` work on the nesting alone, and a mode path
  like `(2,1,0)` addresses any node.
- A layout's domain can be read as natural coordinates or 1-D indices, converted
  colexicographically by `idx2crd` and `crd2idx`. `slice_` fixes modes and `dice` drops them.
- Strides can be scaled bases (`2@0`) that map coordinates to coordinates; zero strides
  broadcast, and `filter_zeros`, `filter` and `nullspace` deal with them. Swizzles permute offsets
  by XOR-ing bits, and live in composed layouts.
- Tensors pair a pointer (with type, memory space and alignment) or a coordinate with a layout;
  `load()` turns one into a `TensorSSA` register value with NumPy-like operations.
- A TMA copy is one instruction per box. The TMA tensor holds coordinates, an mbarrier counts the
  box's bytes, edge boxes are zero-filled on load, and a swizzled shared layout must be read
  through `get_tensor(outer, swizzle=inner)`. On sm_120, stores clip in 16-byte chunks.
- Copies and MMAs are atoms tiled over threads by TV layouts, and `gemm` loops over fragments.
  The TV layouts show tensor cores moving from the warp (`mma.sync`, all in registers) to the
  warpgroup (`wgmma`, A and B in shared memory) to one thread (`tcgen05`, accumulator in TMEM).
  Check the documentation's examples by running them: several are wrong in 4.8.0.
