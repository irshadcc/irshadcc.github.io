## Background

JAX looks like NumPy. You write `jnp.tanh(x @ w)`, and you get an array back. But the same
function can also be compiled with `jax.jit`, differentiated with `jax.grad` and vectorized with
`jax.vmap`, in any combination, and it runs on a CPU, a GPU or a TPU. None of this needs a
special language: the function is plain Python.

The trick is that JAX never reads your Python. It *runs* it, once, with stand-in objects called
**tracers** in place of arrays. Every operation on a tracer is recorded, and the record is a
small, typed program called a **jaxpr**. Compiling means translating the jaxpr to
**StableHLO**, the input language of the **XLA** compiler. Differentiating means running the
function with a different kind of tracer, one that carries a derivative along with each value.
Understanding this explains most of JAX's rules: why a jitted function cannot branch on an array's
value, why `print` inside it runs only once, why a new input shape triggers a recompile, and why
`grad` works on any function built from JAX operations.

This post follows one small loss function through JAX's source, in order:

1. **The running example**, line by line, and the **pipeline** from Python to an executable.
2. **Primitives and traces**: the two ideas every other part is built on.
3. **Tracing**: how `DynamicJaxprTrace` records a jaxpr, one primitive at a time, and what it
   cannot see.
4. **From jaxpr to XLA**: the `jit` call path, lowering rules, StableHLO line by line, what XLA
   does with it, and caching.
5. **Automatic differentiation**: forward mode with `JVPTrace`, then reverse mode as
   **linearize** followed by **transpose**, with the real values at every step, and how `grad`
   composes with `jit`.

If you know PyTorch's compiler stack, the closest parallels are [Torch FX](/blog/torch-fx-graph/)
(graph capture) and [AOTAutograd](/blog/aot-autograd/) (tracing the backward ahead of time); the
[PyTorch dispatcher](/blog/pytorch-dispatcher/) plays a role similar to JAX's traces.

Every jaxpr, IR listing and number below was produced by running JAX 0.11.2 on a CPU, and every
source link points at the commit that release was built from.<Sidenote>`jax.__version__ ==

## The running example

The whole post uses one function: a one-layer model with a squared-error loss.

```python
import jax
import jax.numpy as jnp

def predict(w, x):
    return jnp.tanh(x @ w)

def loss(w, x, y):
    err = predict(w, x) - y
    return jnp.mean(err ** 2)

x = jnp.array([[1., 2.], [3., 4.], [5., 6.]])   # 3 examples, 2 features
w = jnp.array([0.1, -0.2])                       # 2 weights
y = jnp.array([0., 1., 0.])                      # 3 targets

grad_fn = jax.jit(jax.grad(loss))
print(loss(w, x, y))      # 0.8626
print(grad_fn(w, x, y))   # [-3.7562 -4.9563]
```

Line by line:

- `import jax.numpy as jnp` gives the NumPy-like API. Every `jnp` function is a thin wrapper
  that ends in one or more **primitives** from `jax.lax`, the operations JAX actually knows.
- `predict` multiplies the $3 \times 2$ input matrix by the weight vector and squashes each of the
  three results with $\tanh$. In math: $e = \tanh(Xw)$.
- `loss` subtracts the targets and averages the squared errors:
  $L(w) = \frac{1}{3}\sum_{k} (e_k - y_k)^2$.
- `x`, `w`, `y` are `jax.Array`s of dtype float32 (JAX's default).
- `jax.grad(loss)` builds a new function that returns $\nabla_w L$, the gradient with respect to
  the first argument. Nothing is computed yet.
- `jax.jit(...)` wraps that function so the first call traces it, compiles it with XLA and caches
  the executable; later calls with the same shapes run the cached executable.

The numbers, computed by hand so we can check JAX later: $Xw = [-0.3, -0.5, -0.7]$ (first entry
$1 \cdot 0.1 + 2 \cdot (-0.2) = -0.3$), $e = \tanh(Xw) = [-0.2913, -0.4621, -0.6044]$, the error
$e - y = [-0.2913, -1.4621, -0.6044]$, the squares $[0.0849, 2.1378, 0.3653]$, and their mean
$L = 0.8626$. The gradient is

$$
\nabla_w L = \frac{2}{3} X^\top \big[(e - y) \odot (1 - e^2)\big] = [-3.7562,\ -4.9563],
$$

where $\odot$ is elementwise multiplication and $1 - e^2$ is the derivative of $\tanh$. By the
end of the post we will have watched JAX derive exactly this formula, one primitive at a time.

Two things stand out. First, there is only one way in: **tracing**. Python runs once, and from
then on JAX works on the jaxpr. Second, transformations like `grad` are not passes over the
jaxpr after the fact. They are traces too, stacked on top of the tracing that builds the jaxpr, so
the jaxpr that comes out of tracing `grad(loss)` already contains the backward pass. The next
section introduces the two concepts that make this work.

## Primitives and traces

### Primitives

A **primitive** is an operation JAX knows how to handle in every context: `dot_general`,
`tanh`, `sub`, `integer_pow`, `reduce_sum`, `div`, 279 of them in JAX 0.11.2. It is an instance
of [`core.Primitive`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/core.py#L666),
which is little more than a name. What makes it useful is the set of **rules** registered for
it, one per thing JAX might want to do with it:

| Rule | What it answers | Registered with | Used by |
| --- | --- | --- | --- |
| impl | compute the result on real arrays | `prim.def_impl` | eager evaluation |
| abstract eval | output shape and dtype, from input shapes and dtypes | `prim.def_abstract_eval` | tracing |
| JVP | derivative along a tangent | `ad.defjvp`, `ad.primitive_jvps` | `jvp`, `grad` |
| transpose | the adjoint of a linear primitive | `ad.primitive_transposes` | `grad` |
| batching | the same op on a batch | `batching.primitive_batchers` | `vmap` |
| lowering | the StableHLO ops that implement it | `mlir.register_lowering` | `jit` |

For `tanh`, three of these sit next to each other in
[`lax.py`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/lax/lax.py#L4665)
(the `accuracy=HIGHEST` branch of the JVP is left out):

```python
tanh_p = standard_unop(_float | _complex, 'tanh')
ad.defjvp2(tanh_p, lambda g, ans, x, accuracy: mul(g, one_minus_square(ans)))
mlir.register_lowering(tanh_p, partial(_nary_lower_hlo, hlo.tanh))
```

- `standard_unop` creates the primitive and gives it an abstract-eval rule for elementwise ops:
  the output has the input's shape and dtype, and the dtype must be floating or complex.
- `defjvp2` registers the derivative. The `2` means the rule also receives the output `ans`, so
  the derivative $\frac{d}{dx}\tanh x = 1 - \tanh^2 x$ reuses it instead of computing $\tanh$
  again. `g` is the incoming tangent.
- `register_lowering` says: to compile `tanh`, emit `stablehlo.tanh`.

There is no Python-level "graph" anywhere; a JAX program is just a sequence of primitive
applications. Everything else in JAX is a different way of *interpreting* those applications.

### Tracers and traces

A **trace** is an interpreter for primitives. It is an object with a method
`process_primitive(primitive, inputs, params)` that decides what applying a primitive means. A
**tracer** is a value that belongs to a trace: it has an **abstract value** (`aval`, a shape and
dtype such as `f32[3]`) and a pointer to its trace. Tracers implement every array operator
(`+`, `@`, `**`, indexing) and every array method, so Python code cannot tell them from arrays.

JAX keeps one **current trace** in a thread-local context, `trace_ctx`. When no transformation
is active, it is the `EvalTrace`, whose rule is "call `impl`". Each transformation pushes its
own trace for the duration of a call:

| Trace | Tracer | Created by | `process_primitive` does |
| --- | --- | --- | --- |
| [`EvalTrace`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/core.py#L1304) | none (real arrays) | default | run the primitive's `impl` |
| [`DynamicJaxprTrace`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/partial_eval.py#L1623) | `DynamicJaxprTracer` | `jit`, `make_jaxpr` | append an equation to a jaxpr |
| [`JVPTrace`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L520) | `JVPTracer` (primal, tangent) | `jvp`, `jacfwd` | apply the JVP rule |
| [`LinearizeTrace`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L670) | `LinearizeTracer` | `grad`, `vjp`, `linearize` | compute primals now, record tangents |
| `BatchTrace` | `BatchTracer` | `vmap` | apply the batching rule |

You can see the tracer types by printing an argument inside each transformation:

```python
def show(x):
    print(type(x).__name__, x)
    return jnp.sin(x)

jax.jit(show)(1.0)            # DynamicJaxprTracer JitTracer(~float32[])
jax.grad(show)(1.0)           # LinearizeTracer GradTracer(primal=1.0, typeof(tangent)=f32[])
jax.jit(jax.grad(show))(1.0)  # LinearizeTracer GradTracer(primal=JitTracer(~float32[]), ...)
jax.vmap(show)(jnp.ones(3))   # BatchTracer VmapTracer(aval=float32[], batched=float32[3])
```

The third line shows how transformations compose: under `jit(grad(...))` the gradient tracer's
primal is itself a jit tracer. Each trace keeps a `parent_trace`, and when its rule needs to do
arithmetic, it binds primitives on the parent. The `~` marks a **weak type**: a Python scalar
whose dtype yields to whatever it is combined with.

### How a primitive reaches its trace

Every primitive application goes through
[`Primitive.bind`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/core.py#L686).
Here it is with the sharding checks removed:

```python
def bind(self, *args, **params):
    canonical_args = []
    avals = []
    for i, arg in enumerate(args):
        c_arg = dtypes.canonicalize_value(arg)
        aval = typeof(c_arg)
        ...
        canonical_args.append(c_arg)
        avals.append(aval)
    args = canonical_args
    prev_trace = trace_ctx.trace
    trace_ctx.set_trace(None)
    try:
        return self.bind_with_trace(prev_trace, args, avals, params)
    finally:
        trace_ctx.set_trace(prev_trace)

def bind_with_trace(self, trace, args, avals, params, /):
    ...
    return trace.process_primitive(self, args, params)
```

- The loop turns each argument into a JAX value (`canonicalize_value` makes a Python `3.0` a
  float32 scalar) and records its abstract value with `typeof`. For a tracer, `typeof` returns its
  `aval`.
- `prev_trace = trace_ctx.trace` reads the current trace. Note that the trace is chosen by
  *context*, not by looking at the arguments.
- `trace_ctx.set_trace(None)` clears it while the trace works. A rule that wants to bind more
  primitives must therefore say on which trace, with `set_current_trace(self.parent_trace)`.
  This is what keeps nested transformations from accidentally processing their own work.
- `bind_with_trace` hands over to `trace.process_primitive`, which is where each trace does its
  job. The `finally` restores the previous trace.

The simplest trace,
[`EvalTrace`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/core.py#L1310),
just runs the implementation:

```python
def process_primitive(self, primitive, args, params, /):
    with set_current_trace(self):
        ...
        args = map(full_lower, args)
        check_eval_args(args)
        return primitive.impl(*args, **params)
```

Even "eager" JAX compiles. Most `jnp` functions are themselves decorated with `jax.jit`, so
calling `jnp.tanh` on a real array traces and compiles a tiny XLA program the first time and
reuses it afterwards.<Sidenote>For example
[`jnp.matmul`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/numpy/tensor_contractions.py#L132)
and `jnp.tanh` are wrapped in `jit(..., inline=Inline.JAX_EARLY)`. When they are called *inside*
another trace, `inline=JAX_EARLY` makes
[`pjit_staging_rule`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L1250)
paste their equations into the outer jaxpr instead of leaving a nested `jit` call.</Sidenote>

## Tracing into a jaxpr

### Reading the jaxpr

`jax.make_jaxpr(loss)(w, x, y)` traces `loss` and prints what it recorded:

```text
{ lambda ; a:f32[2] b:f32[3,2] c:f32[3]. let
    d:f32[3] = dot_general[dimension_numbers=(([1], [0]), ([], [])) preferred_element_type=float32] b a
    e:f32[3] = tanh d
    f:f32[3] = sub e c
    g:f32[3] = integer_pow[y=2] f
    h:f32[] = reduce_sum[axes=(0,) out_sharding=None] g
    i:f32[] = div h 3.0:f32[]
  in (i,) }
```

Line by line:

- `lambda ; a:f32[2] b:f32[3,2] c:f32[3].` declares the inputs. The names are generated in order,
  so `a` is `w`, `b` is `x` and `c` is `y`. Each has a type: dtype `f32` and a shape. Variables
  before the `;` would be **constants** captured from the enclosing Python scope; there are none
  here.
- `d = dot_general[...] b a` is `x @ w`. Parameters go in brackets: contract dimension 1 of `b`
  with dimension 0 of `a`, with no batch dimensions. The result `f32[3]` is known from the shapes
  alone.
- `e = tanh d` is `jnp.tanh`. The call to `predict` left no trace: Python functions disappear,
  only the primitives they bound remain.
- `f = sub e c` is `predict(w, x) - y`. The Python name `err` is gone too.
- `g = integer_pow[y=2] f` is `err ** 2`. The exponent is a parameter, not an input.
- `h = reduce_sum[axes=(0,)] g` and `i = div h 3.0` are `jnp.mean`, a sum over axis 0 then a
  division by a **literal** constant.
- `in (i,)` lists the outputs.

A jaxpr is in **A-normal form**: every intermediate has a name and every equation applies one
primitive to variables or literals. It has no loops, no branches and no mutation; control flow is
expressed with primitives like `cond`, `while` and `scan` whose parameters hold sub-jaxprs.

### Inside DynamicJaxprTrace

`jit` and `make_jaxpr` both end up in
[`trace_to_jaxpr_nocache`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/partial_eval.py#L2048).
Its core, simplified:

```python
parent_trace = core.trace_ctx.trace
trace = DynamicJaxprTrace(debug_info, parent_trace=parent_trace)
in_tracers = in_avals.map(partial(trace.new_arg, source_info=source_info))
with core.set_current_trace(trace):
    args, kwargs = in_tracers.unflatten()
    ans_pytree = fun(*args, **kwargs)
...
jaxpr, out_avals = trace.to_jaxpr(...)
```

- A fresh `DynamicJaxprTrace` is created; it owns a `JaxprStackFrame` that will hold the
  equations.
- `new_arg` is called once per input aval. It makes a new `Var` (`a`, `b`, `c`), wraps it in a
  `DynamicJaxprTracer`, and appends the var to the frame's input list.
- `set_current_trace(trace)` makes every `bind` inside `fun` go to this trace.
- `fun` runs with tracers instead of arrays. Its return value is converted back into variables,
  and the frame becomes a `Jaxpr`.

The method that records an equation is
[`default_process_primitive`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/partial_eval.py#L1750).
Without the special cases:

```python
def default_process_primitive(self, primitive, tracers, params, source_info=None):
    avals = [t.aval for t in tracers]
    out_avals, effs = _cached_abstract_eval(primitive, *avals, **params)
    out_avals = [out_avals] if not primitive.multiple_results else out_avals
    maybe_consts_out = try_constant_folding(primitive, tracers, params, out_avals)
    if maybe_consts_out is not None:
        out_tracers = [self.new_const(c, ...) for c, aval in zip(maybe_consts_out, out_avals)]
    else:
        eqn, out_tracers = self.make_eqn(tracers, out_avals, primitive, params, effs, ...)
    ...
    if eqn is not None:
        self.frame.add_eqn(eqn)
    return out_tracers if primitive.multiple_results else out_tracers.pop()
```

- `avals` are the input tracers' types, for example `f32[3,2]` and `f32[2]`.
- `_cached_abstract_eval` runs the primitive's shape rule. This is the only "computation" that
  happens while tracing, and it is memoized, so tracing the same op on the same shapes twice is
  cheap.
- `try_constant_folding` handles the rare case where the result is known without any input data.
- `make_eqn` creates one new `Var` per output (`d`), a `TracingEqn` that links the input tracers
  to those vars, and output tracers that point at the new vars.
- `add_eqn` appends the equation to the frame. The returned tracer goes back to Python, which
  uses it as the result of `x @ w`.

### What tracing cannot see

Because Python only runs with tracers, anything that needs an actual *value* fails or behaves
differently:

```python
def g(x):
    if x > 0:          # needs a bool, but x is a tracer
        return x
    return -x

jax.jit(g)(1.0)        # TracerBoolConversionError: Attempted boolean conversion
                       # of traced array with shape bool[].
jax.grad(g)(-2.0)      # -1.0: works, grad's tracer still holds the real primal
```

`x > 0` produces a tracer of type `bool[]`, and Python's `if` calls `bool()` on it, which a jit
tracer cannot answer. `grad` alone works because a `LinearizeTracer` carries its real primal
value, so it can be converted. Under `jit` you either mark the argument static
(`static_argnums`, which makes its value part of the cache key), or express the branch as data
with `jnp.where` or `jax.lax.cond`.

Side effects in Python also run only while tracing. A `print` inside a jitted function shows a
tracer, once per compilation:

```python
@jax.jit
def f(x):
    print("tracing f with", x)
    return jnp.tanh(x) * 2

f(jnp.ones(3))                   # tracing f with JitTracer(float32[3])
f(jnp.zeros(3))                  # (nothing: same shape and dtype, cached)
f(jnp.ones(4))                   # tracing f with JitTracer(float32[4])
f(jnp.ones(3, dtype=jnp.int32))  # tracing f with JitTracer(int32[3])
```

The jaxpr depends only on the abstract values, so the cache is keyed by them. New values with
the same shape and dtype reuse the compiled code; a new shape or dtype traces and compiles again.
After these four calls `f._cache_size()` returns 3.

## From jaxpr to XLA

### The jit call path

`jax.jit(fun)` returns a C++ object built by
[`_cpp_pjit`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L255).
On every call, C++ computes a **signature** from the arguments (pytree structure, shapes, dtypes,
weak types, shardings and the values of static arguments) and looks it up. On a hit it calls the
cached executable directly; Python is not involved at all. On a miss it calls back into Python's
`cache_miss`, which does the work in this order:

| Step | Function | What it does |
| --- | --- | --- |
| 1 | [`_infer_params`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L629) | flatten arguments, compute avals, look up a cached jaxpr |
| 2 | [`_trace_for_jit`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L485) | trace to a jaxpr with `pe.trace_to_jaxpr`, resolve shardings and donation |
| 3 | [`_run_python_pjit`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L133) | at top level, call the implementation of the `jit` primitive directly |
| 4 | [`_pjit_call_impl_python`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L1113) | lower, compile, then run the executable |
| 5 | [`_pjit_lower`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L1224) → `lower_sharding_computation` | build the StableHLO module (cached per jaxpr) |
| 6 | [`lower_jaxpr_to_module`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/mlir.py#L1374) | create the MLIR module and its `main` function |
| 7 | [`compile_or_get_cached`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/compiler.py#L429) | check the persistent compilation cache |
| 8 | [`backend_compile_and_load`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/compiler.py#L335) | `backend.compile_and_load(module, ...)`: XLA compiles through PJRT |

After the first call, `cache_miss` returns "fast-path data" so that C++ can handle the next call
with the same signature by itself.

Inside a trace (for example `jit` inside `grad`), step 3 instead binds the
[`jit` primitive](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L876),
whose parameters hold the inner jaxpr. That is why `make_jaxpr(jax.jit(f))` shows an equation
`jit[name=f jaxpr=...]`, and why transformations can see into jitted functions: `jit` is just
another primitive, with its own JVP, transpose, batching and lowering rules.

The same stages are exposed as a public API, which is how the listings below were produced:

```python
traced   = jax.jit(loss).trace(w, x, y)   # Traced:   holds the jaxpr
lowered  = traced.lower()                 # Lowered:  holds the StableHLO module
compiled = lowered.compile()              # Compiled: holds the XLA executable
print(lowered.as_text())                  # StableHLO
print(compiled.as_text())                 # optimized HLO
```

### Lowering rules

Lowering walks the jaxpr once, in order, and asks each primitive for its StableHLO.
[`jaxpr_subcomp`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/mlir.py#L2191)
keeps an environment from jaxpr variables to MLIR values:

- the jaxpr's inputs are bound to the function's block arguments `%arg0`, `%arg1`, `%arg2`;
- for each equation it reads the MLIR values of the inputs, finds the rule registered with
  [`register_lowering`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/mlir.py#L1050)
  (a platform-specific rule wins over the default), calls it, and binds the outputs;
- literals become `stablehlo.constant` ops.

A rule receives a context with the input and output avals and returns MLIR values. For
`integer_pow`
([source](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/lax/lax.py#L5043)):

```python
def _integer_pow_lowering(ctx, x, *, y):
    if y == 1:
        out = x
    elif y == 2:
        out = hlo.multiply(x, x)
    elif y == 3:
        out = hlo.multiply(hlo.multiply(x, x), x)
    ...
    aval_out, = ctx.avals_out
    return [mlir.lower_with_sharding_in_types(ctx, out, aval_out)]
```

Because `y` is a parameter, the rule chooses the code at compile time: our `err ** 2` becomes a
single multiply.

The StableHLO module, line by line:

- `module @jit_loss` is named after the function. `mhlo.num_partitions = 1` and
  `num_replicas = 1` say it runs on one device.
- `func.func public @main(%arg0: tensor<2xf32>, %arg1: tensor<3x2xf32>, %arg2: tensor<3xf32>)`
  is `lambda ; a b c` with MLIR tensor types.
- `stablehlo.dot_general %arg1, %arg0, contracting_dims = [1] x [0]` is equation `d`, with the
  same dimension numbers.
- `stablehlo.tanh` and `stablehlo.subtract` are `e` and `f`, one op each.
- `stablehlo.multiply %2, %2` is `integer_pow[y=2]`, from the rule above.
- `stablehlo.reduce(%3 init: %cst) applies stablehlo.add across dimensions = [0]` is
  `reduce_sum`: a reduction with initial value 0.0 and `add` as the combiner.
- `stablehlo.divide %4, %cst_0` is the division by the constant 3.0, and `return %5` is
  `in (i,)`.

The mapping is one-to-one because JAX does almost no optimization itself; that is XLA's job.
StableHLO is a versioned, portable dialect, so the same module can be compiled for a CPU, a GPU
or a TPU, or saved with `jax.export` and loaded elsewhere.

XLA's output (the third stage) is already very different. On the CPU, `dot` stays a separate
instruction, and everything after it (tanh, subtract, square, sum and
divide) is **fused** into one loop, `%fused_computation`, so the three intermediate vectors never
reach memory. The division by 3 has become a multiplication by `0.333333343`. The `bitcast`s
reshape `w` to a $2 \times 1$ matrix for free, because a bitcast only reinterprets the layout.

## Automatic differentiation

### Derivatives as linear maps

For a function $f: \mathbb{R}^n \to \mathbb{R}^m$, the derivative at a point $w$ is the
**Jacobian** $J \in \mathbb{R}^{m \times n}$, a linear map. JAX never builds $J$. It computes
products with it, in two directions:

- a **Jacobian-vector product** (JVP), $J t$: push a **tangent** $t \in \mathbb{R}^n$ (a direction
  in input space) forward to the output. One JVP gives one column of $J$.
- a **vector-Jacobian product** (VJP), $u^\top J$: pull a **cotangent** $u \in \mathbb{R}^m$ (a
  weighting of the outputs) back to the inputs. One VJP gives one row of $J$.

Our loss has $n = 2$ inputs and $m = 1$ output, so $J$ is a $1 \times 2$ row: the gradient. A
single VJP with $u = 1$ gives all of it. With forward mode we would need one JVP per input
weight, so $n$ passes; that is why training uses reverse mode.

JAX implements forward mode directly, as a trace. It then gets reverse mode from forward mode in
two more steps: **linearize** (separate the linear part of the JVP from the rest) and
**transpose** (run that linear part backwards). This design means each primitive needs only a
JVP rule, plus a transpose rule for the few primitives that are linear.

### Forward mode: JVPTrace

`jax.jvp(f, (w,), (t,))` evaluates $f(w)$ and $J t$ together. A
[`JVPTracer`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L619)
holds a `primal` (the value) and a `tangent` (its derivative along $t$). Its trace's
[`process_primitive`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L543)
is short:

```python
def process_primitive(self, primitive, tracers, params, /):
    primals_in, tangents_in = unzip2(map(self.to_primal_tangent_pair, tracers))
    if all(type(t) is Zero for t in tangents_in) and ...:
        return primitive.bind_with_trace(self.parent_trace, primals_in, avals, params)
    jvp = primitive_jvps.get(primitive)
    if not jvp:
        raise NotImplementedError(f"Differentiation rule for '{primitive}' not implemented")
    with core.set_current_trace(self.parent_trace):
        primal_out, tangent_out = jvp(primals_in, tangents_in, **params)
    ...
    return maybe_jvp_tracer(self, primal_out, tangent_out)
```

- `to_primal_tangent_pair` unpacks each input. A value that is not one of this trace's tracers
  (like `x` or `y`, closed over from outside) gets a **symbolic zero** tangent, an object of type
  `Zero` that stands for "all zeros" without allocating anything.
- If every tangent is zero, the output's tangent is zero too, so the primitive is simply bound on
  the parent trace: no derivative work at all.
- Otherwise the JVP rule is looked up in `primitive_jvps` and run **on the parent trace**. The
  rule binds ordinary primitives (`tanh`, `mul`, ...) which the parent evaluates, or records if
  the parent is a `DynamicJaxprTrace`.
- `maybe_jvp_tracer` wraps the result in a new `JVPTracer`, unless the tangent came out as a
  symbolic zero.

Most rules are written with
[`defjvp`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L964),
which takes one function per input and sums their contributions:

```python
def standard_jvp(jvprules, primitive, primals, tangents, **params):
    val_out = primitive.bind(*primals, **params)
    tangents_out = [rule(t, *primals, **params) for rule, t in zip(jvprules, tangents)
                    if rule is not None and type(t) is not Zero]
    return val_out, functools.reduce(add_tangents, tangents_out, p2tz(val_out))
```

This is the chain rule, one primitive at a time: the output tangent is the sum, over inputs with
non-zero tangents, of (partial derivative) times (input tangent). For `mul_p` the two rules are
`xdot * y` and `x * ydot`; for `div_p` they are `g / y` and `-g * x / y**2`.

Below, `jax.jvp(loss_of_w, (w,), (t,))` runs with $t = [1, 0]$, the direction of the first
weight. The top listing is the loss jaxpr being evaluated; the bottom is the jaxpr of the JVP,
which you get by tracing it with `make_jaxpr`. Each primitive of the loss turns into one to three
equations.

<JaxprSteps data={jvpSteps} title="jax.jvp(loss, (w,), ([1, 0],)): primal and tangent side by side" />

The tangent of the loss, $-3.7562$, equals the first entry of the gradient: the JVP along
$[1, 0]$ is $\partial L / \partial w_0$. To get $\partial L / \partial w_1$ we would need a

### Reverse mode: linearize, then transpose

Look at the JVP jaxpr again. Its equations split into two kinds:

- equations that use only primals (`e = dot a c`, `g = tanh e`, `h = one_minus_square g`,
  `j = sub g b`, `l = mul 2.0 j`, ...). These are the forward pass, plus some quantities the
  derivative needs, like $1 - e^2$ and $2 \cdot err$.
- equations that use the tangent (`f = dot a d`, `i = mul f h`, `m = mul i l`, `o = reduce_sum m`,
  `q = div o 3.0`). Every one of them is **linear** in the tangent: it multiplies it by a fixed
  value, sums it, or contracts it with a fixed matrix.

Reverse mode exploits this. **Linearization** runs the first kind now and records only the
second kind, as a jaxpr from tangent to output tangent. The fixed values that the linear jaxpr
needs from the forward pass (here $X$, $1 - e^2$ and $2 \cdot err$) are captured as
**residuals**: the equivalent of the activations an autograd engine saves for the backward pass.
**Transposition** then turns the linear map $t \mapsto Jt$ into its adjoint $u \mapsto J^\top u$
by walking the linear jaxpr backwards. The JAX paper on this design calls it "you only linearize
once": the JVP rules are the only derivatives anyone writes.<Sidenote>Radul, Paszke, Frostig,
Johnson and Maclaurin, [You Only Linearize Once: Tangents Transpose to
Gradients](https://arxiv.org/abs/2204.10923), POPL 2023. The transpose rules are not derivatives:
a primitive like `mul` by a constant is its own adjoint up to swapping arguments, and
`reduce_sum`'s adjoint is a broadcast.</Sidenote>

#### Linearize

[`ad.linearize`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L226)
uses two traces at once. A `LinearizeTracer` holds a primal, which is a real value (or a tracer
of the parent trace), and a tangent, which is a tracer of a separate `DynamicJaxprTrace` called
the **tangent trace**. Primitives on primals are evaluated; primitives on tangents are recorded on
the tangent trace.

[`LinearizeTrace.process_primitive`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L713)
looks for a dedicated linearization rule (only a few primitives, like `sin`, `scan` and `cond`,
have one) and otherwise falls back to the JVP rule run under **partial evaluation**
([`linearize_from_jvp`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L821)):

```python
with core.set_current_trace(trace):          # a pe.JaxprTrace
    tangent_args = [trace.new_arg(pe.PartialVal.unknown(a)) if nz else make_zero(a)
                    for a, nz in zip(tangent_avals, nonzeros)]
    out_primals, out_tangents = jvp.call_wrapped(tuple(primals), tuple(tangent_args), **params)
...
jaxpr, out_consts, _ = pe.tracers_to_jaxpr(in_tracers, out_nz_tracers, ...)
```

- The primals are passed in as **known** values and the tangents as **unknown** placeholders.
- The JVP rule runs as usual. In the partial-evaluation trace
  ([`JaxprTrace.default_process_primitive`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/partial_eval.py#L178)),
  an operation whose inputs are all known is executed immediately; one with any unknown input is
  recorded.
- `tracers_to_jaxpr` turns the recorded operations into a small jaxpr from tangents to output
  tangents. Known values that it uses become its constants: the residuals.

#### Transpose

A linear function $t \mapsto Jt$ built from linear primitives can be reversed one primitive at a
time, in reverse order. Each linear primitive has a **transpose rule**: given the cotangent of its
output, it returns the cotangents of its linear inputs. For our five equations:

| Linear equation | Transpose rule | Source |
| --- | --- | --- |
| `i = div h 3.0` | $\bar h = \bar i / 3$ | `_div_transpose_rule` |
| `h = reduce_sum g` | $\bar g = \text{broadcast}(\bar h)$ | [`_reduce_sum_transpose_rule`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/lax/lax.py#L8610) |
| `g = mul f c` | $\bar f = \bar g \odot c$ | [`_mul_transpose_left`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/lax/lax.py#L5215) |
| `f = mul e b` | $\bar e = \bar f \odot b$ | same |
| `e = dot_general a d` | $\bar d = \bar e^\top a$ | [`_dot_general_transpose_rhs`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/lax/lax.py#L6023) |

The bar marks a cotangent: $\bar v = \partial L / \partial v$. The driver is
[`backward_pass3`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/interpreters/ad.py#L299):

```python
env = dict(zip((*jaxpr.constvars, *jaxpr.invars), (*consts, *primals_in)))
lin_eqns = []
for eqn in jaxpr.eqns:
    if any(isinstance(read(x), GradAccum) for x in eqn.invars):
        for v in eqn.outvars:
            env[v] = ValAccum(v.aval.to_ct_aval())
        lin_eqns.append(eqn)
    else:
        ans = eqn.primitive.bind(*map(read, eqn.invars), **params)
        ...
for acc, ct in zip(map(read, jaxpr.outvars), cotangents_in):
    if isinstance(acc, GradAccum):
        acc.accum(ct)
for eqn in lin_eqns[::-1]:
    cts_in = [env.pop(v).freeze() for v in eqn.outvars]
    ...
    rule = get_primitive_transpose(eqn.primitive)
    cts_out = rule(cts_in, *map(up, primals), **eqn.params)
    for x, ct in zip(primals, cts_out):
        if isinstance(x, GradAccum):
            x.accum(ct)
```

- `env` maps the residuals (constvars) to their values and the linear inputs to **accumulators**
  (`GradAccum`). An accumulator is a slot that collects cotangent contributions.
- The first loop sorts equations. Any equation that reads an accumulator is linear and is queued;
  any other equation only involves residuals and is evaluated right away.
- The output's accumulator is seeded with the incoming cotangent (1.0 for `grad`).
- The second loop walks the linear equations in reverse. It **freezes** each output's
  accumulator into a cotangent, calls the transpose rule, and adds the results into the inputs'
  accumulators. Inside the rule, a linear input appears as an `UndefinedPrimal`: the rule knows
  its type but not its value, which marks it as "the argument to transpose with respect to".
- Accumulating with `add` is what handles fan-out: a value used twice gets the sum of both
  cotangents.

<JaxprSteps data={bwdSteps} title="Transposing the linear jaxpr: cotangents flow backwards" />

The final cotangent of the tangent input, $[-3.7562, -4.9563]$, is the gradient, and its first
entry matches the JVP along $[1, 0]$. Check the second by hand: $\bar e = [-0.1777, -0.7666,
-0.2557]$ and the second column of $X$ is $[2, 4, 6]$, so $\bar w_1 = -0.1777 \cdot 2 - 0.7666
\cdot 4 - 0.2557 \cdot 6 = -4.9563$ (to rounding).

### How grad puts it together

`jax.grad` is a thin layer over `vjp`. Its inner function,
[`value_and_grad_f`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/api.py#L542),
does:

```python
f_partial, dyn_args = argnums_partial2(fun, argnums, args, kwargs)
ans, vjp_py, *maybe_aux = vjp(f_partial, *dyn_args, has_aux=has_aux)
_check_scalar(ans)
g = vjp_py(lax_internal._one_vjp(ans))
```

- `argnums_partial2` fixes the arguments that are not differentiated (`x` and `y`), so the
  function seen by `vjp` takes only `w`.
- [`vjp`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/api.py#L1639)
  calls `ad.linearize(..., is_vjp=True)`: the forward pass runs, and we get the loss value, the
  linear jaxpr and the residuals. It packages them into a `VJP` object, `vjp_py`.
- `_check_scalar` is why `grad` requires a scalar output: the seed below only makes sense for one
  number.
- `_one_vjp(ans)` makes the seed cotangent 1.0, and calling `vjp_py` runs
  [`_vjp3_bwd`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/api.py#L1838),
  which calls `backward_pass3` and returns the frozen accumulators: the gradient.

Under `jit`, all of this runs with jit tracers as primals, so the whole thing (forward pass,
residual computations and transposed linear program) lands in one jaxpr and one XLA program:

<CodeStages stages={gradStages} tags={gradTags} step={0} title="jit(grad(loss)): the jaxpr, StableHLO and optimized HLO" />

Three things to notice:

- In the jaxpr, the loss value is still computed and bound to `_`, a dropped variable, because
  `grad` only returns the gradient. `jit` removes such dead code before lowering (`_dce_jaxpr` in `pxla.py`), so the StableHLO
  has no `reduce` at all.
- The residuals `f` ($1 - e^2$) and `i` ($2 \cdot err$) are ordinary values inside one program.
  There is no saving and restoring across a boundary, unlike the forward and backward graphs that
  [AOTAutograd](/blog/aot-autograd/) produces for PyTorch. XLA is free to recompute or keep them;
  here it fuses all of it into one loop.
- The optimized HLO is two dots, $Xw$ and $X^\top(\cdot)$, around one fused elementwise kernel.
  XLA folded $2 \cdot \frac{1}{3}$ into the constant `0.666666687`. The $1 - e^2$ is computed as
  $(1 + e)(1 - e)$ because that is how `one_minus_square` lowers, for accuracy near $|e| = 1$.

### Composing transformations

Because each transformation is a trace and each rule binds primitives on the trace below,
transformations stack in any order and to any depth. The second derivative of $\tanh$ at 0.5 is
`grad` of `grad`:

```python
jax.grad(jax.grad(jnp.tanh))(0.5)   # -0.72686195
```

and analytically $\frac{d^2}{dx^2}\tanh x = -2 \tanh x \,(1 - \tanh^2 x) = -2 \cdot 0.4621 \cdot
0.7864 = -0.7269$. The outer `grad`'s linearize trace sees the inner `grad`'s JVP and transpose
rules binding `tanh`, `one_minus_square` and `mul`, and differentiates *those*. Every rule that
JAX ships is itself written in terms of primitives, so it is differentiable in turn.

The same holds for `jit` inside other transformations. When `grad` meets a `jit` equation, the
`jit` primitive's JVP rule
([`_pjit_jvp`](https://github.com/jax-ml/jax/blob/32544801e26115ac1794926d027148abf3baf009/jax/_src/pjit.py#L1519))
transforms the inner jaxpr with `ad.jvp_jaxpr` and binds a new `jit` on the result, so the
differentiated function stays a single compiled unit.

## Summary

- JAX never parses Python. It **runs** the function once with **tracers**, and every **primitive**
  bound along the way goes to the **current trace**, which decides what it means: evaluate it,
  record it, differentiate it or batch it.
- A **jaxpr** is the recording made by `DynamicJaxprTrace`: typed variables and a flat list of
  primitive equations. It depends only on shapes and dtypes, which is why `jit` caches by them
  and why Python control flow on array values fails under `jit`.
- `jit` lowers the jaxpr with one **lowering rule** per primitive into **StableHLO**, and XLA
  compiles that, fusing elementwise work and folding constants. Cached calls are dispatched
  entirely from C++.
- **Forward mode** is `JVPTrace`, which applies each primitive's JVP rule to (primal, tangent)
  pairs. **Reverse mode** is the same JVP rules under **partial evaluation** (linearize: compute
  primals and residuals now, record the linear tangent program), followed by **transposition** of
  that linear program, walked backwards with accumulators.
- Because rules are written in primitives and transformations are nested traces, `jit`, `grad`
  and `vmap` compose freely, and higher derivatives come for free.
